## 1. 范围

### 1.1 M1 纳入

| 项 | 内容 |
| --- | --- |
| M1-01 | 启动路径移除 `ESP_ERROR_CHECK` abort |
| M1-02 | 配置应用失败记录（stage / esp error / 配置模式） |
| M1-03 | 运行期候选配置应用失败 → 恢复最近一次成功配置（RAM LKG，见 §1.3） |
| M1-04 | 原配置无法应用 → DHCP 救援（同一 SSID/口令，仅 IP 模式降级）；`dhcpc_stop` 失败立即中止静态应用 |
| M1-05 | DHCP 救援也失败 → 离线待配置，不重启、不空转 |
| M1-06 | 离线态 BLE CMD 可用（连接、登录、状态查询、配置修复） |
| M1-07 | 救援不改写 NVS 持久化配置 |
| M1-08 | Wi-Fi 应用失败不污染 MQTT 状态/错误 |
| M1-09 | 正常启动（DHCP / 合法静态）无回归 |
| M1-10 | 失败路径有界，不形成 CPU 占用或重启循环 |

### 1.2 M1 明确不纳入

| 项 | 归属 | 理由 |
| --- | --- | --- |
| 网络是否真正可用（网关不可达、IP 冲突、DNS 不可解析） | M4/M5 与运行时观察 | **B 类失败**，M1 只保证"配置应用失败不会让设备失联"，不自动判定网络质量 |
| 静态参数语义校验（掩码连续、同网段、网络/广播地址） | M2 | M1 必须能处理**已被持久化**的非法值（旧固件写入/NVS 直写），M2 只能拦截**新写入** |
| DNS 设置/清理与回读 | M2 | M1 不改变 DNS 语义 |
| tryconnect 静态模式 guard | M3 | 独立 PR，不碰 tryconnect 生命周期 |
| VALID/pending 两段提交、启动周期计数、持久化回滚 | M4 | 引入 NVS 状态迁移，风险高于 M1 |
| `network.status` 新字段 | M5 | M1-02 的证据是串口日志 + RAM 状态，不上报新字段 |

> 归属调整（2026-11-02 裁决）：`dhcpc_stop` 失败处理由 M2 上移至 **M1**——它是启动恢复正确性的前置条件（不停止 DHCP 就 `set_ip_info` 会让 netif 处于不一致状态）。M2 仍负责完整语义校验、DNS 清零与回读。

### 1.3 必须先说清的范围裁决：M1-03 的"原有效配置"是什么

M1 没有 pending/VALID 双份持久化，**冷启动时 NVS 里只有一份配置**，不存在"上一份有效配置"可回退。因此 M1-03 按以下口径成立（**待评审确认**）：

| 场景 | "原有效配置" | M1 行为 |
| --- | --- | --- |
| 冷启动（唯一配置应用失败） | 不存在第二份持久化配置 | M1-03 **不适用**，直接进入 M1-04 DHCP 救援 |
| 运行期 re-apply（`network.restart` / 配置变更后的运行时重应用） | 本启动周期内最近一次成功应用的配置（RAM LKG） | 恢复 LKG 并重应用；LKG 也失败才进入 DHCP 救援 |

**RAM LKG 的硬约束（2026-11-02 裁决）**：

1. LKG 必须是**已经通过配置校验、且成功应用**的配置快照，不得简单复制当前正在尝试的候选配置。
2. LKG 不存在，或 LKG 自身恢复失败 → **必须继续进入 DHCP 救援**。
3. **不得再次尝试同一份失败配置**（LKG 与失败候选相同则跳过 LKG 步骤）。
4. 验收必须区分冷启动与运行期：**冷启动的 DHCP 救援成功不能算作 LKG 恢复成功**。

实现上把"恢复来源"抽象成 `app_wifi_apply_cfg_t`；M4 只需把来源从 RAM 换成 NVS 的 VALID 配置，状态机与验收表不变（见 §9）。这样 M1 不引入任何 NVS 状态迁移，也不会把 M4 的复杂度提前。

## 3. 设计

### 3.1 应用阶段与失败记录（M1-02）

```c
typedef enum {
    APP_WIFI_APPLY_STAGE_NONE = 0,
    APP_WIFI_APPLY_STAGE_WIFI_STOP,
    APP_WIFI_APPLY_STAGE_SET_MODE,
    APP_WIFI_APPLY_STAGE_SET_CONFIG,
    APP_WIFI_APPLY_STAGE_STATIC_DHCPC_STOP,
    APP_WIFI_APPLY_STAGE_STATIC_PARSE,
    APP_WIFI_APPLY_STAGE_STATIC_SET_IP,
    APP_WIFI_APPLY_STAGE_STATIC_SET_DNS,   /* 预留：M2 检查 DNS 返回值后启用 */
    APP_WIFI_APPLY_STAGE_DHCPC_START,
    APP_WIFI_APPLY_STAGE_WIFI_START,
} app_wifi_apply_stage_t;

typedef struct {
    bool valid;                  /* 本启动周期是否发生过应用失败 */
    app_wifi_apply_stage_t stage;/* 首个失败阶段（根因，不被后续恢复覆盖） */
    esp_err_t err;               /* 首个失败错误码 */
    bool static_mode;            /* 失败时配置模式 */
    uint8_t attempts;            /* 本启动周期应用尝试次数（正常 1，救援 2） */
    char recovery[16];           /* none | lkg_restore | dhcp_rescue | offline */
    esp_err_t offline_stop_err;  /* esp_wifi_stop() 失败时的原始错误；ESP_OK 表示停止成功 */
} app_wifi_apply_failure_t;
```

运行时状态（RAM，M5 才对外暴露）：

```c
typedef enum {
    APP_NET_CFG_STATE_DHCP = 0,
    APP_NET_CFG_STATE_STATIC,
    APP_NET_CFG_STATE_FALLBACK,                /* 静态失败后 DHCP 救援运行中 */
    APP_NET_CFG_STATE_OFFLINE,                 /* 离线待配置，Wi-Fi 已停止 */
    APP_NET_CFG_STATE_OFFLINE_STOP_FAILED,     /* 离线，但 esp_wifi_stop() 实际执行并失败 */
    APP_NET_CFG_STATE_OFFLINE_QUIESCE_TIMEOUT, /* 离线，但连接调用未退出，未执行 stop（不得伪装成 stop 失败） */
    /* M4: APP_NET_CFG_STATE_PENDING / ROLLBACK_STATIC */
} app_net_cfg_state_t;
```

固定日志格式（便于测试 grep 与 M5 复用）：


**并发原语与生命周期日志**（T15/T16 断言的唯一依据；发射点固定，不得由实现自由发挥）：

```text
D (wifi) connect_begin inflight=%u path=%s      /* 发射点：app_wifi_connect_begin() 返回 true 的临界区出口内 */
D (wifi) connect_end   inflight=%u path=%s      /* 发射点：app_wifi_connect_end() 临界区内；path ∈ {profile, fast_path, pmf_retry, retry_direct} */
I (wifi) offline_gate_set                      /* 发射点：置 s_wifi_cfg_offline=true 的临界区出口 */
I (wifi) offline_gate_clear                    /* 发射点(A8):本次 apply 的 STA_START 处理器内(释放与启动窗口同点);仅当门控为 set 时打印 */
I (wifi) wifi_stop_begin                       /* 发射点：app_wifi_enter_offline()/恢复链中 esp_wifi_stop() 调用前 */
I (wifi) wifi_stop_end err=%s                  /* 发射点：esp_wifi_stop() 返回后；err=none 表示成功 */

```

日志行约束：

1. 上表每一行都是 T15/T16/B11/B12 grep 断言的依据；实现少打、改格式、改字段名，对应用例必须判 FAIL，不允许"默契豁免"；
2. `connect_begin` / `connect_end` 必须严格配对成对出现，计数相等（`inflight` 从 1 回到 0）；
3. `offline_gate_set` / `offline_gate_clear` 每次状态切换各一条，不重复打印；
4. `wifi_stop_begin` / `wifi_stop_end` 成对出现；`offline_quiesce_timeout` 与 `recover_quiesce_timeout` 路径**禁止**出现这两个标记；
5. `apply_begin` 在同一恢复链最多出现 1 次（boot 路径 1 次；恢复链 LKG/救援合并为一次链、一个入口行）。

### 3.2 启动路径去 abort（M1-01）

把 `app_apply_wifi_config()` 拆成"取配置 + 应用"，应用函数带 stage 出参，启动入口改为非致命封装：

```c
/* main/wifi.c，替换 2385 行 */
ESP_ERROR_CHECK(esp_netif_init());
...
app_wifi_boot_apply_or_recover();   /* 不再 abort */

static void app_wifi_boot_apply_or_recover(void)
{
    app_wifi_apply_stage_t stage = APP_WIFI_APPLY_STAGE_NONE;
    app_wifi_apply_cfg_t cfg;

    app_wifi_build_cfg_from_config(&cfg);           /* s_config 快照 */
    if (app_wifi_apply_cfg(&cfg, &stage) == ESP_OK) {
        app_wifi_lkg_capture(&cfg);
        app_wifi_set_cfg_state(cfg.sta_use_static ? STATIC : DHCP);
        return;
    }
    app_wifi_record_apply_failure(stage, err, cfg.sta_use_static);
    ESP_LOGE(...apply_failed...);
    app_wifi_recover_from_apply_failure(&cfg);
}
```

注意：`esp_netif_init/event_loop_create_default/esp_wifi_init/event handler register` 的 `ESP_ERROR_CHECK` **保留**——它们失败属于平台级不可恢复错误，与静态配置无关，不在 M1 改造面内。

### 3.3 恢复状态机

```text
apply(candidate)
   │ OK
   ├──► 运行：state = static | dhcp，记录 LKG
   │
   └──► 失败（A 类）
          │ 记录 stage/err/mode
          ▼
   ① LKG 恢复（仅运行期且 LKG 与 candidate 不同）
          │ OK ──► state = LKG 模式，recovery=lkg_restore，结束
          │ 失败/不适用
          ▼
   ② DHCP 救援（同 SSID/口令，强制 DHCP）
          │ OK ──► state = fallback，recovery=dhcp_rescue，结束
          │ 失败
          ▼
   ③ 离线待配置（先门控，后停 Wi-Fi）
          ③a 置 s_wifi_cfg_offline=true，封锁所有连接调度入口
          ③b 等待 in-flight 连接调用归零（R3）
                │ 已归零 ──► esp_wifi_stop()
                │              │ OK / NOT_STARTED ──► state = offline
                │              │ 失败 ──► state = offline_stop_failed（记录原始 err）
                │ 未归零（总等待超限）──► state = offline_quiesce_timeout
                │                          **不调用 esp_wifi_stop()**（R3.1）
          以上状态均：BLE 保持可用；不重启；不允许任何自动连接调度
```

- **每次启动周期最多 1 次静态尝试 + 1 次 LKG 恢复 + 1 次 DHCP 救援**，之后进入 offline；不存在循环重试。
- **LKG 只允许尝试与失败候选不同的配置**；LKG 不存在、与候选相同或恢复失败 → 直接进入 DHCP 救援，不得重复同一失败配置。
- **in-flight 未归零时绝不强制 `esp_wifi_stop()`**；宁可暂时不停止 Wi-Fi，也不声称 stop 与 connect 已串行化。
- 顺序固定，不允许"直接重启兜底"（实施方案附录 A.1 第 6 条）。
- 所有路径都**不写 NVS**（M1-07）。

1. M1 所有路径**不改写 NVS**；`config.get` 在救援/离线后仍返回持久配置（静态字段原样）。
2. 任何 A 类失败都不产生 abort / `Guru Meditation` / `rst:` 循环。
3. 所有 A 类路径 BLE 均可用（BLE 先于 Wi-Fi 初始化，`main/main.c:77-88`）。
4. 救援只降级 IP 模式（DHCP），**不改 SSID/口令、不清静态字段、不改 NVS**。
5. 每次应用尝试链有界：静态 → LKG → DHCP → offline，无循环。
6. B 类（S10/S11）**不触发**自动改配置或回滚；只按现有运行时策略重试/观察。
7. 离线门控**必须先于 `esp_wifi_stop()` 生效**；`esp_wifi_stop()` 失败时门控保持，事件链直连（`do_retry_direct` → `esp_wifi_connect()`）与 connect task 入口同样被抑制，禁止出现"停止失败 → 事件链重连 → 再失败"的循环。
8. 离线门控**禁止由定时器解除**；只允许有效配置提交或受控恢复操作解除。
9. **in-flight 未归零时绝不执行 `esp_wifi_stop()`**；quiesce 超时必须记为 `offline_quiesce_timeout`，不得记为 `offline_stop_failed`。

#### 3.4.1 S9b / S9c 状态定义

`offline_stop_failed` **不是**普通 `offline` 的同义词，必须同时满足并可由日志/RAM 区分：

1. 配置应用失败（保留首个失败 stage / err / mode）；
2. LKG 不适用或恢复失败；
3. DHCP 救援失败（记录救援 stage / err）；
4. `esp_wifi_stop()` 失败（记录原始 stop err）；
5. 离线门控仍然有效（`s_wifi_cfg_offline == true`）；
6. Wi-Fi 驱动运行状态**未知**（可能仍 started，或 stop 执行到一半）；
7. BLE 仍可用；
8. **禁止**任何自动连接调度；
9. 允许用户经 BLE 提交有效配置，或显式 `network.restart` 重新发起受控恢复；
10. 受控恢复前必须**重新 quiesce**：保持门控、等待旧 in-flight 归零后才允许 apply（R6）。

固定日志：

```text
E (wifi) offline_stop_failed apply_stage=wifi_start apply_err=0x%x rescue_err=0x%x stop_err=0x%x
I (wifi) net_config_state=offline_stop_failed
```

M5 的状态查询必须区分 `offline_pending_config`（stop 成功）与 `offline_stop_failed`（stop 失败），不得合并为单一 offline 值。

**S9c（`offline_quiesce_timeout`）**：与 S9b 严格区分——此时 **未调用** `esp_wifi_stop()`，原因是 in-flight 连接调用未在等待上限内退出：

1. 配置应用失败 + LKG 不适用/失败 + DHCP 救援失败；
2. 离线门控已置位且保持；
3. 连接调用在总等待上限内未退出（记录 inflight、耗时）；
4. **不执行** `esp_wifi_stop()`，Wi-Fi 运行状态未知；
5. BLE 可用；禁止自动连接；允许显式受控恢复；
6. **不得**标记为 `offline_stop_failed`；
7. 受控恢复前必须**重新 quiesce**：保持门控、等待旧 in-flight 归零后才允许 apply（R6）；仍超时则保持本状态并拒绝恢复。

固定日志：

```text
W (wifi) offline_quiesce_wait: inflight=%u elapsed=%ums
E (wifi) offline_quiesce_timeout: inflight=%u elapsed=%ums, wifi_stop NOT called
I (wifi) net_config_state=offline_quiesce_timeout
```

M5 是否暴露 `offline_quiesce_timeout` 单独取值，留待 M5 评审；M1 内部状态与日志必须区分。

### 3.5 运行期 re-apply 与 M1-03

- 新增 RAM LKG：

```c
typedef struct {
    bool valid;
    bool sta_use_static;
    char ssid[33];
    char password[65];
    char static_ip[16];
    char static_gw[16];
    char static_mask[16];
    char static_dns1[16];
    char static_dns2[16];
} app_wifi_apply_cfg_t;   /* 同时作为 LKG 的承载结构 */
```

- 每次 `app_wifi_apply_cfg()` **成功后**更新 LKG。
- LKG 只接受"已通过配置校验且成功应用"的快照；**不得由正在尝试的候选配置复制生成**。
- 运行期 re-apply 失败：若 `lkg.valid` 且 LKG 与本次候选不同（SSID + IP 模式 + 静态字段比较），先按 LKG 重应用；成功即恢复原网络，日志 `recover action=lkg_restore result=ok`。
- LKG 与候选相同（例如启动时唯一配置失败）→ 跳过 LKG，直接 DHCP 救援，避免对同一配置重复尝试。
- LKG 恢复失败 → 继续 DHCP 救援，不得再次尝试 LKG 或候选。
- 该路径不依赖 `app_config_snapshot_*`；现有 `network.apply` 的快照/回滚语义保持不变（M1 不动 `main/cmd.c` 的 apply 事务）。

**LKG 生命周期（逐事件，2026-11-03 审查项）**：

| 事件 | LKG 动作 |
| --- | --- |
| 启动 apply 成功 | 建立 LKG（本次 cfg） |
| 运行期 apply 成功 | 覆盖为本次 cfg |
| `config.set` 仅保存（reboot 生效） | **不更新**（未应用） |
| 候选 apply 失败 | **不更新**；LKG 保持上次成功值 |
| `network.restart` 前 | 无需额外快照；LKG 已是上次成功值，候选失败不会覆盖它 |
| LKG 恢复成功 | 内容不变，不重新 capture；state 回到 LKG 模式 |
| LKG 恢复失败 | 不再尝试 LKG 或候选，立即 DHCP 救援 |
| 重启 | RAM LKG 失效；M4 改由 NVS VALID 承担 |

LKG 等价比较字段：SSID + 口令 + `sta_use_static` + 静态五字段；口令仅做 `memcmp`，任何日志/状态都不输出口令。

> A8-r10 补充：LKG 定义为"最近一次成功 apply 的配置"，因此 **DHCP 救援成功也会成为 RAM LKG**（预期语义：运行期回退以最近可运行配置为准）；持久化 VALID 语义仍由 M4 承担。另：每次 apply 必须独立完成 `hold+drain`，drain 失败的那一步不得操作 driver；恢复链的下一步必须重新 drain，不能沿用上一步结果。

### 3.6 离线态与重试门控（M1-10）

关键风险（源码事实）：

1. `app_apply_wifi_config()` 开头调用 `app_wifi_stop_startup_connect_window()`，该函数置 `s_wifi_rt_armed=true`（`main/wifi.c:493`）。此后即使 Wi-Fi 已 stop，`wifi_boot_monitor` 仍按 5s/10s/30s/60s 调度 `esp_wifi_connect()`（每次 `ESP_ERR_WIFI_NOT_STARTED`）。
2. **事件链直连路径绕过调度入口**：`WIFI_EVENT_STA_DISCONNECTED` 处理器在 `do_retry_direct` 分支直接调用 `esp_wifi_connect()`（`main/wifi.c:1809-1818`），不经过 `app_wifi_schedule_connect_task()`。只在调度函数加门控不足以抑制重试。

**进入离线的固定顺序**（2026-11-02 裁决：先门控，后停 Wi-Fi）：

```c
1) 同一临界区内：s_wifi_cfg_offline = true      /* 先门控 */
2) app_wifi_stop_startup_connect_window();       /* 停 90s 窗口 */
3) 封锁全部连接入口（begin() 从此拒绝新许可）：
   - app_wifi_schedule_connect_task() 入口 return
   - app_wifi_connect_task_fn() 起始处 return（拦截已创建任务）
   - WIFI_EVENT_STA_DISCONNECTED 的 do_retry_direct 分支跳过 esp_wifi_connect()
   - WIFI_EVENT_STA_START 在离线时只记录，不开启 90s 窗口、不调度连接
   - wifi_boot_monitor 两条运行时兜底条件追加 && !s_wifi_cfg_offline
   - app_wifi_try_connect_common() 入口返回 APP_WIFI_TRY_CONFIG_OFFLINE
4) app_wifi_wait_connect_inflight(1000ms)        /* 200ms 告警阈值 */
   - 未归零 → state = offline_quiesce_timeout，跳过 5)，不执行 stop
5) esp_wifi_stop()
   - OK / NOT_STARTED / NOT_INIT → state = offline_pending_config
   - 其他错误 → state = offline_stop_failed，记录原始 err；门控保持
6) BLE 服务不动；network.status / config.get / config.set 可用
```

- `esp_wifi_stop()` 失败**不得**导致重启或恢复连接调度；只记录并保持门控。
- 离线态下 `network.status` 仍可用（不调用需要 Wi-Fi 已启动的 API；`esp_wifi_sta_get_ap_info` 失败时 `rssi_valid=false`，现有逻辑已兼容）。
- **门控解除条件（仅两种，禁止定时器解除）**：
  1. 用户经 BLE 提交新的有效配置，并触发受控恢复流程（apply / 重启）；
  2. 用户显式执行一次受控网络恢复操作（`network.restart`）。
- 解除时先清标志，再走正常 apply；失败会重新进入离线门控。
- 显式 BLE 重试不计入"自动重试"，但每次只走一条有界恢复链（§3.3）。

**并发与竞态规则（2026-11-03 审查项）**：

- **R1**：`s_wifi_cfg_offline` 的读写统一经 `app_wifi_runtime_lock()` 保护的 helper（`app_wifi_connect_blocked()` / `app_wifi_set_offline()`）；禁止裸读写。
- **R2**：全部**自动**连接调用点必须通过 `app_wifi_connect_begin()` 取得许可；不依赖任务创建时或事件入口处的单次检查。
- **R3（原子许可）**：连接许可与 in-flight 增加必须是**同一临界区**：

```c
bool app_wifi_connect_begin(void);   /* 同一把锁内：检查 offline → 允许则 inflight++ */
void app_wifi_connect_end(void);     /* 同一把锁内：inflight-- */
```

  连接侧只有 `begin()==true` 才可调用 `esp_wifi_connect()`；`end()` 在驱动调用返回后执行。离线侧在**同一把锁**内置 `offline=true`，随后等待 in-flight 归零；**归零前绝不调用 `esp_wifi_stop()`**。
- **R3.1（quiesce 超时）**：等待 200ms 仅作告警阈值，总等待上限 1000ms。到期仍未归零 → 状态 `offline_quiesce_timeout`，**不执行 stop**，门控保持，记录 inflight 与耗时，等待显式受控恢复；不得记为 `offline_stop_failed`。
- **R3.2（覆盖范围与配对）**：1–4 号自动调用点**全部**用 `begin/end` 包裹，包括事件链 `do_retry_direct`（:1816）与 PMF 重试（:1344）；不能只依赖事件处理器前面的普通门控检查。`end()` 必须在所有路径执行（含 `esp_wifi_connect()` 返回错误、提前 return 分支）；begin 与 end 之间不得出现未配对的 return。
- **R4**：已排队 connect task：延时结束后重新检查；被门控时不改 `s_wifi_sta_connecting`，直接退出。
- **R5**：迟到的 `WIFI_EVENT_STA_DISCONNECTED`：在 tryconnect 归属检查之后若被门控，直接 return，不进入 PMF 重试、直连或调度分支；`WIFI_EVENT_STA_START` 在离线时只记录，不开启 90s 窗口、不调度。
- **R6（恢复前置条件，不是绕过 quiesce 的通道）**：显式恢复不得直接清除门控后 apply。对 `offline_quiesce_timeout` 与 `offline_stop_failed`：
  1. 保持 `offline=true`；
  2. 重新等待旧 in-flight 归零（同一 200ms 告警 / 1000ms 上限）；
  3. 仍超时 → **保持原状态，拒绝本次恢复**（返回现有失败码），不得清门控、不得启动新 apply；
  4. 归零 → 清门控后进入 apply；`offline_stop_failed` 的 apply 首次 `esp_wifi_stop()` 即受控重试，失败重新进入 `offline_stop_failed`；
  5. 记录 `recover_quiesce_wait` / `recover_quiesce_timeout`，供事后判定。
- **R7**：离线标志只在任务上下文写，禁止 ISR 写入。
- **R8**：`esp_wifi_stop()` 失败保持门控，不重试 stop、不重启；状态转 `offline_stop_failed`。
- **R9（显式 tryconnect）**：离线门控期间，`app_wifi_try_connect_common()` 在**取得候选生命周期所有权之前**检查离线并返回 `APP_WIFI_TRY_CONFIG_OFFLINE`；不进入预扫描/候选连接，不调用 `esp_wifi_connect()`。正常模式行为与事件归属状态机不变。

> R3/R3.1 保证 `esp_wifi_stop()` 不会与 `esp_wifi_connect()` 并发；R2/R4/R5/R9 保证门控置位后不再产生任何连接（自动或显式）。

#### 3.6.1 自动连接调用点清单与显式 tryconnect 拒绝

`main/` 内 `esp_wifi_connect()` 实际调用点共 5 处：**4 处自动门控 + 1 处入口拒绝**（逐点明细见 [PR 边界文档](静态IP_M1实现PR边界与测试计划_2026-11-03.md) §2.4）：

| # | 位置 | 触发来源 | M1 门控 |
| --- | --- | --- | --- |
| 1 | `app_wifi_connect_profile_index()` :809 | connect task → profile 连接 | `connect_begin()` 原子许可 |
| 2 | `app_wifi_connect_best_saved_profile()` :893 | connect task → fast path | `connect_begin()` 原子许可 |
| 3 | `app_wifi_retry_with_pmf_required()` :1344 | 断开事件 reason 210 | `begin/end` 包裹；处理器门控只决定是否尝试 |

### 3.7 BLE 救援保证（M1-06）

- 启动顺序已是 BLE → Wi-Fi（`main/main.c:77-88`），去掉 abort 后 BLE 不再可能被 Wi-Fi 配置失败带死。
- 离线态只停 Wi-Fi，不动 NimBLE 与 data_pipe。
- 可用命令（不新增）：`auth.login`、`network.status`、`config.get`、`config.set`、`system.info` 等现有命令。
- 修复路径：`config.set`（保存到 NVS）→ 重启 → 新配置按 §3.2 重新尝试。
- **M1 不新增状态字段**；"离线"的可观察性由 M5 补（`network_config_state`）。

### 3.8 MQTT 隔离（M1-08）

- Wi-Fi 应用失败只写 `app_wifi_apply_failure_t` 与 Wi-Fi 日志，**不触碰** `s_mqtt.last_error` / `s_mqtt.fatal_error`。
- MQTT 在 Wi-Fi 之后启动（`main/main.c:[boot-10]`），Wi-Fi 失败不再 abort，MQTT 初始化按原逻辑执行；无网络时由 MQTT 自身重连策略处理。
- 验收：故障场景下 `network.status.mqtt_last_error` 不含 Wi-Fi 阶段错误；日志中 Wi-Fi 失败行 tag 为 `wifi`，MQTT 行为 `mqtt`。

### 3.9 NVS 不变式（M1-07）

- M1 新增代码路径对 NVS **只读**。
- 现存唯一写 NVS 的路径仍是 `config.set` / `network.apply`（M1 不改其保存语义）。
- DHCP 救援是**运行时救援**，不改 `s_config.sta_use_static`，不改静态字段；重启后仍会先尝试静态配置（再次进入救援），这是预期行为，持久化回滚由 M4 解决。

**不可接受结果（任一出现即 M1 不通过）**：

1. 任一 A 类注入导致 abort/重启循环或 BLE 不可连；
2. 救援路径改写 NVS 或清空静态字段；
3. 离线态仍按 5/10/30/60s 调度 Wi-Fi 连接；
4. B 类场景（无 GOT_IP / ARP 冲突）触发自动改配置或断网；
5. `network.status` 在离线态返回错误或超时；
6. `esp_wifi_stop()` 失败后事件链直连或 connect task 重新发起连接；
7. 离线门控被定时器/周期任务自动解除；
8. LKG 与失败候选相同仍被重复尝试；
9. in-flight 未归零仍执行 `esp_wifi_stop()`，或把 `offline_quiesce_timeout` 记为 `offline_stop_failed`。

## 9. 与 M4 的升级路径

M1 的恢复状态机预留了 M4 的插入点，M4 **不改 M1 结构**，只改数据来源并追加状态：

| M1 | M4 |
| --- | --- |
| LKG 来源 = RAM（本启动周期） | VALID 来源 = NVS 主配置（跨启动） |
| 冷启动无 LKG → 直接 DHCP 救援 | 冷启动有 VALID → 先恢复 VALID，再救援 |
| 无 pending | 启动时优先应用 `cfg_pending`，验证窗口内 confirm |
| `state ∈ {dhcp, static, fallback, offline}` | 追加 `pending`、`rollback_static` |
| 无启动周期计数 | `pending_boot_id` 计数，连续 3 次失败熔断 |
| 决策表 S0–S15 | 追加 pending 应用/确认/回滚/断电行 |

确认条件沿用实施方案附录 A.2：窗口内 GOT_IP **且** `sta_ip_conflict == clear`；`unknown ≠ clear`。

### 10.2 遗留的实现级问题（PR 草案阶段定稿，不阻塞设计定稿）

1. LKG 等价比较的字段集合：SSID + IP 模式 + 静态五字段；口令仅用于判等，不落日志。
2. 失败/状态结构放 `runtime.h` 还是 `wifi.c` 内部：建议 `runtime.h`，供 M5 直接复用。
3. 日志字段顺序与错误名格式：沿用 `esp_err_to_name()`。
4. 测试钩子的 stage 名称与 `diag.testhook` 参数格式。
5. `network.restart` 返回成功但异步 apply 失败的既有语义：M1 不改响应，只保证恢复链与日志。
6. **离线进入/恢复时既有连接中标志的复位策略**：`esp_wifi_stop()` 不保证产生 `STA_DISCONNECTED` 事件（接口直接 down），故障前残留的 `s_wifi_sta_connecting=true`、`s_wifi_connecting_since_ms` 等可能残留；若不复位，恢复链 apply 后 `STA_START` 开窗与新连接调度可能被"仍在连接中"的旧状态抑制。定稿要求：进入离线（stop 成功）时统一复位连接中标志；恢复链 `apply_begin` 前再次校验无残留连接中状态。实现期逐点核对，进 PR 评审清单。
   **实现核对清单（7 项，PR 评审逐条勾选）**：`s_wifi_sta_connecting`、`s_wifi_connecting_since_ms`、`sta_connected`、`sta_has_ip`、`sta_ip_conflict`、`sta_retries`、`connected_ssid`+sta_ip strings；**`connect_inflight` 不在复位清单**——它是同步原语状态，只能由 begin/end 改写，状态清理代码不得强置（§10.7-A6）；以及 **`s_wifi_fast_path_pending`/`s_wifi_formal_only_pending` 显式不复位 + 理由**：两标志在 schedule 入口与 connect task 二次检查处均被门控拦截、monitor 同被门控不会误消费，解除门控后的第一次正常调度按原语义读取，无需清理（§10.7-A2）。
7. `app_wifi_wait_connect_inflight(1000ms)` 的 200ms 告警阈值表达方式：建议 1000ms 作参数、200ms 作内部常量（或独立告警参数）；定稿随 PR 签名一并给出。
