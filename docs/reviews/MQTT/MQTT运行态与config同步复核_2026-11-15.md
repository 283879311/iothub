# MQTT 运行态与 config 同步：实施证据

> **文档状态：HISTORICAL（实现证据；当前验证状态以 CMD 任务台账为准）**  
> **产品基线：** 固件 1.3；相关实现提交见下文。  
> 本文保留实现依据、锁边界和未验收事实，不再维护实施前逐行审查过程。

## 1. 问题与实施结论

原问题是 MQTT 任务在无锁情况下读取 `s_config` 与配置更新并发，可能产生数据竞争；同时 MQTT 读取 `s_wifi` 未持 Wi-Fi 运行态锁 W。

当前实现：

| 项目 | 实施结果 | 证据 |
|---|---|---|
| R1 MQTT 配置读取 | `app_mqtt_cfg_snapshot()` 在 C 锁内复制 MQTT、UART、网络模式及属性所需字段；锁外执行 stop/init、URI 构造等操作 | `999db00fd34d8b8696ae49e8a163c082c891f584` |
| R2 telemetry/state | 属性与状态发布各自取得一次配置快照，锁外构造 JSON | 同上 |
| token 生命周期 | 使用模块静态 `s_token_snap`，不把全局配置 token 缓冲区地址交给 esp-mqtt | 同上 |
| R4 Wi-Fi 状态 | `app_mqtt_wifi_snapshot()` 在 W 锁内复制 `sta_has_ip/sta_ip`，替换四处读取 | `8d7d768e46b46f9c2ff5574dcdfe53d26c72ed7a` |

## 2. 必须保持的并发约束

- C 锁只用于复制配置字段；不得把 esp-mqtt stop/init、JSON 构造或发布操作移入 C 锁。
- C 快照返回并释放 C 后，才单独取得 W 快照；C 与 W **不嵌套**。
- 配置快照与 Wi-Fi 快照是先后独立取得，只保证各自字段受对应锁保护，**不保证同一时刻的一致性**。
- 保留既有 `M→W` 顺序；新增的 W 快照调用点不得持有 M，不能引入 `W→M`。
- MQTT 的 `s_config` 读取应继续集中在配置快照函数内；Wi-Fi 状态读取应继续集中在 Wi-Fi 快照函数内。
- `s_token_snap` 的静态存储期是当前实现对 esp-mqtt 字符串生命周期的保护；R5 对底层库复制语义的独立确认仍未完成，不得把它写成已验证通过。
