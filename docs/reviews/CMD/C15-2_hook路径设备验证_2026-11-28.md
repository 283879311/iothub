## 3. A0：生产固件连接参数预检（只读）

条件：连接前用 `MGMT_OP_LOAD_CONN_PARAM (0x0035)` 写入 per-peer 参数 24–40 units / latency 0 / supervision 600，`addr_type = BDADDR_LE_PUBLIC (0x01)`；btmon 从连接前开始；连接后仅发送免 token 的 `device.info`（5 s 一次）。

| 判据 | 结果 |
|---|---|
| `LE Create Connection` | min 30 ms / max 50 ms / latency 0 / supervision 6000 ms (0x0258) |
| `LE Enhanced Connection Complete` | interval 45 ms / latency 0 / supervision 6000 ms |
| 设备策略 | `sup=6000ms -> satisfied, skip update request`（仅此一条） |
| 60 s 静置 | 11 次心跳全部 `ok`，无断链；无 `LE Connection Update`、无远端参数请求 |
| 结束方式 | 我方 `Disconnect`（0x16/0x13），非设备侧超时 |

实现要点（内核源码核实）：

- `mgmt_hdr = {opcode, index, len}`；`0x0015` 是 `GET_CONNECTIONS`（固定长度 0），误用会 `EINVAL`。
- `addr_type = 0` 是 `BDADDR_BREDR`，`load_conn_param` 对非 LE 类型静默 `continue`，但仍返回 `Command Complete status=0`——表现为“成功却无效”。
- 内核 per-peer `hci_conn_params` 在**创建时**拷贝 `hdev` 默认值（默认 supervision 42 = 420 ms）；事后修改 debugfs 不影响已有条目。
- BlueZ 5.72 经 `bt_io_connect(BTPROTO_L2CAP, CID=ATT)` 建链 → 内核 `hci_connect_le()` → `hci_le_create_conn_sync()` 读取 `hci_conn_params`，故上述 MGMT 参数对该路径生效。

文件（证据分支）：`artifacts/c15_a0_a1_20261128/a0/a0_hold_r4.json`、`a0/a0_serial.log`、`a0/a0_btmon_params.txt`。

## 6. 排除项（审核用）

1. 日志中 `password` 字段是 harness `sanitize()` 输出的 `<redacted>` 占位符（恰好 10 字符），不是真实口令；证据包与本文均不含凭据。
2. 设备使用 Kconfig 出厂默认口令（`main/Kconfig.projbuild` 的 `AUTH_DEFAULT_PASSWORD`），本轮**未修改任何凭据或认证配置**。
3. 预跑尝试 1 因把占位符当作口令而 `invalid_credentials`，脚本在**任何写命令之前**退出，无设备副作用；尝试 2 用默认口令完成实验。
4. 0x222 根因在主机侧：per-peer `hci_conn_params` 使用默认 420 ms supervision，触发设备 out-of-policy 参数更新请求且主机侧未完成（依据：`a1/a1_btmon_params.txt` 与主机侧 `hci_conn_params` 默认 420 ms supervision 记录）。设备固件未修改。
5. MGMT 参数条目为内核内存态：适配器下电/重启或重启 bluetooth 服务后失效，需重新写入。
