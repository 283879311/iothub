## 1. 双 TTL 时间线（P0 修正稿）

```
T0 = app_cmd_net_store_trial()            → trial TTL 起（300s）
     （此时 try_connect_ip() 已返回 OK——连接与 netcheck 等待全部发生在 T0 之前）
T1 = app_operation_set_state(GOT_IP)      → operation TTL 起（300s）
Δ  = T1 − T0 = store 后快照读取与状态交付的实际间隔（源码口径，预期亚秒级，
     执行时实测记录；不得按连接/netcheck 耗时估算）
trial 预计到期 T0+300s；operation 预计到期 T1+300s ≈ T0+300s+Δ
operation.c expire task ≈1s 轮询；进入 cleanup 后按 operation ID 清 trial
     ⇒ async 分支内"A（trial 独立过期）"可观测窗口 ≈ Δ（亚秒级），轮询不可靠
```

**证据强度决定（裁决方案 1）**：trial 自身 TTL 的 lazy 清理由**专用 BLE sync
TTL 分支**独立证明（§2 S2'，无 operation，真正隔离）；async 分支（S4）只保留
B 观测（operation expired/cleanup/job clear），A 降为机会性记录。

## 2. 分支与顺序（裁决方向不变，插入专用 TTL 分支）

```
S0 身份守卫（§3）→ 串口在录确认 → 前置 device.status/config.get
S1 分支① BLE sync trial cancel（零 op 零 async）：
   sync tryconnect → 受理响应 → trial ready 采集 → BLE cancel{trial_id}
   → {trial_id,"cancelled"} 采集 → trial idle 采集
S2 分支② BLE sync 04c 段 A（独立，不复用 trial）：
   sync tryconnect → 原始受理响应帧+键序 → trial ready 采集
   → BLE cancel → trial idle
S3 分支③ trial 不匹配构造尝试（只读；不匹配 ID 明确指定，见下）
S4 分支④ BLE sync 专用 TTL 分支（新增，无 operation）：
   sync tryconnect → trial ready 采集（记 T0' = 受理响应时刻）
   → **不 cancel、保持 BLE 会话不断**（BLE 断连会清 trial——v3 已核 ：401）
   → T0'+270s 起每 15s 查询 network.status（预到期采样，应仍 ready）
   → T0'+300s 起每 15s 查询（应出现 state:"idle"——该查询本身即触发
     trial_ready lazy clear，与前一帧 ready 构成成对证据）
   → 观测完成即止（trial 已 idle，无需 cancel）
S5 分支⑤ MQTT async expired（唯一改指向段）：
   S5a 改指向（§5）→ 接入 mini_broker ≤75s
   S5b async tryconnect → GOT_IP（**实测记录 T0/T1 与 Δ**）
   S5c B 观测：operation 自然 expired → cleanup 确认（persistent 恢复）
       + job clear 确证（≥120s）+ trial 终值记录
   S5d 机会性 A：仅在轮询恰好捕获 trial 于 operation 终态前 idle 时记录；
       未捕获记"未观察到"，不作失败、不声称独立验证
   S5e 恢复指向 → TB:21883 验证
S6 结束态验收（§7）→ SHA256SUMS
```

**分支③ 不匹配 ID 明确指定**：`op-00000000CDEF1234`（格式合法的**不存在**
id）——BLE `operation.get{operation_id: "op-00000000CDEF1234"}` + 同刻
`network.status`（trial ready 块在场）；实测 wire 归档。若结果不构成 04b
判定表的 mismatch 分支形态，如实记"该分支按此构造不可达"+原因，不强造。

衔接已核实：①②④ 均以 trial idle 收尾（cancel 或 lazy clear）→ 后续 sync/async
入口 trial-busy 检查不阻塞；⑤ 入口另受 `s_net_async.active` 与 trial 忙检
双重兜底。

## 6. 异常恢复规则（与 v3/v4 相同，要点重列）

身份漂移/新 boot → STOP（改指向状态先恢复）；BLE 断连 → 重连 ≤3 次 → 失败
按 §5 声明处置（**分支④ 特别强调：BLE 断连会清 trial，该分支立即作废重试
至多一次**）；cancel 无响应 → 350ms 重试一次 → STOP；GOT_IP 90s 超时 →
采集实态、重试至多一次；cleanup 后 120s 未恢复 → STOP；未列明异常一律
STOP + 恢复 + 归档，不即兴处置。
