# BLE 常态化运行与异常韧性验收（T5 方案冻结版）

日期：2026-10-24
前置：T4 单端全绿（PASS 14 / FAIL 0 / SKIP 1，#15 双端证据延后）。

## 0. 定位与边界

T4 已证明 BLE 通信、长响应、双通道和基本网络操作在单次流程下正常。T5 回答一个新问题：

> 设备在反复配网、BLE 断连、网络消失和操作超时之后，是否仍能持续保持可管理、状态一致、资源稳定。

硬边界：

- 以固件稳定性为主，小程序只是测试工具；
- 不引入新的 BLE 协议版本；
- 配对加密（SM_LVL=0 → 配对）独立为 T6 安全专项，不是 T5 签收前置；
- **第一阶段不动固件**：先做 M1 取证与测试器，只有证据证明存在实际缺陷才改固件。

## 1. M1：测试基线与终态槽回收验证（先行）

核实当前固件（含 2026-10-24 槽语义改进）的回收规则，把行为做成有日志、有结果的测试。

固件现行语义（以实现为准）：

- 终态保留统一 600s（2026-10-25 修订：淘汰机制上线后分级失去动机，回退分级以保住检查表第 15 项 ≥5min 幂等保证）；
- 槽满（4 条终态记录都在保留期）且无活动 operation 时，覆盖**最老的终态记录**受理新请求；
- 被覆盖的 operation 再查 `operation.get` 返回 `not_found`；
- 串口日志出现 `reclaim oldest terminal <id> state=<state> age=<ms>`。

测试步骤（小程序 T5 页「M1 · 终态槽回收取证」可自动执行）：

1. 连续制造 4 个失败操作（不存在 SSID），直到终态记录达到槽容量；
2. 发起第 5 次 `network.tryconnect`；
3. 确认新操作被受理（`accepted`），串口出现 reclaim 日志；
4. 查询 O1（最老）：应为 `not_found`（已回收）；O2–O4 在保留期内仍可查；
5. 保留期到期行为：终态统一 600s 后观察自动回收（旧 120s 分级用例作废）。

通过标准：不因历史终态记录耗尽而无法配网；回收对象与日志符合设计；新操作状态不被旧操作污染。

注意：`busy` 代表已有活动操作，与终态槽回收是两回事，必须分开测试；取证报告已内置该区分（第 5 个返回 `busy` 时 verdict 提示结合活动操作判断）。

## 2. M2：循环配网与资源 soak（核心）

### 2.1 场景分组（首轮 50 轮的分配，非实测结果）

| 场景 | 代号 | 轮数 | 重点观察 |
| --- | --- | --- | --- |
| 成功试连、查询状态、取消或按设计回滚 | A tryconnect-cancel | 15 | 操作状态一致、正式配置不被误覆盖、cancel 幂等 |
| 错误口令 / 不存在 SSID | B designed-failure | 15 | 错误分类、超时清理、终态记录回收 |
| 成功试连后 apply | C apply | 10 | 正式配置持久化、STA 和 MQTT 恢复、profile 不累积 |
| BLE 断连后重新登录、继续查询 | D relink | 10 | token 失效、操作状态可恢复查询 |

10 轮冒烟按 3/3/2/2 缩放；100 轮扩展同比例。`failure` 集只排 B，`connect` 集只排 D。

每轮保存 `operation_id` 与原始请求/响应 id；错误码（wrong_password / ap_not_found / timeout / busy / no_slot / operation_state / expired / disconnected）分别记录，不统一归类为"配网失败"。

### 2.2 资源采样

每轮记录：操作起止与终态时间、`operation_id`、状态迁移序列、`sta_has_ip`/`sta_ip`/`mqtt_connected`/`connected_ssid`、profile 数量、错误码；B 轮另核对正式 SSID 未被覆盖。

堆曲线边界（第一阶段不动固件）：协议层暂无 heap 字段（`device.info` 只有版本/安全位），free heap / largest free block 以**串口 diag 日志**为准，与测试报告按时间戳对时。协议层暴露 heap（如 `device.status` 加法字段）列为 T5 第二阶段候选，由 M2 证据决定是否立项。

### 2.3 首轮签收标准

- 50 轮均有明确的成功/失败/取消/超时结果，无无解释的悬挂操作；
- `no_slot` = 0；出现 `busy` 必须能对应到真实活动操作；
- 正式配置与 profile 数量符合预期，无逐轮累积残留；
- 堆无持续下降趋势，largest free block 无持续恶化（趋势判据，先固定采样条件与基线，不单以"下降 10%"作为通过线）;
- MQTT 断开必须有可解释原因与恢复结果，不只看结束态；
- 无 NVS 写入失败、任务栈异常、断言或重启。

### 2.4 测试器实现规格（已实现）

- `utils/t5runner.js`：计划生成（3:3:2:2）、四类场景、逐轮证据、汇总与报告渲染、M1 槽取证；
- `pages/t5/`：独立「T5 韧性测试」页（不混入配网页），配置=轮数 10/50/100 × 场景集（混合/失败/连接）× 节奏（串行/紧凑），目标 SSID/口令预填当前正式网络与本地口令记忆；
- 四条实现原则：
  1. 每轮保留原始请求/响应/请求 id/`operation_id`，不只存 PASS/FAIL；
  2. 可中止：中止后停发新操作，并按协议 cancel 当前活动操作；
  3. 断连不无限重试（补链恰好一次，失败即停整轮 run），不自动复用旧 token（补链内重新登录）；
  4. 报告导出原始证据 + 汇总统计，口令/token 全部脱敏（`***`），便于与串口日志对时。

## 3. M3：异常注入与恢复（人工/半自动）

| 注入场景 | 必须验证的结果 |
| --- | --- |
| 配网操作进行中关闭小程序或断开 BLE | 重连后重新登录；旧 token 被拒；仍能查询操作状态 |
| 配网过程中关闭目标 AP | 操作按预期失败或超时，错误原因可查；恢复 AP 后能重新配网 |
| 输入错误口令 | 不覆盖正式配置；错误不被误报成 busy/no_slot |
| `accepted` 后不再轮询 | 按设计超时（约 20s accepted TTL）并清理资源，之后能发起新操作 |
| `got_ip` 后不执行 apply | trial 按既定有效期（300s）处理；正式配置不被意外提交 |
| 取消操作后重复取消 | 幂等语义（cancelled / operation_state），不重复清理或破坏新操作 |
| 设备重启 | BLE 可重连、重新登录；配置与操作状态符合固件持久化设计 |

计时口径：分别签收三类恢复，不机械套用 30 秒——

- 可管理态恢复（BLE 可连、重新登录、查询状态）；
- 网络恢复（STA 重新拿到 IP）；
- 业务恢复（MQTT 重连）。

**设计边界纠正**：原讨论的「committing 阶段断电重启」按**观察性测试**执行——记录重启后的配置/profile/网络状态，检查是否不一致。设计冻结采用的是旧快照恢复，并未承诺断电原子提交；若要求断电原子性，需另立设计任务（持久化顺序、恢复标记、掉电恢复机制）后再设为硬性验收项。

### 3.1 M3 实测结果（2026-10-25，主机侧自动化）

工具：`tools/ble_p0/t5_m3_matrix.py`；结果：`tools/ble_p0/results/t5_m3_20261025_120003.json`（矩阵主跑）+ `t5_m3_20261025_120821.json`（M3-7 复跑 5/5）。

| 场景 | 结果 | 证据/备注 |
| --- | --- | --- |
| M3-1 候选中 BLE 掉线 | **PASS** | 旧 token 复用 → `unauthorized`；重连重登成功；旧 op 可查且为 `cancelled`（设备按设计在 BLE 断连时取消活动候选，串口 `async network operation cancelled on BLE disconnect`） |
| M3-2 目标 AP 消失 | **子集 PASS；中途关 AP 待人工** | 自动化子集：不存在 SSID → `failed/ap_not_found`，原因可查。真实的"连接中途 AP 消失"需可控 AP（如手机热点开关），留 v2 测试器/人工执行，取证 `operation.get` + `last_disconnect` |
| M3-3 错误口令 | **PASS** | 干净态 `failed/wrong_password`（~13s，事件驱动）；正式配置与 profile 数量逐字段不变；未被误报为 busy/no_slot |
| M3-4 accepted 后不轮询 | **PASS** | 25s 静默后查询：op 已自行终态（failed/wrong_password）；随后新 tryconnect 正常受理。附注：字面 `expired` 状态在现有 AP 下不可达——所有候选 <20s 由事件终止（P2-4 两层预算结论），TTL 到期路径无触发条件 |
| M3-5 got_ip 后不 apply | **实质 PASS** | 迟到 apply 被拒（`operation_state`）；正式配置未提交；trial 已清（idle）。op 本体在 got_ip 后 ~36s 因**宿主 BLE 掉线**（reason 0x222）被按设计取消为 `cancelled`，未活到 300s TTL——`expired` 未观测到；语义确认：BLE 侧候选随会话存亡，链路稳定时才会走 300s 到期 |
| M3-6 取消/重复取消 | **PASS** | connecting 中 cancel → `cancelled`；重复 cancel 幂等返回 `cancelled`；未知 ID → `not_found` |
| M3-7 设备重启（观察性） | **PASS（复跑 5/5）** | 首跑注入失败：esptool rc=0 但复位未生效（串口 cat 并发占口），已定位为脚本环境问题；净跑：`Hard resetting via RTS pin` 确认硬复位，**三分计时：可管理 5.4s(广播)+2.6s(登录)，网络+业务 ≤15.45s（首询即真，与开机基线 IP≈6.5s/MQTT≈11s 一致）**；重启后配置逐字段一致；operation 表清空（RAM 态即重启证据；该次串口因端口被 esptool 重置而丢流，以 JSON 证据为准） |

环境注记：当日宿主蓝牙极不稳定（18 分钟 12 次重连，0x222/0x213 混合），M3-5 的提前取消与 M3-7 首跑的注入失败均与此环境相关；固件侧行为全部符合设计。M3 矩阵结论：**7 场景中 6 PASS + 1 子集 PASS（剩余部分待可控 AP）**；未发现新的固件缺陷（P1-10 扰动窗口已在 t5c 排查中单独立项，本轮按 SETTLE 间隔规避）。
