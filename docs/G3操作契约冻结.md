# G3 操作契约冻结（operation_id / 查询 / 通知）

> 状态：契约冻结，**尚未实现**
> 日期：2026-10-21
> 前置：G2 同步网络事务已通过；本契约只定义 G3，不改变 G2 的 v0 兼容行为

## 1. 目标与边界

G3 把耗时操作从“命令处理任务内同步阻塞”改为“受理 + 后台 worker + 可查询状态”：

```text
请求 -> 校验/权限/幂等 -> 创建 operation -> accepted
                                      |
                             worker 执行（单一活动操作）
                                      |
              operation.event（尽力通知） + operation.get（权威查询）
                                      |
                          success / failed / cancelled / expired
```

硬边界：

- BLE CMD 任务、HTTP handler 不得等待 Wi-Fi 连接/提交；
- 通知不是状态来源，丢通知后必须能 `operation.get` 补查；
- 同一份操作记录不保存密码、MQTT token、Web 口令；
- 操作表、事件队列、通知长度、终态保留数量都有固定上限；
- G3 不包含 OTA 操作，不改变 Web/LittleFS/OTA；
- v0 同步 `network.tryconnect/apply/cancel` 保留到 G3 实机验收通过，不能在同一提交里删除。

## 2. operation_id 与生命周期

- 格式：`op-` + 16 位大写十六进制，长度 19，例如 `op-5A1C9E7304B2F681`；
- 生成：`esp_random()` 生成 64 位，碰撞时重试；不允许使用递增序号；
- 作用域：设备本次启动（RAM）；重启后全部丢失；
- 一个 operation 只对应一个网络候选/提交事务；
- `operation_id` 不是鉴权凭据：`operation.get/apply/cancel` 仍需 BLE login token
  或 HTTP 会话；但 ID 必须不可预测。

### 2.1 状态枚举

| 状态 | 含义 | 可取消 |
| --- | --- | --- |
| `accepted` | 已受理，worker 尚未开始 | 是 |
| `connecting` | 正在试连候选并等待 DHCP | 是 |
| `got_ip` | 候选已获得 IP，等待 apply/cancel/过期 | 是 |
| `committing` | 正在保存配置/profile 并重启网络 | 否 |
| `success` | 提交完成，正式配置已生效 | 终态 |
| `failed` | 试连/提交失败，旧配置已恢复（或明确记录回滚失败） | 终态 |
| `cancelled` | 在可取消状态取消，旧配置保持 | 终态 |
| `expired` | accepted/connecting/got_ip 超过 TTL | 终态 |

合法迁移：

```text
accepted -> connecting -> got_ip -> committing -> success
    |           |           |           |
    |           |           |           +-> failed
    |           |           +-> cancelled/expired
    |           +-> failed/cancelled/expired
    +-> cancelled/failed/expired
```

- `committing` 不可取消；`network.cancel` 返回当前状态，不假装取消。
- 终态不可再次迁移；重复 apply/cancel 只返回当前终态。
- `got_ip` TTL 300 秒（沿用 G2 trial TTL）；`accepted/connecting` 总时限 20 秒；
  终态保留 600 秒。

### 2.2 TTL 到期与槽位耗尽的确定顺序

`got_ip` 到期时不能只改 operation 状态，否则会出现“operation 已 expired、底层 trial
仍可 apply”。固定顺序：

```text
worker 发现 deadline 到期
  -> 标记 slot 为 expiring（拒绝并发 cancel/新事务）
  -> 调用 cleanup 回调（清 trial/恢复旧网络）
     -> 成功: 状态 expired，error=timeout
     -> 失败: 状态 failed，error=cleanup_failed
  -> 清除 expiring，允许槽位在 retention 后回收
```

- cleanup 失败时不得显示 expired/cancelled；必须保留可查询的 failed 状态；
- `committing` 不参与 TTL 到期，只有 success/failed 两个出口；
- 4 个 slot 全被未过 retention 的终态占用时，新请求返回 `no_slot`（上层映射为
  `busy`），**不得覆盖仍可查询的 operation**；
- 活动 operation（accepted/connecting/got_ip/committing）存在时，新网络请求返回
  `busy`，不排队。

### 2.3 实现状态（2026-10-21，第一轮）

已实现但尚未接入 v1/BLE 通知：

- `operation_state.c/h`：纯状态机 + 主机侧单元测试 `tools/operation_state_test.c`；
- `operation.c/h`：4 槽静态表、单 worker、并发限制、TTL/retention、cleanup 回调、
  槽位耗尽保护；
- `APP_OPERATION_SELFTEST` 测试构建：状态机/并发/槽位/TTL 10 项断言通过；
- v0 同步 `network.tryconnect/apply/cancel` 未改动。

资源验收结果（`APP_OPERATION_LIFECYCLE_TEST`，2026-10-21）：

```text
第一轮（无 defer）：
baseline             free=13492 largest=10240 PASS
worker after_start   free= 9276 largest= 6144 PASS（零余量）
worker + MQTT 重连   free= 7380 largest= 4608 FAIL

加入 MQTT restart defer 后：
baseline             free=13460 largest= 9216 PASS
worker after_start   free= 9208 largest= 5376 FAIL（<6144）
operation 活动期间请求 restart：deferred=1 pending=1，MQTT 不重建
operation 期间最低     free= 9208 largest= 5376 FAIL
cancel 释放 defer 后重启最低 free= 6504 largest= 4864 FAIL
worker stack high-water = 3072–3160B / 4096B（剩余约 1KB）
```

结论：

- defer/合并机制有效：operation 活动期间 restart 请求被合并，没有重建峰值；
- 但 **worker + MQTT 稳态本身 largest 只有 5376B**，已低于 6144B；defer 只能移走
  重连峰值，不能消除基线不足；
- 终态释放 defer 后的延迟 restart 仍会跌破门槛（6504/4864），因此“推迟”不是完整解；
- worker 栈高水位 3072–3160B，不能缩到 3072B；
- worker 采用首次 operation 惰性创建，创建失败时 `app_operation_start` 返回错误并释放槽位；
- worker 创建后常驻，未实现空闲回收；若后续回收，必须同时解决终态 TTL tick。
- 未接入 v1 入口/BLE 通知；v0 同步路径不变。

下一轮必须先解决 worker + MQTT 基线本身的内存归属（不是继续推迟或缩栈），
并在稳定 MQTT 窗口复测 `free≥8KB/largest≥6KB`；否则不接 `network.tryconnect`
异步入口。

## 3. 资源硬上限

| 资源 | 上限 | 依据 |
| --- | --- | --- |
| operation 表 | 4 槽 | 1 个活动 + 最多 3 个终态 |
| 活动网络操作 | 1 个 | 不允许排队；新请求返回 `busy` |
| 事件队列 | 8 条 | 通知尽力而为，状态仍以表为准 |
| 单条通知 | 256 B | 不携带 SSID/密码/token |
| terminal 保留 | 600 s / 3 条 | 超出淘汰最旧的终态 |
| worker 栈 | 4096 B | 只跑 Wi-Fi 试连/提交，不解析大 JSON |
| operation 记录 | ≤ 160 B/槽 | 固定字段，无指针、无 cJSON |

实现要求：

- operation 表、事件队列使用静态存储，不依赖运行时 malloc；
- 通知 JSON 在 256B 栈缓冲内组装，失败只丢通知，不改状态；
- 事件队列满时丢弃最旧事件并计数，`operation.get` 仍返回最终状态；
- G3 上线前记录基线：当前 BLE+MQTT 稳态 free≈13.8KB/largest≈9.2KB；
  加入 operation 机制后 free 不得低于 8KB、largest 不得低于 6KB，且 `mqtt_shed`
  不得因 G3 增加。

## 4. 命令契约（v1.0）

以下均为 v1.0 外壳；v0 同步命令保持不变。

### 4.1 发起试连

```json
{"id":"req-1","version":"1.0","cmd":"network.tryconnect",
 "args":{"ssid":"Office-WiFi","password":"***","idempotency_key":"try-20261021-01"},
 "token":"<BLE_TOKEN>"}
```

成功：

```json
{"id":"req-1","ok":true,"data":{"operation_id":"op-...","state":"accepted"}}
```

- `accepted` 必须在 100ms 内返回；真正的连接在 worker 中执行；
- 已有活动操作且 key 不同：`busy`；
- 相同 `idempotency_key`：返回已有 operation 的当前状态，不重复启动；
- 权限：BLE/HTTP 登录后允许；MQTT 禁止。

### 4.2 查询

```json
{"id":"req-2","version":"1.0","cmd":"operation.get",
 "args":{"operation_id":"op-..."},"token":"<BLE_TOKEN>"}
```

返回当前状态和结果摘要；不返回密码/token。`got_ip` 可含 SSID、IP；
`failed` 含 `error`；`committing` 不含未完成的提交细节。

### 4.3 应用

```json
{"id":"req-3","version":"1.0","cmd":"network.apply",
 "args":{"operation_id":"op-...","idempotency_key":"apply-20261021-01"},
 "token":"<BLE_TOKEN>"}
```

- 只接受 `got_ip` 且未过期的 operation；
- 相同 key 重复 apply：返回当前状态，不重复写 NVS；
- `committing` 后不可取消；失败必须走 G2 的配置/profile 快照恢复；
- 回滚失败时状态为 `failed`，`error="rollback_failed"`，不得报 success。

### 4.4 取消

```json
{"id":"req-4","version":"1.0","cmd":"network.cancel",
 "args":{"operation_id":"op-..."},"token":"<BLE_TOKEN>"}
```

- `accepted/connecting/got_ip`：设置取消标志，worker 在 2 秒内停止并恢复旧配置，
  终态 `cancelled`；
- `committing/success/failed`：返回当前状态和 `cancel_accepted=false`，不假装取消；
- 重复 cancel：返回同一终态，无副作用；
- 取消后再次 tryconnect：必须创建新 operation_id，不复用旧候选。

### 4.5 通知

订阅 CMD TX 后，状态变化发送：

```json
{"version":"1.0","event":"operation","operation_id":"op-...","state":"got_ip"}
```

- 仅发送 `operation_id/state/error`，不发送 SSID、IP、口令、token；
- 通知是 best-effort：队列满/未订阅/MTU 不足时允许丢失；
- 客户端必须以 `operation.get` 为准，不能只依赖通知；
- 终态至少尝试发送一次；发送失败计数进 diag，不重试阻塞 worker。

## 5. 幂等规则

- `idempotency_key` 可选，长度 8–64，ASCII；
- key 作用域：本次启动 + 同 owner 传输（BLE/HTTP）；
- 相同 key 的 try/apply/cancel：
  - 找到同一 operation：返回当前状态，不执行副作用；
  - 未找到且旧终态已淘汰：允许创建新 operation，但客户端应使用新 key；
- 不带 key 的重复请求视为新请求；网络事务建议客户端总是带 key；
- key 不写入 NVS，不跨重启保留。

## 6. 断连与重启语义

### BLE 断开

- BLE owner 的 `accepted/connecting/got_ip` operation：取消并恢复旧配置；
- `committing`：继续完成，终态保留，客户端重连后 `operation.get`；
- 非 BLE owner（HTTP）的 operation 不受 BLE 断开影响；
- login token 失效；重连后必须重新 login 才能查询/apply/cancel。

### 重启

- 所有 operation 只在 RAM，重启即丢失；
- 客户端在设备重启后 `operation.get` 返回 `not_found`；
- 不做“重启后恢复未完成事务”的承诺；正式配置以 NVS 为准；
- 若重启发生在 `committing`，按 NVS 实际提交结果处理，不能报 success。

## 7. 错误码

沿用协议错误对象 `{code,message}`，G3 新增/明确：

| code | 场景 |
| --- | --- |
| `busy` | 已有活动网络操作 |
| `not_found` | operation 不存在或已过保留期 |
| `operation_state` | apply/cancel 与当前状态不匹配 |
| `idempotency_conflict` | 同 key 但请求语义不同 |
| `cancel_not_allowed` | committing/success/failed 上尝试取消 |
| `expired` | 候选超过 TTL |
| `rollback_failed` | 提交失败且快照恢复失败 |

## 8. 验收矩阵

| 场景 | 验收标准 |
| --- | --- |
| 受理延迟 | tryconnect 在 100ms 内返回 accepted，BLE CMD 任务可继续处理 status |
| 正常事务 | accepted→connecting→got_ip→committing→success；通知与查询一致 |
| 通知丢失 | 丢弃/不订阅通知后，operation.get 仍能拿到最终状态 |
| 重复 tryconnect | 同 idempotency_key 只产生一个 operation；不同 key 返回 busy |
| 重复 apply/cancel | 返回当前状态，无重复 NVS 写入/无副作用 |
| connecting 取消 | 2s 内进入 cancelled，旧网络恢复，CLI 可继续操作 |
| committing 取消 | 返回 cancel_not_allowed，不中断提交 |
| BLE 断连 | 非 committing operation 取消；committing 完成；重连后查询一致 |
| 设备重启 | operation.get=not_found；正式配置不因未完成操作改变 |
| 资源 | 4 槽、8 事件队列、256B 通知上限生效；free≥8KB/largest≥6KB；shed 不增加 |
| 回滚失败 | 状态 failed + rollback_failed，不报 success |

## 9. 实施顺序（G3）

1. 实现静态 operation 表、状态机、幂等键、终态淘汰；
2. 实现单 worker 与 `network.tryconnect` v1 异步受理；
3. 实现 `operation.get`、`network.apply/cancel` 状态校验；
4. 接入 BLE 通知与失败计数；
5. 替换 v0 同步路径前，保留 v0 兼容并做 A/B 回归；
6. 按第 8 节矩阵做真机验收，记录 heap/largest/通知丢弃。

## 10. 不做的事

- 不为 operation 机制引入动态链表/大 JSON 缓冲；
- 不在通知里携带 Wi-Fi 凭据或 MQTT token；
- 不承诺通知必达；
- 不承诺重启后恢复未完成操作；
- 不在 G3 顺手改 Web/LittleFS/OTA；
- 不在 G3 解决 G4 的 auto_connect 运行态隔离；G4 仍需单独验收。
