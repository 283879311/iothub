# 2026-10-19 页面初始分块 A/B（512B vs 256B）

## 方法

- DUT：B `192.168.1.42`，固件包含：
  - 每页堆/发送统计（1.3-89）；
  - `storage selftest` 在页面发送或内存非 normal 时跳过；
  - `HTTP_HTML_INITIAL_CHUNK_BYTES` 作为唯一实验变量。
- 负载：同一脚本，页面 `/config` 每 30s、`led.toggle` 每 5s、status 每 2s，持续 30 分钟。
- 页面仍是 gzip 直出：LittleFS `config.html.gz` + 常驻 FILE* + 静态 `chunk[2048]`；
  不存在整页解压或整页堆复制。
- 统计来自串口 `html page:` 行，包含每页 start/min/end、全局 `min8_all`、
  `send()` 的 EAGAIN/ENOBUFS/ENOMEM/timeout、outbox 和降档次数。

## 结果

| 指标 | 512B | 256B |
| --- | ---: | ---: |
| 测试窗口页面 | 57（另有 3 页预验证） | 57（另有 1 页预验证） |
| HTTP 200 | 全部 | 全部 |
| 503 / 超时 / critical | 0 / 0 / 0 | 0 / 0 / 0 |
| 最终分块分布 | 49 页 512，10 页降 256 | 58 页 256 |
| 有 EAGAIN 的页 / 重试次数 | 7 / 10 | 10 / 15 |
| ENOBUFS / ENOMEM / timeout | 0 | 0 |
| 页内最低 free / largest | 1,664 / 400 | 2,632 / 960 |
| `min_free<4096` 页 | 35/60 | 32/58 |
| `min_largest<2048` 页 | 16/60 | 32/58 |
| `min_largest<1024` 页 | 6/60 | 1/58 |
| 全局 `min8_all` | 28B | 260B |

> 两项全局最低值不一定发生在页面发送的 start/end 采样点；512 那组的
> `min8_all` 下降没有落在任何一页的 start→end 变化里，说明页面之外的
> 命令/MQTT/其他任务也可能贡献低点。

## 1024B 对照的限制

- 当前 B 启动后 `largest≈6.9KB`，现有预检在 `largest<8KB` 时把初始 1024
  自动降为 512；因此本次 1024 组实际仍是 512，不能作为有效 1024 数据。
- 历史 1024 数据（`largest≈10.7KB` 时）：4 小时第一段 137 页出现 136 次降档，
  并有 2 次 critical；包括 512 未出现的堆临界和 MQTT 写超时。
- 结论：1024 在低 largest 下本来就会被预检降档；只有 largest≥8KB 才会真正
  使用 1024，而这正是历史 critical 出现的区间。

## 判断

1. **256B 不是更好的默认值**：它把 `largest<1024` 页从 6 降到 1，但
   `largest<2048` 页从 16 增到 32，EAGAIN 页从 7 增到 10、重试从 10 增到 15；
   更小的块增加了调用/pbuf 次数，没有消除 TX 压力。
2. **512B 是更好的中间值**：EAGAIN 和降档次数更少，页内最低 free 也更接近
   原来的 1024 区间；但它仍有 16/60 页 `largest<2048`、6/60 页 `<1024`，
   **不能单独作为修复**。
3. **根因不在“整页缓冲”或“初始块大小”本身**：页面数据是静态缓冲流式发送，
   峰值来自 `send()` 触发 lwIP/Wi-Fi TX 池；下一步必须做有界协调/预留，
   而不是继续只调 chunk。

## 协调实验（512B + 有界 MQTT 让路）

在 512B 基线上增加了：

- 页面发送期间/`mqtt_outbox` > 2048B 时，遥测任务延后低优先级 state/attributes；
- 保留 `MQTT_IO_EVENT`，页面结束后补发最新值；
- RPC 响应仍直接 publish，不经过该闸门。

30 分钟同频页面/命令测试结果：

| 项 | 结果 |
| --- | ---: |
| 页面 / HTTP 200 | 57 / 全部 |
| 503 / timeout / 计划外 MQTT 断链 | 0 / 0 / 0 |
| `low-prio publish deferred` 触发 | **0 次** |
| 页内最低 free / largest | 2,312 / 960 |
| `largest<2048` 页 | 29/58 |
| `largest<1024` 页 | 26/58 |
| send EAGAIN 页 / 重试 | 13 / 14 |
| 全局 `min8_all` | 772B |

这组测试里 MQTT 让路闸门**没有触发**，页面仍把 `largest` 压到 960B，说明当前
“页面 30s + 命令 5s”负载下压力主要来自页面发送本身，而不是 MQTT 并发。
另外该组启动时 `largest≈6.9KB`，低于 512 基线组的 9.7KB，两组不能只看绝对值
比较；但“让路未触发”这一事实不受影响。

## 建议

- 采用 **初始 512B + 发送中最低 256B** 作为当前中间基线，不切 256B 默认；
  256B 的 EAGAIN 更多，且没有把 `largest` 抬到安全区。
- **不要把 MQTT 协调当成本轮根因修复**：它在页面/命令低并发下不触发；保留代码
  可用于真实 MQTT 并发，但下一步必须先做页面发送节奏/运行门槛实验：
  1. 将分块间隔从 20ms 提高到 50/100ms，观察页面耗时、页内最低 largest 和 EAGAIN；
  2. 在每块发送前若 `largest<2048`，做有界等待（例如 20–50ms）再发，而不是继续降档硬发；
  3. 只有节奏实验仍不足时，才做 Wi-Fi 动态 TX/TCP snd 缓冲 A/B；
  4. 最后再跑 30 分钟页面专项和 4 小时全开回归；当前不削 BLE/MQTT 功能。
