# 2026-10-19 chunk 间隔 A/B（A0 20ms / A1 50ms / A2 100ms）

## 方法

- 固定：512B 初始分块、selftest 避让、MQTT 协调代码、诊断埋点；
- 页面 `/config` 每 30s、`led.toggle` 每 5s、status 每 2s，每组 20 分钟；
- 唯一变量：`HTTP_HTML_CHUNK_GAP_MS`（chunk 完成后的主动让出）；
- 新增 `post_page`：页面结束后 500ms 用非阻塞 esp_timer 采样，不占用 httpd 任务；
- 并发延迟另测：页面每 2s + 命令每 1s，两个独立 curl 客户端共 60s。

- A2 测试窗口 critical=0；预验证阶段出现过一次 critical，已排除在测试窗口外，但说明 100ms 不是无风险。
- 三组测试窗口 HTTP 全部 200，无 503、无超时、无计划外 MQTT 断链。

## 并发页面/命令延迟（60s，页面每 2s + 命令每 1s）

| 组 | page p50/p95/max | command p50/p95/max |
| --- | ---: | ---: |
| A0 20ms | 0.456 / 0.667 / 0.790s | 0.209 / 0.427 / 0.520s |
| A1 50ms | 0.844 / 1.540 / 1.555s | 0.221 / 0.720 / 1.348s |
| A2 100ms | 1.476 / 1.572 / 2.838s | 0.203 / 1.359 / 1.776s |

并发测试证实：页面请求占用 httpd 时，命令会排队；A0 p95 命令延迟约 0.43s，A1 约 0.72s，A2 约 1.36s。单看串行 harness 的命令 p50 会漏掉这个排队。

## 判断

1. **A0=20ms 保持为当前默认**：延迟最好，post_page 全部恢复；缺点是页内 largest 仍低。
2. **A1=50ms 不是明确更好**：EAGAIN 和 `<2048` 页减少，但 `<1024` 页从 1 增到 8，页耗时约翻倍，命令 p95 从 0.43s 增到 0.72s。不能仅凭 EAGAIN 减少就采用。
3. **A2=100ms 拒绝**：页面/命令 p95 明显恶化，且 2/38 页 500ms 后未恢复，支持“更长间隔可能延长缓冲占用”的担心。
4. **只调节奏不够**：A0 仍有 largest 832B、1,536B 中位；需要运行门槛（`largest<2048` 有界等待）或低频 lwIP/Wi-Fi buffer 证据，不能只继续调间隔。
5. **口径**：A2 启动堆不同，不能与 A0/A1 做严格排序；后续若需比较 A2，必须重刷到相近启动 largest，或重复多轮取中位数。

## 下一步

- 保持 A0=20ms，做实验 B：每块前 `largest<2048` 时等待 20–50ms、最大 100–200ms，再决定发送 256 或结束响应；
- 同时补并发命令延迟作为固定指标；
- 若 B 仍无法把 largest 抬到安全区，再做页面前后低频 lwIP/Wi-Fi buffer 采集；
- 专项达标后才跑 4 小时回归；当前不削 BLE/MQTT 功能。
