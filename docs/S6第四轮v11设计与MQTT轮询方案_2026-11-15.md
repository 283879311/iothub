## 1. 轮询改走 MQTT（附 6 条件逐条落实）

| # | 评审条件 | v11 实施 |
| --- | --- | --- |
| 1 | 独立唯一 client_id，不冒用设备 ID | `iothub-harness-<uuid4前8位>`，启动时打印并落盘；与设备 `iothub-B0A73228C8E4` 无交集 |
| 2 | 每请求唯一 ID，严格按 ID 匹配 | `hp-<seq>-<rand4>`；**仅接受 body.id 完全相同**的响应；topic 尾段 rid 亦须匹配，防止串台 |
| 3 | 串行或明确并发关联 | `asyncio.Lock()` 串行化，**同一时刻只有一个在飞请求**；超时即丢弃该 ID（后续同 ID 响应被忽略） |
| 4 | EMQX ACL 必须实测（匿名回环≠设备主题权限） | 预检：① SUBSCRIBE 响应主题，SUBACK 授权码非 0x80；② 向 `v1/devices/me/rpc/request/preflight-<rand>` 发 QoS1，确认 PUBACK 且 rc=0。**预检在改指向之前**，此时设备仍在 TB，不会被误触发。任一失败 → STOP，不进入测试 |
| 5 | operation.get 只查本轮自己创建的 op | `_op_registry` 集合记录本轮 op-ID；查询前校验 ∈ 集合，否则拒发 |
| 6 | 通道失联记 `POLL_TRANSPORT_FAILED`，不得解释为 operation 失败/超时 | 传输层与设备语义分离：`Rpc.call()` 返回 `("OK", data)` / `("TRANSPORT", 原因)`。收到 TRANSPORT → `_results["op_e"]="INCONCLUSIVE_TRANSPORT"` + STOP，**绝不重发 tryconnect** |

**保留 BLE**：改指向、恢复写回、终态复核仍走 BLE（MQTT 源禁写 mqtt 域键——
policy 已核实）；BLE 是 MQTT 恢复失败时的独立手段。**不因 MQTT 轮询而删除任何
BLE 恢复通道。**

## 2. 错误分类（v11 新增，互不混淆）

| 类别 | 判据 | 记录 |
| --- | --- | --- |
| `POLL_TRANSPORT_FAILED` | MQTT 超时/无响应/EMQX 断连/未授权 | 结果状态 `INCONCLUSIVE_TRANSPORT`，STOP，不重试、不改判为设备失败 |
| 设备语义终态 | operation.get 返回 failed/cancelled/expired | 按原规则：failed/cancelled → 立即 STOP（**不重试**）；expired 且未见 GOT_IP → 记 `ACCEPTED_TTL_EXPIRED`（不重试，见 §3） |
| `connect_failed` | 设备 returned failed + connect_failed | **维持立即 STOP**，不自动重试（评审裁决：该码可来自断开超时/配置失败/connect 调用失败/等待窗结束，非单一瞬态；细分原因后再议） |
| cleanup 未达成 | 窗口内未连续两次满足 STA+trial | `CLEANUP_UNCONFIRMED`，STOP，不进 op-V |
| 恢复未确证 | 见 §4 | `RECOVERY_UNCONFIRMED` / `RECOVERY_FAILED` / `RECOVERY_CONFIRMED` |

## 3. 重试规则（收紧后）

- **零自动重试**：`connect_failed`、`cancelled`、轮询无终态、传输失败一律 STOP。
- 唯一例外保留原 v11 口径的 `ACCEPTED_TTL_EXPIRED` 分类重试——**本轮默认关闭**
  （评审未要求恢复该例外；如需开启须单独批准）。脚本以 `--allow-accepted-ttl-retry`
  显式开关，缺省关闭。

## 4. 恢复分阶段（评审要求，替代"config.set ok 就算恢复"）

| 阶段 | 动作 | 失败处理 |
| --- | --- | --- |
| R1 | BLE 会话获取（原会话或 `ensure_session()` 重连 ≤3 次） | 无法建立 → `RECOVERY_UNCONFIRMED`（BLE 不可达） |
| R2 | `config.set` 写回 S0 快照值；要求 `ok:true` 且 `changed` 含目标键 | 写回被拒 → `RECOVERY_FAILED` |
| R3 | **独立读取**：`config.get` 回读 host/port == 快照 | 不符 → `RECOVERY_UNCONFIRMED` |
| R4 | **broker 侧确认**：EMQX 上设备消息静默 ≥30s（已离开 EMQX） | 仍有消息 → `RECOVERY_UNCONFIRMED` |
| R5 | 设备侧 `network.status.mqtt_connected == true`（**与 R3 间隔 ≥5s 再读一次**） | 未连 → `RECOVERY_UNCONFIRMED` |

**只有 R2–R5 全部通过才记 `RECOVERY_CONFIRMED`**；任何一项无法确认一律
`RECOVERY_UNCONFIRMED`（区别于写入被拒的 `RECOVERY_FAILED`）。
TB 侧无管理接口，无法由 harness 直接观测——此限制在证据中明示，不伪装。

## 11. v11.1 修订（对应首轮静态审查的 P0/P1）

| 编号 | 审查意见 | v11.1 实施 |
| --- | --- | --- |
| **P0-1** | `connect(); subscribe(); loop_start()` 时序不可靠，subscribe 可能 NO_CONN 且未检查 | Rpc/Presence **改为连接状态机**：`on_connect` 收到 CONNACK 成功后才 `subscribe`，记录 `subscribe` 返回码；`wait_ready()` 要求 CONNACK 成功 + subscribe rc==0 + SUBACK 非空且无 128；**未就绪不得进入任何使用路径**（run_round 在 ACL 预检/改指向之前先 `wait_ready`，失败即 STOP） |

### 11.2 仍未解决的限制（如实保留）

1. **ACL 预检 ≠ 设备身份权限**：只证明 harness 客户端能订阅响应主题、发布请求并获得 PUBACK。
2. **预检的 `device.info` 是真实 MQTT 请求**：`v1/devices/me/rpc/request/+` 为共享
   主题结构；若 EMQX 上还有其他订阅同主题的设备，它们也会收到。执行前需现场
   确认该 broker 无其他设备使用该主题（已列入执行前置）。
3. **R4 不能证明 TB 侧已收到**：只证明设备在有效监听窗口内未再向 EMQX 发消息；
   TB 无管理接口，此限制保留。
4. **TCP 预检是 PC 侧**：设备出网条件的真凭实据是它在 EMQX 上出现（在场检测）。
