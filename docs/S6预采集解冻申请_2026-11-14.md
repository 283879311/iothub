## 1. 双 TTL 时间线（毫秒精度修正稿）

```
trial deadline     = esp_timer_get_time()/1000 + 300000   （store_trial 时刻起）
operation deadline = app_operation_now_ms()   + 300000   （set_state(GOT_IP) 时刻起）
T0 = store_trial；T1 = set_state(GOT_IP)；Δ = T1 − T0 的实际毫秒间隔
     （连接与 netcheck 在 try_connect_ip() 内、T0 之前完成，不计入 Δ）
两 deadline 关系：trial 不晚于 operation；Δ>0ms ⇒ trial 严格先到期；
                  Δ=0ms ⇒ 同时到期（不写"恒先于"）
```

**T0/T1 取证口径（诚实声明）**：wire 无 created_ms/expires_ms，GOT_IP 转换
时刻无设备日志——**不伪称取得设备内部精确 T0/T1**。采用主机 monotonic 时钟
**区间取证**：trial 侧 = 最后一次 `trial=idle` 与首次 `trial=got_ip` 请求/响应
时刻及轮询间隔；operation 侧 = 最后一次 `connecting` 与首次 `got_ip` 的时刻；
Δ 以**测量区间**报告。

## 2. 分支与顺序（token 续签节点加粗）

```
S0 身份守卫（§3）→ 串口在录确认 → 前置 device.status/config.get
   （IP 基准：固化当次实测 DHCP 地址 + 设备身份 + 采集时刻）
S1 分支① BLE sync trial cancel（零 op 零 async）：
   sync tryconnect → 受理响应 → trial ready 采集
   → **not_found 负向对照**：BLE operation.get{operation_id:"op-00000000CDEF1234"}
     （预期 not_found——find 失败前置返回，不触 trial 匹配）+ 同刻 network.status
   → BLE cancel{trial_id} → cancelled 采集 → trial idle
S2 分支② BLE sync 04c 段 A（独立）：
   sync tryconnect → 原始受理响应帧+键序 → trial ready 采集
   → BLE cancel → trial idle
S3 分支④ BLE sync 专用 TTL（方案 1，无 operation）：
   **auth.login 续签①** → sync tryconnect → trial ready 采集（T0' 主机时钟）
   → 不 cancel、保持 BLE 会话（断连清 trial——作废重试至多一次）
   → T0'+270s 起每 15s 预到期采样（应仍 ready）
   → T0'+300s 起每 15s 查询至 idle（lazy clear 成对证据）
S4 分支⑤ MQTT async expired（唯一改指向段）：
   **auth.login 续签②** → 改指向（§5）→ 接入 mini_broker ≤75s
   → async tryconnect(CMCC-502+口令) → GOT_IP（主机时钟区间记录 trial/operation
     两转换，报告 Δ 区间）
   → B 观测：自然 expired → cleanup 确认（persistent 恢复）→ trial 终值记录
   → **job clear 验证 op**：async tryconnect(不存在 SSID __jobclear_probe__)
     → 受理响应返回**新 operation_id**（≠ expired op id）= job 已清的确证；
       该 op 走真实生命周期至 failed/ap_not_found 终态 + cleanup
   → S5d 机会性 A（归因收紧）：若轮询捕获"operation.get=GOT_IP 而 trial 已
     idle"——**一律归档为"观察到 trial idle、operation 尚未发布终态；清理原因
     未判定"**（expire 先 cleanup 后写 EXPIRED，trial 可能已被 cleanup 清除）；
     除非有独立证据证明采样发生在 cleanup 开始之前，否则不得称为"trial 自身
     TTL 捕获"
   → 恢复指向 → TB:21883 connected=true（**≤80s 轮询上限**，超限按 §6 STOP）
   → **auth.login 续签③**（若恢复时距上次续签接近 600s）
S5 trial mismatch 分支：**标"不可达/未覆盖"**——唯一可构造形态（sync trial
   的 operation_id 为空 vs 任意查询 id）不构成 04b 判定表的 mismatch 语义；
   不计入验收覆盖，原因归档
S6 结束态验收（§7）→ SHA256SUMS
```

## 6. 异常恢复规则（要点重列）

身份漂移/新 boot → STOP（改指向状态先恢复）；BLE 断连 → 重连 ≤3 次 → 失败
按 §5 声明处置（**分支④ 断连清 trial，作废重试至多一次**）；cancel 无响应 →
350ms 重试一次 → STOP；GOT_IP 90s 超时 → 采集实态、重试至多一次；cleanup 后
120s 未恢复 → STOP；**auth.login 失败 → STOP**（token 失效将中断后续全部
BLE 操作）；恢复轮询 80s 超限 → STOP；未列明异常一律 STOP + 恢复入口 +
归档上报，不即兴处置。

## 7. 结束态验收（口径不变）

正常验收 = 恢复采集前运行态（CMCC-502 / TB:21883 / trial idle / 无活动 op，
以 op-V 终态 + job clear 确证为准）；TQ2026 落地单列"已知回落路径"不判完全
恢复；禁止为满足结束态改生产 profile。

## 8. 冻结边界不变

不含：烧录、整机重启、NVS 直接写入、config.set 持久键（唯一例外=§5 且恢复）、
apply、任何绕过真实 cleanup 的人为终态、与其他验收并发。
auth.login 仅刷新会话 token，不触碰 trial/job/配置。
