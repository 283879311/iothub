## 2. S6 固件缺陷：`S6-OWNER-STUCK`（11-15）

**现象**：S6 预采集连续三轮 `connect_failed`，重试无效。

**根因（串口证据）**：Wi-Fi owner 自第一轮起永久停在 `CLEANUP`（uptime 8122661 起，3.5h 零转移、无 cleanup 终态日志、watchdog 从未启动）。代码路径：`tryconnect_release` 直接调 `step_locked(RELEASE_TRYX)`，绕过了 `step_ev` 里的 `restart_kind`/`started_ms` 记账，导致 restart 任务走 APPLY 分支，owner 永不释放。

**修复**（已代码签收，见 `S6-OWNER-STUCK固件修复_2026-11-15.md`）：

1. 交接记账统一到**持锁转移出口**（`app_wifi_cleanup_handover_account_locked()`）；
2. 唤醒失败 → `CLEANUP_FAILED` 终态（绝不伪造 `NONE`）；
3. restart 任务兜底：`owner==CLEANUP && kind!=CLEANUP` 时强制纠正；
4. FI 注入：`restart_wake_fail`（一次性、cleanup 路径限定）、`cleanup_hold`（≤40s、可被 clear/abort 中断）。

## 4. 阶段 B 门禁工具链（11-15 ~ 11-16）

目标：在**不依赖 root、不读 /proc 枚举、不误碰串口**的前提下，证明"读 MAC 的那一刻是安全的"，并用可复核证据约束回滚。

### 4.1 关键设计决定（按问题演进）

| 问题 | 结论 |
| --- | --- |
| 如何证明采集存活 | 改为**采集端持 `<log>.lock`** 的 flock 协议；门禁用 `LOCK_EX|LOCK_NB` 试探 |
| 锁按日志导致双采集争用 | 锁改为**按串口唯一**（`/run/lock/iothub_serial_<ttyUSBx>.lock`），capture 与门禁同一函数 |
| `STOPPED` 被当成"端口空闲" | 改名 `COOPERATING_CAPTURE_STOPPED`，证据恒 `port_free_proven=false`；读 MAC 需**两条独立条件**：持端口锁 + 操作者 `--attest-no-external-holder` 声明 |
| final 证据可被旧文件冒充 | `run_id` 加 uuid8；`validate_final_evidence()` 校验 run_id/port/mac/锁路径/声明/恢复字段/时间 |
| 证据目录可复用 | `prepare_fresh_evidence_dir()` 原子 `mkdir(exist_ok=False)`，两个入口共用 |
| 时间戳可被 NaN 绕过 | `is_strict_number()` 严格有限数值（拒 bool/NaN/±Inf） |
| FI 无法启动时门禁反而挡住恢复 | 新增 `--recovery-mode`：链/日志/boot 只记录不否决，仍强制锁/锚点/BIN sha/声明/证据 |
| 烧录与恢复采集竞争 | `flash_frozen.sh` 自带端口锁（采集未停 rc=6）；R2 补齐 stop→flash→start |
| 烧录失败后采集停在"已停" | `capture_guard.sh` 退出路径恢复；恢复失败 **rc=90**，证据失败 **rc=91**；执行前状态必须 RUNNING（否则 **rc=92** 且不执行） |
| 锁被非采集进程持有 | 新增 `liveness`（PID cmdline + 端口锁双证，不一致 UNKNOWN），与门禁 `state`（保守口径）分离 |

### 4.2 测试与冻结

- 离线测试：`tests/s6_gate/test_gate.py`，**141 断言**（真实 flock、fake 端口锁、fake BLE 会话；不连设备）。
- 现场只读验证：步骤 0 / 锚点 / 回滚门禁 `rc=0`（一次），复用目录 `rc=2`，预建目录 `rc=2`，采集持锁时 `flash_frozen.sh` `rc=6`。
- **冻结基线**：`d09f3553d575afad7a00da2a71d52fe0a5b38b73`（工具链不再修改）。

> 测试结果为**本机执行**记录；外部审查仅做静态 diff 审查，未独立运行。
