# 小程序（wx-ble-provision）代码评审 —— 只读，不改代码（2026-11-10）

> 触发：T4 19:03 轮 15/1/9（#11 NOT_RUN、#21 FAIL），用户要求审核客户端代码。
> 范围：与本轮故障相关的代码路径（传输层/链路恢复/验收用例/契约消费），全部对着源码
> 与设备串口证据核过。**本评审未修改任何小程序代码。**

## 0. 设备侧事实（先把归属钉死）

C8E4 串口（1.3-2ef2a38）：

| uptime | 事件 |
| --- | --- |
| 21,077,949 | central connected（手机） |
| 21,709,349 | **`idle terminate ... idle=300s subscribed=1`** → `0x216` 本地终止 → 10ms 后广播 |
| 23,546,619 起 | 多轮 connect → 客户端 `0x213` 断开 → 广播（正常节奏） |
| 23,797,059 | central connected，之后**再无任何断链事件** |
| 23,951,449（实时） | `adv=0 conn=1 rx_age=153097` —— **订阅态僵尸链路** |

结论：
1. **P2 在真机生产路径上开火了**（21,709s 那条），300s 阈值行为正确；
2. 19:03 的 #11/#21 是同一现象：手机栈在 23,797s 后没把断链送达设备，设备依规
   不广播（conn=1），客户端 26s 扫描预算内必然扫不到；
3. 设备侧无崩溃/无复位/无 panic；这是**两端恢复预算不匹配**：
   设备自救 300s ≫ 客户端扫描预算 26s。

## 1. P1 级问题（建议优先修）

### P1-1 节流计时基准错位：按「发送开始」而非「写完」

`utils/protocol.js:285-289`：

```js
async _throttle() {
  const wait = MIN_COMMAND_INTERVAL_MS - (Date.now() - this.lastDispatchAt);
  if (wait > 0) await sleep(wait);
  this.lastDispatchAt = Date.now();   // ← 发送开始时刻
}
```

实际写入在 `:359` `await this.ble.write('CMD_RX', bytes)`，长命令按 20B 分片 +
20ms 片间隔要 200-300ms 才写完。设备限流按**收到完整行**计时（200ms），所以
「长命令 → 210ms 后发短命令」这条路径必然踩限流。

证据（串口）：#23 实测 `auth.login id=21` 在上一批响应后 120-180ms 到达 →
`W ble cmd rate limited` → 350ms 重试后 id=22 才成功。表现就是"一次逻辑登录
在 wire 上出现两条 auth.login"。

修法：`lastDispatchAt` 改在 `ble.write` 返回后打戳（或新增 `lastWriteDoneAt`，
节流按它算 `+210ms`）。单行级修改，收益是消掉所有"短命令跟长命令"的限流重试。

### P1-2 `ensureLink` 拆旧链路后不复核设备侧广播

`utils/link.js:140-149`：`ble.connected` 时 `discover()` 失败 → `disconnect()`
→ **立刻进入扫描**（2 窗 ×12s + 2s 退避）。而 `disconnect()` 的 `closed` 只
代表手机本地 GATT 关闭（同文件注释与 `ble.js:390-392` 已写明"不等于外设已断"）。

这正是 #21 第 3 轮失败的路径：手机栈持链 → 设备 conn=1 不广播 → 26s 扫不到。

对比 `#11`（`acceptance.js:629`）用 `waitForAdvertising(12000)` 拿设备侧证据，
两条用例方法论不一致。

修法：
1. 拆链后先 `waitForAdvertising`（预算取契约值）；
2. 未见到广播时返回专属 code（如 `link_stale`），由调用方决定；
3. `ensureLink` 失败路径挂一键 `resetAdapter`（按钮已存在，见 P2-1）。

### P1-3 `#21` 的失败归因缺设备侧证据，误判为 FAIL

`utils/acceptance.js` `checkRelink3`：每轮断开前取了 `device.status`（`preBle`，
很好），但断开后**没有** `waitForAdvertising`，扫描失败直接 `fail(...)`。

与 #11 的口径不一致：#11 在"设备未重新广播"时记 EXPECTED（不计 FAIL），#21 记
FAIL——同一个物理现象，两个结论。

修法（方法论，不影响产品）：扫描两窗失败且 `preBle.connected=true` 时，
① 尝试一次 `resetAdapter()` 再重连；② 仍失败则记 BLOCKED/NOT_RUN 并附
`lock_stale` 判据（conn=1 + rx_age_ms>90000 + adv_retry=0），不记 FAIL。
或者保留 FAIL 但明确写"主机栈半开，非设备缺陷，已由适配器重启恢复"。

## 2. P2 级问题

### P2-1 扫描失败文案没提已有的一键按钮

`utils/link.js:186-193` 的失败文案："恢复：手机关蓝牙再开（或强制停止微信）"。
但 t3/t4/t5/stress/accept 页已有「重启蓝牙恢复广播」按钮（`accept-core.js:169-193`，
仅断开态显示）。用户看到长文案时不会知道有按钮。

修法：文案加一句"或点上方「重启蓝牙恢复广播」（等价，一键）"。

### P2-2 `waitForAdvertising` 预算硬编码 12s ×3 处

`acceptance.js:629 / :794 / :1860`。建议进契约（如
`timing.json#derived_client_budgets.client_adv_wait_ms`），代码只读契约值——
这也是 Phase 3 双绿 CI 的自然接入点。

### P2-3 `ensureLink` 注释已过时

`utils/link.js:155-160` 写"两窗累计 ~26s，覆盖看门狗兜底（~6s）与常见监督超时"。
现状：订阅态看门狗是 **300s**（契约 v1.1），26s 覆盖不了。注释会误导后续排查。

修法：改为"覆盖监督超时与手机栈恢复；订阅态僵尸链路超出本预算，走适配器重启"。

### P2-4 `#23` 判据口径需要区分「登录请求数」与「登录成功数」

`#23` E1 断言 `authLogins 增量=1`。由于 P1-1 的限流重试，一次逻辑登录在 wire
上可能出现两条 auth.login（一条 rate_limited + 一条成功）。若计数器按请求计，
会误判 FAIL；按响应计则 PASS。建议同时记录两项并在报告里区分。

## 3. P3 级建议

1. **`logRing` 600 条**：T5 soak/压测长跑会绕回，早期报文被挤掉。建议
   `logSummary` 在环形覆盖时标注 `wrapped:true` 并保留已淘汰区间的最小/最大日志号。
2. **`contract_sha`**（Phase 3）：本次两端 `contract/v1/*.json` 已逐字节一致
   （sha 全同），但报告头与 `device.info` 没有哈希，漂移不可见。建议报告头写
   `contract_version + 四文件 sha256 前 8 位`，设备侧 Phase 3 加 `contract_sha`。
3. **`utils/contract.js` 的 data.js 生成链**：已具备（`tools/gen_contract_data.js`），
   建议在 CI 里加"JSON→data.js 重新生成后 git diff 必须为空"，防止手改。

## 4. 做得好的地方（保持）

- `disconnect()` 区分「本地 GATT 关闭」与「外设断连」，并用 `waitForAdvertising`
  拿设备侧证据——这个认识水平高于一般实现，本轮定性全靠它；
- 身份锁 `device_mismatch` + 尾号匹配 + 连后校验，21:48 串台类问题已真机闭环；
- `resetAdapter` 的 `_resetting` 事件抑制（避免误判"用户关蓝牙"）；
- 契约消费已落地：`bmirror.js:31` 直接 `require('./contract').TERMINAL_STATES`，
  `acceptance.js:2044` 用 `contract.isTerminal`，`TRY_TRANSIENT_CODES` 从契约取；
- `json-stream.js` 字节级括号配对正确处理字符串内的 `{`/`}`/转义。

## 5. 设备侧/契约侧的配套动作（我方）

1. 已在 `timing.json#derived_client_budgets.link_recovery` 记录：设备自救 300s ≫
   客户端 26s，**客户端必须提供适配器重启路径，不得依赖等待**；
2. 契约 `firmware_baseline` 已同步到 `1.3-2ef2a38`（修正了 9e1d6c5 的陈旧值）；
3. 可选（1.2 提案）：设备/客户端任一方增加链路保活（客户端每 30s 发一条轻命令，
   或设备发起 ping 要求应答），使订阅态回收阈值可降到 60-90s，从根上消掉 5 分钟
   空窗——需双方评估功耗与协议增量。

## 6. 结论

- 本轮 #11/#21 **不是固件缺陷**：设备按契约行为（订阅态 300s 自救），
  失败源于手机栈半开 + 客户端 26s 预算覆盖不了；
- 客户端代码整体成熟，但有 **3 个 P1 可改进点**（节流基准、拆链后不复核广播、
  #21 归因口径），其中前两个直接对应本轮与 #23 的现场表现；
- 产品层最有效的补丁：**一键适配器重启**（已有）接到失败路径上，而不是让用户
  去关系统蓝牙。
