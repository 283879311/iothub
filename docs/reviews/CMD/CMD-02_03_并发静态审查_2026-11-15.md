### 1.1 无锁读的性质分类

| 类别 | 位置 | 说明 |
| --- | --- | --- |
| **理论数据竞争**（跨任务） | 723–726、1033、2667/2757/2863 | 写者可能是 worker / NimBLE 任务；读者是 dispatcher。C11 下属 UB，但对象是对齐 `bool`/`char[]`，Xtensa 上实际表现为"读到旧值或撕裂的短窗口"。 |
| **解锁后使用** | 811 | 解锁后读 `operation_id` 组响应；若此时 cleanup 被另一任务触发，`memset` 可能清空该缓冲，响应出现空 `operation_id`（窗口极窄）。 |
| **worker 起始副本** | 555、567–569 | run_fn 一开始就复制 `active/ssid/password/owner`，**未持 J**；此时若 cancel/expire 已进入 cleanup 并 `memset`，副本可能被撕裂。 |
| **单任务安全** | 1069/1087/2757 | 仅 dispatcher 读写，属既定设计；一旦 apply 移到别的任务执行即失效。 |

### 1.2 CMD-02 结论

- 绝大多数字段符合"J 串行"的既定契约；**例外是上表 7 处读点**。
- 这 7 处不影响当前功能验收，但**不满足**"每个字段有明确锁保护/单任务所有权说明"的 CMD-02 验收标准。
- 建议（不改语义，均为小改）：
  1. L723–726 幂等查重段、L1033 `st_internet_verified` 读、dispatch 三处 `active` 读，统一改为持 J 的窄函数（如 `app_cmd_net_job_active()` / `app_cmd_net_job_verified()`）；
  2. L811 在锁内把 `operation_id` 复制到局部数组后再组响应；
  3. worker 起始副本（555/567–569）移入 J 内（复制后立即解锁），顺带消除与 cleanup 的撕裂窗口。
- **未做代码修改**：本轮只出证据，改动需单独排期与回归。



### 1.3 CMD-02 最小补丁设计（待代码授权）

**设计目标**：只把 7 处跨任务读点纳入既有 J = s_net_job_lock 所有权边界；不改变命令协议、错误码、operation 状态机、网络流程及锁序。所有锁内操作仅做标量/定长缓冲区快照；cJSON、日志、operation API、Wi-Fi API 均在解锁后执行。

| 读点 | 当前读者 / 可能写者 | 最小处理 | 锁内快照 | 行为影响 |
|---|---|---|---|---|
| cmd.c:723–726（active/op/idem_key） | dispatcher；受理、worker cleanup 可写/清零 | 增加局部快照块，持 J 一次复制三项，随后解锁；后续幂等比较、app_operation_get_status、响应构造均使用局部值 | bool job_active、app_operation_t *job_op、char job_idem_key[sizeof(s_net_async.idem_key)] | 保留原判断顺序和 busy/幂等响应语义；不在 J 内获取 O 锁或构造 JSON |
| cmd.c:811（operation_id） | dispatcher；cleanup 可并发 memset | 在受理路径释放 J 之前复制到局部数组；响应只读局部数组 | char accepted_operation_id[sizeof(s_net_async.operation_id)] | 响应仍使用受理时生成的 ID；消除解锁后读共享缓冲区 |
| cmd.c:1033（st_internet_verified） | apply dispatcher；worker 写阶段快照、cleanup 清零 | 在该判断前持 J 复制 bool，解锁后判断局部值 | bool internet_verified | 仅增加同步；不在锁内调用日志或构造错误响应；保留原 verify_timeout 分支 |
| cmd.c:2667/2757/2863（三个 dispatch active 读点） | dispatcher；worker cleanup 可清零 | 使用单一窄 helper app_cmd_net_job_is_active()：内部持 J 读 bool 后立即解锁 | bool active | 保留各分支原有判断位置与返回错误；不把检查与后续业务合并成更大锁区 |
| cmd.c:555,567–569（worker 起始 active/ssid/password/owner） | operation worker；cleanup 可并发清零整个 job | app_cmd_net_async_run() 开始时持 J 一次性复制并验证；解锁后再调用 Wi-Fi/MQTT/operation API | bool job_active、char ssid[33]、char password[65]、app_cmd_source_t owner | 保留本次 run 的局部凭据快照；若取得锁时 job 已清理则返回 ESP_ERR_INVALID_ARG；不在 J 内执行阻塞操作 |

#### 实施约束

1. app_cmd_net_job_is_active() 只能在调用方未持 J 时调用；不得在已持锁路径重复调用，避免递归锁依赖扩散。
2. 723–726 的快照锁区只复制字段；解锁后再调用 app_operation_get_status() 或构造 cJSON，避免新增 J → O 持锁范围。
3. worker 快照锁区不调用 app_operation_get_status()、app_wifi_set_active_operation()、日志或任何可能阻塞的 API。
4. 811 的局部 ID 必须在受理路径持 J 时复制；不能改为解锁后重新调用 app_operation_id() 代替共享字段快照。
5. s_net_async_apply_internal 仍按 dispatcher 单任务所有权处理，不纳入 J 读点；此约束需保留注释，若未来改为跨任务读写再重新审查。
6. 本设计不处理 CMD-03 的 store_trial 窄窗口，也不抽取 cmd_net_guard；两者独立评审、独立授权。
7. 实施后必须重新核对全部读写点与锁序，并执行 git diff --check、严格语法/编译检查及针对受理、重复幂等、apply、cancel/expire 的回归；未取得对应构建/测试证据不得标 PASS。

#### 语义与验收边界（2026-11-15 审阅补充，C1–C3）

**C1 · 消除数据竞争 ≠ 检查与动作原子**

本补丁只把读点纳入 J 锁快照，**不宣称**检查与后续业务动作是原子的；各组的原子性仍由既有机制保证：

| 读点组 | 快照后仍存在的窗口 | 真正的安全边界 |
| --- | --- | --- |
| 723–726（幂等查重） | 快照后 job 可能被 cleanup 清零，仍可能返回旧 op 的幂等终态 | operation 的 `generation`/终态保留语义；返回值仍属合法幂等结果 |
| 811（受理响应） | 无（纯局部副本） | — |
| 1033（`st_internet_verified`） | 快照后该值可能被 cleanup 清零 | 后续 `set_state(COMMITTING)` 与 `expiring` 闸；本门仅为"理论不可达"兜底 |
| 2667/2757/2863（`is_active()`） | 返回 true 后业务分支照常执行，期间 job 可能被清零 | 受理/apply/cancel 各自在 J 内的二次校验与 operation 状态机 |

**C2 · 第 5 组必须保持原有早退顺序**

## 2. CMD-03：锁序、回调时序与并发关系

### 2.1 `operation.c` 的并发模型（代码可证）

- 单一临界区 `s_ops_mux`（`operation.c:49`），所有状态迁移、槽位扫描、`generation` 比对都在其中。
- **回调一律在临界区之外执行**：
  - `run_pending`：锁内取 `run_fn/ctx` 并置 `CONNECTING`+`running=true` → 解锁 → 调 `run_fn`（L573–577）→ 再锁清 `running`；
  - `cancel`：锁内置 `expiring=true` 并快照 `cleanup/ctx/generation` → 解锁 → 调 `cleanup`（L487–489）→ 再锁按 `generation` 裁定终态；
  - `expire_one`：同 cancel 模式（L645–649）。
- `expiring` 闸：cleanup 在飞期间，`app_operation_set_state` 一律返回 `ESP_ERR_INVALID_STATE`（L421–437），保证"进入 COMMITTING"与"cleanup 已启动"互斥。
- `running` 标志：run_fn 返回前禁止槽位回收/复用（`app_operation_reclaim_terminal_locked` 跳过 `running`）。
- `set_state` 对 `COMMITTING` 清 `deadline_ms`（不可取消、不按 TTL 过期）。

### 2.2 锁序

| 方向 | 证据 | 结论 |
| --- | --- | --- |
| `J → O` | cleanup 持 J 调 `app_operation_state/id`（cmd.c:490–498）；受理持 J 调 `app_operation_start`（787/792）；apply 成功/失败持 J 调 `set_state`（1093/1124） | 存在且一致 |
| `O → J` | operation.c 的回调都在 `portEXIT_CRITICAL` 之后（573–577、487–489、645–649） | **不存在** |
| `J → W/M/F` | `apply` 持 J 调用内层 `execute_method`（含 config/NVS，见 CMD-14）；`operation_status` 的 W/M 取用在 J 之外 | 唯一长持锁点是 apply（已知，CMD-14） |

**不变量（必须保持）**：`operation.c` 不得在 `s_ops_mux` 内调用任何 `cmd.c` 回调；否则立即形成 `O → J` 与既有 `J → O` 的对锁死锁。

### 2.3 回调时序

| 触发 | 锁内动作 | 锁外动作 | 终态裁定 |
| --- | --- | --- | --- |
| worker 取活 | 置 `CONNECTING`、`running=true` | `run_fn`（void `cmd_net_async_run`） | run_fn 自行 `set_state`；失败路径在 `expiring` 时让位给 cleanup |
| cancel | `expiring=true`、快照回调 | `cleanup_fn`（`cmd_net_async_cleanup`） | 回调成功且 `generation` 未变且仍 active → `CANCELLED`；回调失败 → `FAILED/CLEANUP_FAILED` |
| expire | 同上 | 同上 | → `EXPIRED` / `FAILED/CLEANUP_FAILED` |
| 终态保留 | `terminal_ms` 记录，600s 后回收 | — | `running` 为 true 时回收跳过 |

### 2.4 发现：worker 的 post-wait 守卫看不到 `expiring`

- 事实：`app_operation_status_t`（`operation.h:59–69`）**不含** `expiring`；worker 在阻塞返回后只校验 `state == CONNECTING && generation` 一致（cmd.c:583–591）。
- 机制：`cancel`/`expire` 先置 `expiring=true`，但状态要到 **cleanup 返回后**才变 `CANCELLED/EXPIRED`。若 `app_wifi_try_connect_ip` 恰在此窗口返回 `APP_WIFI_TRY_OK`：
  1. worker 的守卫看到仍是 `CONNECTING` → 通过；
  2. `app_cmd_net_store_trial()`（持 J）在 cleanup 已 `memset` 之后**重新写入 `s_net_trial`**；
  3. worker 继续写 `netcheck_gen`/`st_*`（写入已清空的 job，`active=false`）并 `stage_snap_put`；
  4. 随后 `set_state(GOT_IP)` 被 `expiring` 闸拒绝（或状态已终态），op 仍为 `CANCELLED`。
- 后果：一个已取消的 op 可能留下**有效 trial**（含候选 SSID/口令），在 trial 的 300s TTL 内让 `tryconnect` 的 `trial_busy` 分支返回 `busy`，阻塞后续受理。
- 窗口性质：要求"连接成功"与"cancel 进入 cleanup"几乎同时发生；当前未见现场复现，属**待动态验证**的机制性缺口。
- 建议（不改状态机）：`app_cmd_net_store_trial()` 在持 J 后增加 `s_net_async.active && s_net_async.op == op` 校验（需要传入 op），或在 `app_operation_status_t` 暴露 `expiring` 供 worker 守卫使用。两种方案都需设计评审，**不支持**直接改 `expiring` 语义。
- 现有缓解：BLE 断连取消时 `try_connect` 通常返回 `CANCELLED`，走失败分支而不写 trial；这解释了为何 R2 场景未触发。
