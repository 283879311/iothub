> 结论：**GATT 定义、CMD 控制通道、DATA 字节回环、MTU23 分片、双通道并发、断连恢复均已完成实测**。T3 功能项 **15/15 PASS**（`t3_ble_channels_20261023_234439.json`）。

## 2. GATT 只读审计

active 实现为 NimBLE；`main/bt_gatts.c` 是 Bluedroid 备用实现，属性同构。

| 特征 | 属性（实测） | CCCD | 值容量/实现 |
| --- | --- | --- | --- |
| DATA RX `0002` | `write`, `write-without-response` | 无 | `NUS_RX_VALUE_MAX=256`；回调只 memcpy+入队 |
| DATA TX `0003` | `notify` | 有（`00002902-...`） | notify-only；无 read/write/indicate |
| CMD RX `0004` | `write`, `write-without-response` | 无 | 行重组器，单行 ≤512B |
| CMD TX `0005` | `notify` | 有（`00002902-...`） | notify-only；命令响应队列 |

实测九项全部 true：Service 存在、两个 RX 支持 write/without-response、两个 TX 支持 notify、两个 TX 均有 CCCD、两个 TX 均不提供 indicate。未发现 DATA/CMD 共用同一个特征或同一应用层缓冲区。

## 3. 源码实现与可靠性边界

### 3.1 DATA 路径

- DATA RX 的 GATT access 回调（`main/bt_gatts_nimble.c:77-118`）把本次写入拷贝到 256B 栈缓冲，然后调用 `app_ble_dataplane_on_write()`（`main/transport_ble.c:52-56`）。
- `app_ble_dataplane_on_write()` 只调用 `data_pipe_feed(DATA_PORT_BLE, ...)`；`data_pipe_feed()` 把字节按 256B 分块入 **16 深度静态队列**（`main/data_pipe.c:13,169-203`），队列满时丢弃剩余字节并返回 false，但 **GATT 回调忽略返回值，ATT 写响应仍是成功**。
- `data_pipe` 任务按路由位图出站。`data.loopback=true` 时 BLE 端口路由到自身（`main/data_pipe.c:149-162`），用于本轮 BLE↔BLE 实测；默认路由是 BLE→UART1|MQTT、UART1→BLE、MQTT→BLE（`main/config.c:420-422`）。
- DATA TX 由 `app_ble_gatts_notify()` 发送（`main/bt_gatts_nimble.c:371-397`）：按 `s_mtu-3` 分片，单片上限 512B；**没有应用层发送队列、没有分片间延时、没有重试**。中途失败时已发送前缀返回 true，`data_pipe` 仍按整块计入 tx，未发送部分不会补发。
- DATA TX 只有在客户端订阅 CCCD 后才发送；未订阅时 GATT 写仍可成功，但数据被丢弃且不通知发送端。
- **断连**：`app_ble_gatts_nimble_on_disconnect()`（`main/bt_gatts_nimble.c:271-283`）复位订阅/MTU，并调用 `app_ble_cmd_on_disconnect()` 清理命令通道；**没有调用 `data_pipe` 的 flush/clear**，也没有会话 ID。队列中的旧字节在重连后可能被重新路由到新订阅（队列只有 16 深度，窗口小，但不是结构上禁止）。
- `data_pipe` 设计明确写着“有界静态队列：满了就丢弃并计数；数据面允许丢帧，不允许撕裂/错位”（`main/data_pipe.h:13-17`）。这是 **best-effort 原始字节语义**，不是可靠流。

### 3.2 CMD 路径

- CMD RX 行重组（`main/ble_cmd.c:130-180`）：接受 `\n` 结尾或完整 JSON；单行 ≤512B；命令队列 8。
- 命令任务独立，5 次/秒限频；CMD TX 有独立 8 深度队列和发送任务（`main/ble_cmd.c:205-276`）；每片间隔 20ms；仅在“一个字节都没送出”时重试 3 次，已送前缀不重发（避免重复 JSON）。
- 断连清理：`app_ble_cmd_on_disconnect()` 清 token、行缓冲、TX 队列，并取消 BLE 活动网络候选；本轮实测新会话无旧 JSON 片段泄漏。
- `operation.get` 在长响应发送期间可以被命令任务处理；但 CMD TX 是 FIFO，响应可能排在长响应之后。MTU23 下长响应约 1.2s，足以让 `operation.get` 请求落在分片窗口；MTU256 下约 100ms，`operation.get` 请求通常在长响应结束后才发出。

### 3.3 共享资源与并发

- CMD TX 和 DATA TX 使用不同的 GATT 特征/CCCD，但共享 NimBLE host、msys mbuf 池和 BLE 射频。
- CMD 有独立 TX 队列和 20ms 片间隔；DATA 没有独立 TX 队列/片间隔。双通道并发本轮通过，但 DATA 慢接收端没有背压。
- `data_pipe` 的 BLE/UART1/MQTT 出站由同一个 `data_pipe` 任务执行；本轮只验证 BLE→BLE 回环，没有验证 UART1/MQTT 源的长 DATA 帧。
- **2026-10-25 补测（`tools/ble_p0/t3_uart1_datapath.py`，`t3_uart1_20261025_232341.json`，物理 UART1 接入 ttyUSB1）**：
  - **BLE→UART1 出站（B2U）通过**：200B 与 1000B（50×20B DATA RX 写入）经 data_pipe 路由到 UART1 TX，**逐字节一致、零丢失**——外部宿主侧首次验证了 DATA RX 入站→路由→UART 出站链路（T3 归档缺口的一半）。
  - **UART1→BLE 入站（U2B）无法测试：固件缺口（P1-11）**——全工程无 `uart_read_bytes`/UART 事件任务，`data_pipe_feed(DATA_PORT_UART1,...)` **不存在**；UART1 RX 只装了驱动缓冲、无人读取，`rx[UART1]` 统计恒为 0。`data_pipe.h`"三边共用入站/出站"的注释与实现不符：UART1 是**只有出站没有入站**的半边端口。本轮 256B/2048B 写入 ttyUSB1 零回传即此原因（非接线问题——反向已逐字节通过）。
  - 影响：`data_route_uart1=→BLE` 路由目前是死配置（无源可路由）；"UART/MQTT 大帧 → DATA TX 多分片"路径在 UART 侧无输入源，MQTT 下行源仍未测。

### 3.4 UART1 单路压测（2026-10-26，`tools/ble_p0/t3_uart1_stress.py`）

范围按决策：只压当前唯一可用的单路（BLE DATA RX → data_pipe → UART1 TX @115200），不涉路由/回环。结果 `t3_uart1_stress_20261026_000319.json`（v3；v1/v2 的 recv=0 与 sent 溢出为 harness 记账缺陷，已修并注明）：

| 相 | 条件 | 结果 |
| --- | --- | --- |
| S1 可靠写 32KB 无节奏 | 240B with-response，宿主固有限速 ≈1.14KB/s | **零丢失逐字节一致**；低于 UART 排空速率（11.5KB/s），压不出过载（宿主 ATT 往返延迟 ~200ms/写，是宿主侧天花板） |
| S1b 无确认写洪泛 64KB | 240B without-response，宿主突发 **710KB/s**（≈62× UART 速率） | 收 19.4KB、丢 46.1KB；**全部整块 240B 丢弃、严格有序、零撕裂**——设备侧 113 条 `queue full (port 1), dropped 240B` 佐证，正是 data_pipe"允许丢帧、不允许撕裂/错位"的契约行为 |
| S2 限速 64KB @24ms | ≈10KB/s，期间宿主链路掉线 2 次（自动重连续传同一分片） | **零丢失**（exact=false 为上相渗漏前缀的记账伪影，非设备丢失） |
| S3 小帧 8KB @20B 无确认 | 400 次小写 | **零丢失逐字节一致** |
| S4 耐久 300KB @24ms/30s | 期间宿主链路掉线 **7 次**（~每 8-10s） | **零丢失**（重连续传同分片语义成立）；goodput 960B/s 受掉线拖累 |

设备侧全程：堆健康（min 43.5KB）、`mqtt_shed=0`、无崩溃；MQTT 镜像路由同批 ~1500 次发布正常消化（`mqtt_outbox` 峰值 1428 后自行排空）。**宿主环境注记**：本轮 BLE 链路每 ~46s（后半程 ~8-10s）周期性掉线（0x222，8 次/轮），属 P1-1 宿主侧问题——反而实证了重连续传语义：跨掉线零丢失。

**模块验收结论（冻结，2026-10-26）**：单路 UART 出站模块压测**通过**——(1) 喂入速率 ≤ 排空速率时零丢失（S1/S2/S3/S4，含跨宿主掉线重连续传）；(2) 队列过载时丢弃有界（整块、有序、不撕裂，v2 轮 113 条告警佐证该路径）；(3) 小帧/大帧/耐久完整性均保持。**不为提高吞吐改 data_pipe**；以此作为稳定基线。

### 3.4.1 结论边界（模块通过 ≠ 覆盖全部场景）

- **过载保护有效 ≠ 无损保证**：S1b 洪泛下丢弃约 46KB 是契约内行为，该模式不保证数据全部送达 UART。
- **重连续传仅覆盖本轮路径**：S2/S4 证明了"断链重连后从同一分片续传"语义；不等价于所有断链时序均已覆盖。
- **测试器历史伪影（已修，不计为固件缺陷）**：v1/v2 的 `recv=0`（drain 循环覆盖累积）、`sent` 记账溢出（尾部分片多记）、相间数据渗漏前缀（跨相 `exact=false`）。验收以 v3 修复后脚本 + 设备侧日志为准。

### 3.4.2 丢弃告警与丢字节的对应关系（审计修正）

- **告警粒度（源码 `data_pipe.c:186-189`）**：每次 `feed()` 调用最多打一条 `queue full (port N), dropped M byte(s)`，M = 该次调用丢弃的剩余总字节数（本测试 240B/写 → 每条告警 = 一次 240B 丢弃），非按队列块计。
- **v2 轮**：113 条告警 ≈ 27KB 告警丢弃（其 recv=0 为 harness 伪影，实际收量未知），证明队列过载路径真实存在且逐写告警。
- **v3 轮（存档轮）修正**：S1b 的 46KB"丢失"**主体不是队列溢出**——设备断链时间戳 54233ms 正落在洪泛中段，无确认写在链路死亡瞬间整体丢失（ATT 语义），设备未收到的字节不产生告警；队列从未过载，故 v3 全程 **0 条 data_pipe 告警**（日志中 11 条 "queue" 均为 ble_cmd 的 `cmd queue full`）。v3 的完整对账：sent 65,536 = recv 19,440（断链前已入管道并排空）+ 断链瞬间未达 ~46KB；子序列校验证明收到的 19,440B 是原序列的有序整块子集。初稿"113 条告警佐证 S1b"系引用错误轮次，特此更正。
- **复测注意**：控制台（UART0@115200）与业务共存时日志可能交错/截断，告警条数不保证完整，对账以 harness sent/recv 算术 + 子序列校验为准，告警仅作行为佐证。

### 3.4.3 环境问题（独立跟踪，不因模块通过关闭）

宿主 BLE 断链 **不是随机抖动**：v3 轮 8 次断链间隔 48.4/46.4/46.4/46.3/46.5/46.4/46.5s——**精确周期 46.4s**，reason 恒为 0x222（LL Response Timeout）。机理假设：设备每次连接发起连接参数更新请求（30-50ms，`bt_gatts_nimble.c:262-268`），宿主控制器/BlueZ 未完成该 LL 过程，**规范 40s LL 过程响应超时**到期即断链（40s + 建连开销 ≈ 46.4s，每次重连重置时钟）。待验证：btmon 抓 LL 过程；手机连接是否同样 ~46s 死亡（区分宿主侧/设备侧）。P1-1 保持开放，按此签名单独分析。

**路由层设计**（P1-11 入站实现 vs 文档修正）按决策在模块验收冻结后另行立项。

### 5.2 CMD（MTU23）

| 测试 | 结果 |
| --- | --- |
| 275B 长命令 | 14×20B 写入；实际 275B；返回 `unknown_method`（故意使用未知方法，**不改配置**）；证明 20B 行重组。真实 275B 静态 v0 `config.set` 已在 T1/P0 以 240B 分片验证；T3 用同尺寸合成命令验证 20B 传输路径，避免改配置 |
| 长响应 `config.get` | 1186B；60 个 20B 分片；完整 JSON id 匹配；`long_response_ok=true` |
| 长响应期间 `operation.get` | 请求在长响应期间发出；`opget_sent_during_long=true`；state `connecting`；latency 1.218s；响应因 CMD TX FIFO 排在长响应后（`opget_done_before_long=false`） |
| CMD+DATA 并发 | 长响应期间发送 100B DATA；DATA 回环 100B 逐字节一致；CMD 响应完整，无串道 |
| 断连 | 长响应已发 61 片时断连；重连后 `device.info` 正常；新会话无旧 JSON 片段 |

MTU256 严格基线（`234025`）：长响应 1186B 为 5 个 253B 级分片，分片发送约 100ms；首片到达前还有约 1s 的命令处理/调度延迟，`operation.get` 在本脚本“等到首片后再发”的规则下落在剩余分片窗口之后（`opget_sent_during_long=false`），因此该项在 MTU256 基线为 false；恢复后复核用 `--no-require-opget-during` 记录该预期差异，其余 15 项全通（`235335`）。

### 5.3 双通道并发与断连

- CMD 长响应期间 DATA 回环 100B 成功；CMD TX 和 DATA TX 的特征/回调/队列相互独立，未观察到覆盖或串道。
- CMD 断连清理有效：token 失效、行缓冲/TX 队列清空、新会话只看到新响应。
- DATA 断连本轮未观察到旧字节，但**源码没有显式清理 `data_pipe` 队列/会话**；这属于残余风险，不应据此宣称断连隔离已由协议保证。
