# 静态 IP 回写「回读不一致 / characteristic_missing」定性（2026-11-06 21:43）

> 现场：小程序 21:43:23 `config.set`（net_mode、sta_use_static、静态地址/掩码/网关）
> → 21:43:25 报「已受理但回读不一致（设备返回 sta_use_static=true / sta_ip_addr=-）」；
> 21:43:50 重试 → 报「写入失败 [characteristic_missing]」。
> 串口全程有录（`artifacts/t4_rerun_20261106/serial_t4.log`，boot C）。
> **结论：配置写入成功并已生效；两条报错都出在客户端，设备侧无需回滚。**

## 1. 设备侧事实（boot C 只读复核，21:47）

```

串口 boot C: wifi: STA_CONNECTED: static ip mode / IP_EVENT 192.168.1.50
             mqtt: MQTT connected（4.9s）
```

**静态配置完整持久化，网关/掩码/DNS 都在，`.50` 已生效，MQTT 在线。** 不需要重写。

## 2. 报错一：`sta_ip_addr=-` 是客户端字段名不匹配

设备 `config.get.network` 的键是：

| 设备实际键 | 小程序回读用的键 | 结果 |
| --- | --- | --- |
| `sta_use_static` | `sta_use_static` | ✅ true |
| `sta_static_ip` | `sta_ip_addr` | ❌ 取不到 → `-` |
| `sta_static_netmask` | `sta_netmask` | ❌ |
| `sta_static_gateway` | `sta_gateway` | ❌ |

`sta_use_static` 恰好同名，所以「一半读到了、一半是 -」。**改成设备键名即可**（或做一层 key 映射）。
这与 §7.4 的字节计数问题是同一类：套件侧字段名/口径与设备契约不一致。

## 3. 报错二：`characteristic_missing` 是复位后的旧 GATT 句柄

串口时间线（boot B）：

```
479225  rx v1 cmd=config.set id=135 (235B)
479255  ble cmd effect=reboot: response sent, reboot scheduled (1.5s)
479765  rx v1 cmd=config.get id=136        ← 客户端在复位窗口内做回读（+0.54s）
480755  wifi: STA disconnected reason=8(ASSOC_LEAVE) → rst:0xc (SW_CPU_RESET)
        boot C：static ip mode / .50 / MQTT connected
```

`config.set` 的响应字段里**本来就有信号**（`main/cmd.c:1486-1487`）：

```c
cJSON_AddBoolToObject(resp, "applied", effect != CFG_EFFECT_REBOOT);      /* false */
cJSON_AddBoolToObject(resp, "restart_required", effect == CFG_EFFECT_REBOOT); /* true */
```

设备按 `restart_required=true` 在 1.5s 后重启；21:43:50 的第二次写发生在重启之后，
小程序仍持旧 GATT 对象 → `characteristic_missing`（需重新发现服务，不是设备特征缺失）。

## 4. 处置

**客户端（必须）**

1. `config.set` 返回后先看 `restart_required`：为 true 时**不做内联回读**，直接进「设备重启中」流程
   —— 等断开 → 等重新广播 → 重新发现服务 → 重登 → 再 `config.get` 校验；
2. 回读校验用设备键名（`sta_static_ip`/`sta_static_gateway`/`sta_static_netmask`）；
3. `characteristic_missing` 归到「需要 relink」分支，不要提示「设备特征不完整」。

**固件（可选 P2，非本次阻塞项）**

- `config.set` 已调度重启后，后续命令可回 `rebooting` 明确拒绝，避免客户端拿到半截响应；
- 重启前等待 BLE TX 队列排空（有界，如 ≤2s），避免在途长响应被复位切断；
- 串口在片 20 后静默 620ms 直至复位（若只是日志被截，片 21 起也应有行）——
  疑似 `notify_chunk` 在主机缓冲耗尽时阻塞，属"长回包 + 背压"的既有脆弱点，可与 DEF-SCAN-001 二期一起看。

## 6. 【21:58】三条客户端改法已全部落地（固件侧仍 0 项改动）

改动全部在 `wx-ble-provision`，16 套自测 **951 项全绿**（page-provision 112→120，

### 6.1 键名修正（比预想更严重：未知键被静默忽略）

`main/config_apply.c` 配置表核实：固件**不存在** `sta_ip_addr / sta_gateway /
sta_netmask / sta_dns_addr`，且未知键是「静默忽略」（config_apply.c:770
`ignore unknown field`）——即 21:43 那两次写入里**只有 `net_mode` 与
`sta_use_static` 真正生效**，`.50` 是设备里本来就存的旧值碰巧一致。
这是隐性陷阱：写一个新地址会静默保持旧地址且界面显示「已受理」。

已改（写入与回读统一为固件配置表键名）：

| 旧（无效） | 新（配置表同名字段） |
| --- | --- |
| sta_ip_addr | sta_static_ip |
| sta_gateway | sta_static_gateway |
| sta_netmask | sta_static_netmask |
| sta_dns_addr | sta_static_dns1 |

同步修改：netcfg 页写入/回读/诊断行、console 页「config.set 静态IP」预设。

### 6.2 restart_required=true → 重启流程，绝不在窗口内联回读

netcfg `_staticWrite` 读到 `resp.restart_required===true` 后走新函数
`_staticWaitRebootAndVerify`：等断开（≤12s）→ `_relinkOnce`（等重新广播 →
ensureLink 重连+重登，凭据用会话内存凭据）→ `config.get` 回读校验（新键名）→
运行态确认（预算 25s，比内联路径的 15s 宽：重启后要重新关联 + 重连 MQTT）。
旧固件 v0 外壳响应无该字段，维持内联回读的双轨兼容路径。

### 6.3 characteristic_missing → relink 分支

- `_staticWrite` 写入遇 `characteristic_missing / not_connected / disconnected /
  ble_write_timeout` → `_relinkOnce` 一次后重写；relink 失败报「链路已失效且自动
  重连未成功，请手动重连后重试」，**不再出现「设备特征不完整」**；
- `errors.js` 文案改为「BLE 特征不可用：设备可能已重启或链路已失效，请重新连接」；
- `ble.js` write 的 `!ch` 分支报错信息同步改为「句柄已失效，请重新连接」。

### 6.4 顺手修掉的一个真实 UX bug

`_applyStaticCfg` 原来每次被 `refreshStatus` 调用都把 `verify` 置空——
即「✔ 已生效」刚写出来就被状态刷新抹掉，用户永远看不到。已改为保留非空结论，
仅用户编辑（onStaticSwitch/onStaticInput）时清除。
