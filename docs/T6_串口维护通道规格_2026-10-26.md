# T6 串口维护通道规格（评审版，未实现）

日期：2026-10-26。状态：**规格待评审**——批准后按实验分支模式实现。
前置：P0-6/P1-1/P1-10/P1-11 已关闭并推送（`a62ab62`）；UART1 业务数据面（双向）已验收冻结。

## 0. 定位与硬边界

串口维护通道 = BLE 之外的**本地救援/产线通道**，用于 BLE 不可用（射频故障、手机端 bug、看门狗场景）时的最后手段。

**硬边界（本节任何一条被实现违反即打回）**：

1. **物理隔离**：只用 UART0（USB 调试口，与 ESP_LOG 控制台同口）；**不碰 UART1**（业务数据面，已冻结）。
2. **方向隔离**：维护通道读取 UART0 上的**用户输入行**并回写响应；ESP_LOG 日志照常输出到同一 UART0。两者**不做字节流复用**——响应以 `\r\n` 帧界回写，日志行天然以换行结束；解析器只认行首 `{`，日志行直接忽略（见 §5 帧格式）。**不引入**"data_pipe 混流/路由"类设计——维护通道与 data_pipe 零交互。
3. **权限上限**：串口通道权限 ≤ BLE 通道（同一鉴权、同一 per-source 守卫网），另加物理在场约束（§3）。

## 1. 命令范围（最小救援集 + 白名单）

复用 `app_cmd_execute_ex` 分发器与 v1 命令 schema（与 BLE 完全同一执行路径，不另写处理器）。

**白名单（v1 `cmd` 名）**：

| 允许 | 理由 |
| --- | --- |
| `device.info`、`auth.login` | 探测与鉴权 |
| `network.status`、`network.scan` | 救援诊断 |
| `network.tryconnect`、`operation.get`、`network.apply`、`network.cancel` | 完整配网事务 |
| `config.get`、`config.set` | 配置读写（含 v0 网络域，走既有路径） |
| `network.profile.list`、`network.profile.delete` | profile 管理 |
| `diag.*`（只读类，若有） | 现场诊断 |
| `system.reboot` | 恢复手段 |

**明确禁止**（串口侧直接 `forbidden`，不进入分发器）：

- `factory.reset`——需物理确认（BOOT 键），串口命令单独不可触发；
- `auth.admin.set`、`provisioning.pin.set`（敏感写；`device.info.security.sensitive_writes_allowed=false` 的既有语义）；
- `uart.send`、`data.loopback`、`led/relay/io` 控制类——与救援无关且 io 控制已有物理/云通道。

## 2. 鉴权

- **同一账号体系**：`auth.login(username, password)` → 设备侧 token（与 BLE 同源凭据，`app_auth_check_credentials`）；
- **token 规则与 BLE 相同**：600s TTL；**串口会话独立于 BLE 会话**（各自 token，互不通用、互不失效）；
- 白名单内除 `device.info`/`auth.login` 外全部 `auth_required`；
- 失败率限制：同 BLE 侧不做账号锁定（既有行为），但串口侧**输入行级限频**见 §6。

## 3. 物理在场约束（比 BLE 多的一层）

串口通道**默认关闭**，两个使能方式（都要求物理接触）：

1. **持续按住 BOOT(GPIO0) 时上电/复位** → 本次启动会话内串口通道开启（`serial_maintenance_unlocked`，RAM 标志，不落 NVS）；
2. （备选，默认不实现）config 编译期开关 `CONFIG_IOTHUB_SERIAL_MANTERNA_ALWAYS`，仅产线构建启用。

> 理由：UART0 线序公开于板边，任何人插上 USB 即可敲命令不可接受；BOOT 组合把攻击面收缩到"能物理按键的人"，与 factory.reset 的既有物理确认同级。代价：救援时需一次带按键的复位——可接受（BLE 救援仍是一线，串口是 BLE 失效后的二线）。

## 4. 命令源与权限映射

- 新增 `APP_CMD_SOURCE_SERIAL` 进 `app_cmd_source_t`；
- **per-source 守卫对齐 BLE**：所有 `source == APP_CMD_SOURCE_BLE` 的分支同步加 SERIAL（网络命令守卫 `cmd.c:1209` 的允许集、operation owner 映射 BLE/SERIAL 各自独立 owner、IO 事件来源标记 `APP_IO_SOURCE_SERIAL`）；
- **MQTT 域守卫不变**（SERIAL 与 BLE 同属本地源，可改网络域——这正是救援需要的能力）。

## 5. 帧格式与传输

- **行分隔 JSON**：一行一条命令（`\n` 或 `\r\n` 结尾），编码 UTF-8；v1 外壳与 BLE 相同（`{"id","version":"1.0","cmd","args","token"}`）；响应也单行 JSON + `\r\n`；
- **输入重组**：行缓冲 512B 上限（与 BLE CMD 一致），超长行丢弃整行并回 `line_too_long`；
- **日志共存规则**：解析器只接受**行首为 `{`** 的行；ESP_LOG 行（`I (1234) tag:` 前缀）与启动 banner 自然被忽略；响应回写与日志输出在 UART0 上交错是**预期行为**（客户端按行配对 `id`，与 BLE JSON 流配对同理）；若评审认为不可接受，备选方案 B：维护响应加前缀 `#M# `（4 字节标记），客户端先扫标记再解析——默认方案 A（无前缀），B 留待实测噪声后定；
- **二进制安全**：不承诺（维护命令全是 ASCII JSON）。

## 6. 超时、限频与并发

| 规则 | 值 | 说明 |
| --- | --- | --- |
| 行读超时 | 无（行缓冲到换行为止，20ms 轮询） | 半行不死等 |
| 命令限频 | 与 BLE 相同 5 次/s（200ms 间隔），超限回 `rate_limited` | 串口无 BLE 突发，按行自然节流 |
| 命令执行超时 | 与 BLE 相同（长命令如 scan 由命令自身异步化，通道不阻塞） | `tryconnect` 返回 operation_id，轮询 `operation.get` |
| 并发模型 | **单读者任务**（1 个 `serial_maint` 任务，栈 4KB，优先级 3） | 一次一条命令，天然串行 |
| 与 BLE 并发 | 允许同时连接；**operation 语义不变**（SERIAL/BLE 各自 owner，槽位/淘汰/busy 语义共享，已有实现天然支持） | BLE 断连只取消 BLE-owned 候选，不影响 SERIAL-owned |
| 与 data_pipe | **零交互**：不调 feed、不注册端口、不设路由 | 硬边界 §0.2 |

## 7. 模块与实现要点（预估 ~250 行）

- 新文件 `main/serial_maint.c/.h`：BOOT-unlock 探测（复用 `prov_pin.c`/bootstrap 的按键读取模式）、行读取任务、白名单、v1 包装（复用 `ble_cmd.c` 的 envelope 函数或提取共用）、响应回写（`fprintf(stdout)`/`uart_write_bytes(UART_NUM_0)`，需实测 ESP_LOG 与 stdout 共存的正确回写方式）；
- `cmd.h/cmd.c`：`APP_CMD_SOURCE_SERIAL` 枚举 + 守卫分支同步；
- `operation.h/c`：`APP_OPERATION_OWNER_SERIAL`（与 BLE owner 并列，无行为差异）；
- **不改**：data_pipe、uart.c（UART1）、BLE 栈、Wi-Fi 栈。

## 8. 验收清单

1. 未按 BOOT 复位：串口输入任意命令 → 无响应（或单行 `serial_maintenance_locked` 提示，评审定）；
2. BOOT-unlock 后：`device.info`（无 token）→ `auth.login` → 白名单命令全通；
3. 禁止命令（factory.reset/auth.admin.set/uart.send）→ `forbidden`；
4. 错误凭据 → `invalid_credentials`；无 token → `auth_required`；错误 token → `unauthorized`；
5. 完整救援事务：坏 SSID、无 IP、MQTT down 场景下 `scan → tryconnect → operation.get → apply` 成功恢复（无 AP 参与）；
6. BLE 与串口并发：各自登录、各自发命令、SERIAL-owned operation 不被 BLE 断连取消；
7. 超长行 → `line_too_long`；限频 → `rate_limited`；
8. `config.set` 重启生效类命令：响应先回、后重启（与 BLE 的 reboot_after_response 语义一致）；
9. 回归：UART1 数据面（B2U/U2B 各一轮逐字节）、BLE P0 冒烟（登录/status/scan）、ESP_LOG 输出不受干扰；
10. 日志/响应交错实测：连续命令 + 触发日志（如 diag 周期行）时客户端按 id 配对成功率 100%（方案 A 的判据；不达标改方案 B 前缀）。

## 9. 开放问题（评审时定）

1. 锁定状态下的回显：完全静默 vs 单行提示（倾向**单行 `serial_maintenance_locked`**，否则现场误判"串口坏"）；
2. 方案 A/B（响应前缀）默认取 A，验收第 10 条不达标再切；
3. `diag` 域是否纳入白名单（当前 diag 无命令面，只有串口日志——若无命令则从白名单去掉）；
4. token 与 BLE 同时有效时的 `auth.admin.set` 等：两边都禁（维持 §1 禁止清单）。

## 10. 明确不做（本轮）

- 不做加密/加密传输（物理在场 + 本地口的威胁模型下，明文与 BLE 同级；需要时另立 T-sec）；
- 不做 UART2（板级无空闲引脚规划，UART0+BOOT 解锁已满足场景）;
- 不做动态路由/多串口扩展。
