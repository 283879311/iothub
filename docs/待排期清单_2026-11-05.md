## P2 审计结论（2026-11-05，只读代码 + 真机各一次）

**结论：P2 前提不成立，建议关闭。**

1. **失败收尾已自带恢复**：`app_wifi_tryconnect_finish(result, restore_old=true, old_cfg, …)`
   （`wifi.c` 试连收尾）对所有非 OK 结果都会 `esp_wifi_disconnect()` +
   `esp_wifi_set_config(WIFI_IF_STA, old_cfg)` + 恢复自动连接并调度重连。
   也就是说"试验失败"不会把设备留在候选网络。
2. **唯一可能"got_ip 后失败"的入口是 `store_trial` 返回 false**，而它只在
   `source == BLE && !app_ble_gatts_connected()` 时为 false（`cmd.c` store_trial），
   即 BLE 在 trial 期间掉链——该场景必定先走 `on_ble_disconnect → cancel → cleanup`
   （DEF-MQTT-003 已在 cleanup 里恢复持久配置）。
3. **真机验证**：BLE `network.tryconnect`（真实口令）→ 等 `trial.state == got_ip`
   → 立刻 SIGKILL BLE 客户端（不发 disconnect）→ 12s 后
   `network.status = .50 / cfg_state=static / trial=idle`，无 `.28` 残留。

因此 P2 不需要独立机制；`operation.c` run_fn 失败路径不调 cleanup 是**事实**，
但该路径的运行态已由试连收尾恢复，不构成缺陷。

残余（仅记录，不排期）：`store_trial` 失败时 run_fn 直接置 CANCELLED，
其正确性依赖"掉链必先经过 cleanup"这一前置；若将来新增不经过 cleanup 的清 job
路径，需要重新评估。
