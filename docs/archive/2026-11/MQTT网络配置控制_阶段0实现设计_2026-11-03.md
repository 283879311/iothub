# MQTT 网络配置控制：阶段 0 实现设计（接口治理与事务边界）
> **状态**：ARCHIVED（文档状态标定 2026-11-14，定义与索引见 [docs/README.md](README.md)）


> 状态：**阶段 0 实现已完成主机/编译验证；设备负向测试未执行，未烧写、未操作设备。**
> 依据：`docs/MQTT网络配置控制方案评审回复_2026-11-03.md`（SHA-256 `e9b0b98abbf49eaa800a83c740a11c342d5702e04455174efd39462084283971`）。
> 范围：只做入口治理、owner/cancel、配置互斥、profile 不变量和负向测试设计；**不实现阶段 1 状态机，不开放生产 MQTT 网络控制**。

## 1. 目标与非目标

目标：

1. 封堵 `.async` 外部旁路，同时保留 BLE v1 合法适配路径。
2. 增加 MQTT v1 网络事务入口，生产默认关闭，阶段 2 才开闸。
3. 增加 `APP_OPERATION_OWNER_MQTT`，owner 在事务创建时固定。
4. cancel 同时校验“调用者认证身份 + operation owner”。
5. 网络事务期间所有 `config.set`/profile 删除返回 `busy`。
6. 最后一个可用 profile 不可删除。
7. 新增错误码和 v1 映射。
8. 建立可在主机侧运行的策略/权限测试。

非目标：

- 不新增 `INTERNET_CHECKING`/`MQTT_CONNECTING`/`ROLLING_BACK`/`ROLLED_BACK`。
- 不实现互联网探测、MQTT 验证、自动轮询。
- 不修改 M1/静态 IP 运行逻辑；`ip_mode` 仅定义接口，阶段 1 消费。
- 不执行任何板端测试；设备测试需单独批准。

## 2. 现有入口事实（只读核对）

全仓 `.async` 引用仅 `ble_cmd.c:347-353`（BLE v1 映射）、`cmd.c:1774-1783`（dispatch）和 `cmd.c:543-546`（内部 apply child）；没有其他外部调用点。`app_config_factory_clear_wifi_profiles` 仅 `bootstrap.c:78` 工厂复位调用；普通删除仅 `cmd.c:2171`。

| 入口 | 现状 | 风险 |
| --- | --- | --- |
| BLE v1 | `ble_cmd.c` 将 `network.tryconnect/apply/cancel` 映射为 `.async`，再进 `app_cmd_execute_ex` | 合法适配与外部直调共用 `.async` 字符串 |
| MQTT | `mqtt.c` 只解析 v0 `method/params`；网络方法在 `cmd.c` 被 `guard_rejected` | 无 v1 envelope；开闸没有事务白名单 |
| `.async` | `cmd.c:1774-1783` 直接暴露；apply/cancel helper 无 source 检查 | 外部可绕过 v0 守卫 |
| owner | `operation.h` 只有 INTERNAL/BLE/HTTP；非 BLE 映射 HTTP | MQTT 事务归错属主 |
| cancel | `app_cmd_net_cancel_async` 只查 operation_id/state | 无调用者认证+owner 双重校验 |
| config.set | `cmd.c:1427` 不检查网络事务；快照是整份 config+profiles | 回滚覆盖并发修改 |
| profile 删除 | `config.c:851` 无最后 profile 不变量 | 切换中删掉回滚目标 |

## 3. 设计

### 3.1 命令策略模块（纯逻辑，可主机测试）

新增 `main/cmd_policy.h/.c`，不依赖 Wi-Fi/MQTT，只接收：

- `app_cmd_context_t`（source/origin/exec_env/auth_level）
- method 字符串
- 解析后的参数摘要（是否 net/MQTT 域、是否 `.async`）

策略结果：`ALLOW`、`FORBIDDEN`、`BUSY`、`INVALID_ARGUMENT`、`NOT_ENABLED`。

规则：

1. `exec_env==ENTRY` 且 method 以 `.async` 结尾：一律拒绝；只有内部 child 可执行 `.async`。
2. 外部入口的 `source=UNKNOWN/TOUCH/SERIAL`：网络事务方法拒绝。
3. MQTT：只允许 `network.status`、`network.tryconnect`、`network.apply`、`network.cancel`、`operation.get`；`network.scan/restart/profile.delete`、`config.set` 的 net/MQTT/BT/UART/admin 域拒绝。
4. BLE/HTTP：保持现有命令集合，但 `config.set` 受事务门控。
5. `.async` 不再作为适配层入口；适配层直接调用 3.2 的内部 API。

### 3.2 协议适配层边界

新增内部 API（`main/cmd_net_adapter.h`，实现留在 `cmd.c`）：

```c
esp_err_t app_cmd_net_tryconnect_adapter(const app_cmd_context_t *ctx,
                                         const cJSON *args,
                                         cJSON **resp, const char **err);
esp_err_t app_cmd_net_apply_adapter(const app_cmd_context_t *ctx,
                                    const cJSON *args,
                                    cJSON **resp, const char **err);
esp_err_t app_cmd_net_cancel_adapter(const app_cmd_context_t *ctx,
                                     const cJSON *args,
                                     cJSON **resp, const char **err);
```

- BLE v1 适配层在归一化 `cmd/args` 后，对三个网络方法直接调用上述 API，不再构造 `network.apply.async` 字符串。
- MQTT v1 适配层同样直接调用；v0 MQTT 网络方法维持 `guard_rejected`。
- 适配层构造 `app_cmd_context_t`：`source/origin=BLE|MQTT`、`exec_env=ENTRY`、`auth_level=LOCAL_TOKEN`（BLE token 已验证 / MQTT broker 会话已认证）。
- `app_cmd_execute_ctx` 的 `.async` 分支只接受 `exec_env==INTERNAL`；外部直调返回 `forbidden`。这保留内部测试/内部 child 能力，不保留外部旁路。

### 3.3 MQTT v1 入口与特性门

- `mqtt.c` 增加 envelope 识别：存在 `version:"1.0"` 时解析 `id/cmd/args`；否则保持现有 v0 `method/params`。
- 阶段 0 的 v1 适配只覆盖网络方法：`network.status/tryconnect/apply/cancel`、`operation.get`；其他 v1 命令返回 `unknown_command`，不扩面。
- 响应统一 `{id, ok, result|error{code,message}}`；v0 响应保持 `{success,...}`。
- 编译开关 `APP_CMD_MQTT_NET_TXN_ENABLE` 默认 **0**：
  - 阶段 0 生产构建：MQTT 网络事务方法返回 `forbidden`（接口已 v1 化但未开闸）；
  - 阶段 0 测试构建：置 1，并同时定义 `APP_CMD_MQTT_NET_TXN_TEST_BUILD=1`；未定义测试标记却置 1 时用 `#error` 拒绝编译；
  - 测试构建必须在诊断信息/版本字符串中带 `mqtt_net_txn=test`，生产构建必须带 `mqtt_net_txn=off`；
  - 阶段 2 评审通过后才在正式构建置 1；不提供任何运行时命令开关。

### 3.4 owner 模型

- `app_operation_owner_t` 增加 `APP_OPERATION_OWNER_MQTT`。
- `app_operation_start` 的 owner 由适配层显式传入；不得从请求 JSON 读取。
- owner 在 operation 创建后不可变；`app_operation_status_t` 已携带 owner。
- `app_cmd_net_on_ble_disconnect` 只取消 `owner=BLE`；MQTT owner 的 trial/幂等键/终态不因 BLE 断开变化。
- `app_operation_find_by_key(owner, key)` 按 owner 隔离 MQTT 与 BLE/HTTP 幂等键。

### 3.5 cancel 双要素校验

新增纯函数：

```c
bool app_cmd_cancel_allowed(const app_cmd_context_t *ctx,
                            app_operation_owner_t owner);
```

规则：

| 调用者（可信身份） | owner | 结果 |
| --- | --- | --- |
| 已认证 BLE | BLE / MQTT / HTTP | 允许 |
| MQTT | MQTT | 允许 |
| MQTT | BLE / HTTP | 拒绝 |
| HTTP | HTTP | 允许 |
| HTTP | BLE / MQTT | 拒绝 |
| 未认证/UNKNOWN/TOUCH/SERIAL | 任意 | 拒绝 |

- 调用者身份取 `ctx->source` + `ctx->auth_level`，不取 JSON 字段。
- owner 取 operation 结构内的不可变字段，不取当前连接来源。
- 跨 owner 返回 `forbidden`；未认证返回 `unauthorized`。
- `network.cancel.async` 只允许 internal child；适配层直接调用 API。

### 3.6 配置事务门控

新增 `main/cmd_cfg_txn.h/.c`：

```c
typedef struct { uint32_t token; } app_cmd_cfg_txn_t;
bool app_cmd_cfg_txn_begin(app_cmd_cfg_txn_t *out);      /* 开网络事务 */
void app_cmd_cfg_txn_end(app_cmd_cfg_txn_t token);
bool app_cmd_cfg_txn_guard_enter(void);                  /* config.set/profile.delete */
void app_cmd_cfg_txn_guard_exit(void);
```

- **不新增独立长持锁**：`active` 与 token 状态由现有递归 `app_config_lock` 保护；避免新增“cfg_txn 锁 → NVS”的长持有链。
- `begin()`：取 config 锁，检查 active，生成新 token 并置 active，释放；`end(token)`：取 config 锁，匹配 active+token 才清除。
- 网络 operation 创建后、任何配置快照前 `begin()`；终态/cleanup `end(token)`。
- 同步 `network.tryconnect` trial 从试连开始持有 token，直到 trial apply/cancel/expire；trial 结构保存 token。
- `config.set` 与 `network.profile.delete`：取 config 锁，检查 active；若 active 返回 `busy`；否则在同一锁内完成 patch/profile 保存/删除，再释放。NVS 写入沿用 config.c 现有锁路径，不新增锁层。
- 持锁期间不得调用 Wi-Fi API、MQTT API、回调或任何可能重入的网络栈操作；NVS 是现有配置路径，阶段 0 不扩大其阻塞范围。
- 事务期间 `CFG_EFFECT_REBOOT` 也被 `config.set` 门控挡住，避免重启丢 operation。
- 锁序保持现有的 **config 锁 → NVS**；网络 job 锁内调用 begin/end 时只取 config 锁，不反向取 job 锁。

### 3.7 profile 不变量与全量清空语义

**只读调用点核对结果：**

| 调用点 | 语义 | 处理 |
| --- | --- | --- |
| `main/bootstrap.c:78` `app_factory_reset_to_defaults` | 工厂复位显式清空 | 允许；这是唯一合法的全量清空入口 |
| `main/cmd.c:2171` `network.profile.delete` | 普通删除 | 删除后必须 ≥1 个可用 profile，否则 `last_profile` |
| `main/config.c:851` `app_config_delete_wifi_profile` | 普通删除实现 | 在 config 层做计数不变量，不能只靠命令层 |
| `main/config.c:959` `app_config_snapshot_restore` | 事务回滚恢复到快照 | 允许恢复空快照，但仅限同一事务且快照原本为空；不属于普通删除 |
| `main/config.c:346-355` invalid blob / load | 损坏恢复 | 允许重置为空并告警；不是用户删除路径 |
| `main/config.c:359` `app_config_store_wifi_profiles_blob` | 底层写 blob；`count==0` 时 erase key | 内部函数，必须由上述明确语义的调用方使用；普通删除不得传入空 blob |

**不变量：**

1. 普通删除（`app_config_delete_wifi_profile`）：加载后统计有效 profile；目标存在且总数 ≤1 时返回 `ESP_ERR_INVALID_STATE`，命令层映射 `last_profile`。
2. 工厂复位（`app_config_factory_clear_wifi_profiles`）：独立语义，允许清空；仅 `bootstrap.c` 工厂复位路径调用。阶段 0 将其重命名为 factory-only API 并加注释，禁止从命令/恢复路径调用。
3. 损坏 blob 恢复：允许初始化空 profiles 并告警；不得静默把“空”当成用户删除成功。
4. 快照回滚：允许恢复快照中的空列表，但必须由同一事务的 `snapshot_restore` 触发；普通删除不得通过 `app_config_store_wifi_profiles_blob(count=0)` 绕过。
5. `network.profile.delete` 同时受 3.6 门控；事务期间返回 `busy`。

**实现注意：** 如果后续需要“恢复默认配置”命令，必须新增独立语义和单独评审，不能复用普通删除，也不能直接暴露 `app_config_factory_clear_wifi_profiles`。

### 3.8 错误码

内部：

- `APP_OPERATION_ERR_MQTT_UNAVAILABLE`
- `APP_OPERATION_ERR_INTERNET_UNVERIFIED`
- `APP_OPERATION_ERR_STATIC_IP_PINNED`
- `APP_OPERATION_ERR_LAST_PROFILE`

### 3.9 内部调用身份与 token 生命周期（评审补充）

**A. 内部调用身份必须可信：**

- adapter API 的 `app_cmd_context_t` 只能由协议适配层在进程内构造；不得从客户端 JSON 读取 `source`、`owner` 或 `exec_env`。
- `exec_env=INTERNAL` 不是“全放行”标记：`.async` 分支还要校验 origin（BLE/MQTT/HTTP）、method 在内部 allowlist、depth 合法；不满足即拒绝。
- 请求 JSON 中出现 `source`/`owner`/`exec_env` 字段一律忽略或按未知字段拒绝，绝不参与授权。
- 内部 child 只允许执行 `network.apply`（trial 提交）等明确定义的内部命令，不允许通过 `.async` 扩大命令面。

**B. `cmd_cfg_txn` token 生命周期：**

1. 每次成功 claim 生成新的单调 token。
2. release 必须同时匹配 `active` 状态和 token。
3. token 不匹配时不改变当前事务状态，只记录告警。
4. 事务结束、取消、超时、启动失败和异常 cleanup 都必须有确定释放路径；释放函数幂等。
5. 所有配置写入入口（`config.set`、`network.profile.delete`、未来新增的配置写命令）必须经过同一门控。
6. 门控状态由 `app_config_lock` 保护，不新增 cfg_txn 独立锁；锁序保持 `config → NVS`。持锁期间不得调用 Wi-Fi API、MQTT API、回调或任何可能重入的网络栈操作；NVS 沿用现有路径，不扩大阻塞范围。

**C. 阶段 0 不提前实现阶段 1：**

- 不增加 `INTERNET_CHECKING`/`MQTT_CONNECTING`/`ROLLING_BACK`/`ROLLED_BACK`。
- 不实现互联网探测、MQTT 验证、自动轮询、回滚状态机。
- 生产构建 `APP_CMD_MQTT_NET_TXN_ENABLE=0`；阶段 0 只允许测试构建置 1，且必须能从构建配置/诊断信息识别为测试版本，不提供运行时开关。
- 阶段 0 只保证“入口可治理、owner 可判定、配置不被并发写坏、profile 不被删空”。
