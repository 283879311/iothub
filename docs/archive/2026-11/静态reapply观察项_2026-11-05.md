# 运行期 re-apply 静态不生效：只读核查（2026-11-05）

> 现象：持久配置为静态 .50，但 `network.reconnect`（wifi_restart 运行期 re-apply）后运行时 IP 仍为 DHCP .28；`effect=reboot`（芯片重启）后静态正常生效。
> 结论：**恢复链 DHCP 救援接管，静态 re-apply 失败原因需串口复现确认；此行为非 v1 迁移引入。**

## 1. 只读链路核查（wifi.c）

1. `app_wifi_schedule_restart()`（`wifi.c:3487`）→ `wifi_restart` 任务（`wifi.c:3438`）→ `app_wifi_build_cfg_from_config()`（`wifi.c:2196`，从 `s_config` 读 `sta_use_static=true` + 静态字段）→ `app_wifi_apply_cfg()`。
2. 静态阶段（`app_configure_sta_static_ip`，`wifi.c:625`）：`dhcpc_stop`（ALREADY_STOPPED 已豁免）→ `set_ip_info` → DNS。任一失败 → 失败返回。
3. 失败后走恢复链（`app_wifi_recover_from_apply_failure`，`wifi.c:3004`）：
   - ① LKG 恢复：仅当 LKG 有效且**与失败候选不同**（`app_wifi_lkg_equals`，`wifi.c:2224`）；
   - ② DHCP 救援：同 SSID 降级 DHCP，不改 NVS，`cfg_state=fallback`。

## 2. 本轮现象与恢复链吻合

- N06 事务前 LKG = 静态 .50（之前成功应用）；re-apply 候选 = 静态 .50 → `lkg_equals=true` → **跳过 LKG 恢复**；
- 直接 DHCP 救援 → .28，`cfg_state=fallback`。与观测完全一致。
- 而此前 `.50→.51→.50` 的 config.set 走 `effect=reboot`（芯片重启，boot apply），不经过该恢复链，所以静态生效。

## 3. 【2026-11-05 取证完成】失败阶段定位：stage=wifi_start（STA_START 事件未投递）

BLE v1 触发 `network.reconnect`，全程串口捕获（`reapply_serial_evidence.log`）：

```
I (710934) wifi: apply_begin mode=static source=runtime_restart
I (710944) wifi:state: run -> init               ← esp_wifi_stop，STA 断开
I (710984) wifi: STA down with BLE connected: event-chain retry suppressed;
            120s formal-only monitor owns recovery
I (711044) wifi: static ip configured: ip=192.168.1.50 ...   ← 静态阶段全部成功
I (711044) wifi: apply_await_start gen=2
I (711054) wifi:mode : sta (b0:a7:32:28:c8:e4)   ← esp_wifi_start 返回 OK
I (711324) wifi: ble fast retry: first attempt in 120000ms
E (713154) wifi: apply_start_timeout gen=2, gate stays closed   ← 2.1s 无 STA_START
E (713154) wifi: apply_failed stage=wifi_start err=ESP_ERR_TIMEOUT mode=static attempt=2
W (713154) wifi: recover action=dhcp_rescue begin
I (713184) wifi: apply_await_start gen=3
I (713494) wifi: apply_start_released gen=3       ← 救援(DHCP) 310ms 即收到 STA_START
I (713494) wifi: net_config_state=fallback
```

**结论：**

1. 静态配置阶段（parse/dhcpc_stop/set_ip/dns）全部成功，与代码审查一致；
2. 失败点是 `stage=wifi_start`：`esp_wifi_start()` 返回 OK，但 `WIFI_EVENT_STA_START` 2s 内未投递；
3. 对照组：紧随其后的 DHCP 救援（gen=3）在**同样 BLE 连接**下 310ms 收到 STA_START；
4. 窗口内两个可疑共存因素：MQTT 客户端正在 stop（STA down 触发）+ BLE 共存调度；gen=3 时 MQTT 已停止完毕；
5. `APP_WIFI_START_WAIT_MS=2000`（`wifi.c:96`）在此场景不够，或 IDF 6.0.3 coexist 下 stop→start 快速序列的 STA_START 被延迟/丢失。

**复现条件**：BLE 已连接 + 运行期 re-apply（static）→ STA_START 超时概率性发生（本轮 2 次复现：MQTT 回归后 reconnect、本次取证）。

**修复方向（待评审，不动代码）：**

1. `stage=wifi_start` 超时后**先重试一次 start**（stop→start 一次）再判失败——当前直接进恢复链，把"事件迟到"放大成"静态被 DHCP 救援降级"；
2. 或延长等待 + 在 STA_START 缺失时轮询 `esp_wifi_get_status`；
3. 恢复链兜底改进：`lkg_equals(failed)`（候选==LKG==持久配置）时重试候选而非直接 DHCP 降级；
4. 客户端可见性：`network.status` 暴露 `cfg_state`（static/dhcp/fallback）。

设备已恢复：dns2 flip-flop 两次 reboot → 静态 .50、MQTT 在线、配置与测试前一致。

## 4. 建议修复方向（待根因确认后评审）

1. 若 `set_ip_info` 在连接态失败：apply 静态阶段先 disconnect 再配置（boot 路径本来就是断开态，所以只有运行期 re-apply 暴露）。
2. 恢复链①跳过条件加例外：`lkg_equals(failed)` 时若失败候选==LKG==持久配置，重试一次静态而非直接 DHCP 救援（避免“静态配置被自己的救援永久降级”）。
3. `network.status` 增加 `cfg_state`（static/dhcp/fallback/offline）暴露，便于客户端区分“持久静态、运行时救援”。

## 5. 影响

- 不影响 v1-only 迁移结论；属 M1 运行期恢复链的既有行为（v1 之前亦如此）。
- 实际风险：静态设备运行期 `network.reconnect`/apply 后 IP 变 .28 且不重启不恢复；MQTT 若指向同网段静态规划地址会失联（本轮 TB 是公网地址所以 MQTT 仍在线）。
