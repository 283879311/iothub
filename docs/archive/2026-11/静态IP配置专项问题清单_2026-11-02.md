# 静态 IP 配置专项问题清单（2026-11-02）

> **2026-11-04 历史边界**：本文记录 v0 `config.set` 时代的静态 IP 问题；当前 v1-only 合同已改为 BLE v1 `config.set`（`args.patch` 允许 network/static 域）。命令示例仅作历史证据，不要照抄。


> 状态：**审计完成，尚未修改代码。**  
> 本文是独立工作项，不并入已冻结的 tryconnect 功能补丁。  
> 源码基线与 tryconnect 补丁相同：`main/wifi.c`、`main/cmd.c`、`main/config_apply.c`、`main/config.c`、`main/ble_cmd.c`。

---

## 0. 本次失败分类

65D8 的 v0 `config.set` 请求启用了静态 IP，但没有提供 `sta_static_ip`，设备在配置校验阶段明确拒绝：

```text
I (35953) ble_cmd: rx method=config.set id=-1
W (35963) cfg_apply: reject net patch: sta_static_ip required when static IP enabled
```

归类：

**`CONFIG_VALIDATION_REJECTED`**

不是：

- Wi-Fi 连接超时；
- MQTT 连接失败；
- 配置已应用但网络不可达；
- 设备没有执行配置。

客户端显示的“写入失败/等待超时”是上层表现，设备侧实际是同步拒绝。

---

## 1. 接口层（P1）

### 1.1 v1 `config.set` 明确禁止 network 域

- `main/ble_cmd.c:307`：`config.set` 在 v1 允许列表。
- `main/ble_cmd.c:614-620`：patch 中出现任何 `CFG_DOMAIN_NET` 字段，v1 直接返回：

```json
{"ok":false,"error":{"code":"invalid_argument","message":"invalid_argument"}}
```

因此 v1 无法设置静态 IP。`config.get` 可以读静态字段（`main/cmd.c:1054-1059`），但 `config.set` 不能写，接口读写不对称。

### 1.2 当前唯一入口是 v0 `config.set`

v0 请求：

```json
{
  "id": 1,
  "method": "config.set",
  "params": {
    "sta_use_static": true,
    "sta_static_ip": "192.168.1.50",
    "sta_static_gateway": "192.168.1.1",
    "sta_static_netmask": "255.255.255.0",
    "sta_static_dns1": "192.168.1.1"
  },
  "token": "..."
}
```

问题：

- App 若使用 v1 `config.set`，会在适配层被拒绝；
- App 若使用 v0，必须自己拼完整字段；
- 当前错误码到 App 的展示没有区分“配置校验失败”和“网络/超时”。

### 1.3 静态字段

| 字段 | 必填条件 | 说明 |
| --- | --- | --- |
| `sta_use_static` | 启用静态时 true | network 域，effect=reboot |
| `sta_static_ip` | 启用静态时必填 | 不能为空，不能是 0.0.0.0 |
| `sta_static_gateway` | 启用静态时必填 | 不能为空，不能是 0.0.0.0 |
| `sta_static_netmask` | 启用静态时必填 | 不能为空，不能是 0.0.0.0 |
| `sta_static_dns1/2` | 可选 | 非空时必须是合法 IPv4 |

字段表见 `main/config_apply.c:487-508`。

## 2. 校验层（P1）

### 2.1 当前已有的校验

`cfg_validate_static_ip_cross()`（`main/config_apply.c:242-285`）只检查：

- 启用静态时 IP/网关/掩码非空；
- 三者都是合法 IPv4 且非 0.0.0.0；
- DNS 非空时是合法 IPv4。

### 2.2 缺失的语义校验

- 掩码是否连续合法（例如 `255.0.255.0` 当前只按 IPv4 语法接受）；
- 网关是否与设备 IP 同一子网；
- 设备 IP 是否是网络地址/广播地址；
- 设备 IP 是否等于网关；
- IP 是否落在当前 DHCP 池内（设备侧无法知道 DHCP 池，需要产品/部署约束）；
- DNS 是否与当前网络可达（只能运行时验证，不应在配置层硬拒绝）。

**风险**：当前可以保存一组语法合法但不可通信的静态参数。

### 2.3 `empty_keeps` 语义

静态字符串字段带 `.empty_keeps = true`（`main/config_apply.c:489-508`），`cfg_apply` 中空串表示保持旧值（`main/config_apply.c:643-645`）。

后果：

- 启用静态时，如果 App 省略 `sta_static_ip`，而旧值也是空，跨字段校验拒绝；
- 如果旧值非空，App 发空串不会清空，而是静默保留旧值；
- 不能用空串清除单个静态字段；应通过 `sta_use_static=false` 或明确的字段清空语义处理。

## 3. 运行时层（P1）

### 3.1 DHCP/静态切换顺序

`app_apply_wifi_config()`（`main/wifi.c:1884-1963`）：

1. `esp_wifi_stop()`；
2. 清运行时 Wi-Fi 状态；
3. `esp_wifi_set_mode(WIFI_MODE_STA)`；
4. `esp_wifi_set_config(WIFI_IF_STA, ...)`；
5. 静态分支调用 `app_configure_sta_static_ip()`；
6. `esp_wifi_start()`。

`app_configure_sta_static_ip()`（`main/wifi.c:539-594`）：

1. 读取静态字段；
2. `esp_netif_dhcpc_stop()`；
3. `esp_netif_set_ip_info()`；
4. 仅在 DNS 字符串非空时 `esp_netif_set_dns_info()`；
5. 返回。

问题：

- `esp_netif_dhcpc_stop()` 失败只告警，仍继续 `set_ip_info`；
- `esp_netif_set_dns_info()` 返回值未检查；
- 从静态切回 DHCP 时，没有显式清理旧的静态 DNS；
- 从 DHCP 切静态且新 DNS 为空时，旧 DNS 可能残留；
- 需要确认静态 IP 路径是否会触发 `IP_EVENT_STA_GOT_IP`，否则 `s_wifi.sta_connected/sta_has_ip` 和 ARP 冲突检测都不会启动（源码目前依赖该事件，未显式注入事件）。

### 3.2 静态 IP 与 tryconnect 没有互锁

`app_wifi_try_connect_common()`（`main/wifi.c:2057+`）只切换候选 SSID/口令，不修改 netif 的静态 IP/DHCP 状态。

风险：

- 静态 IP 已启用时调用 `network.tryconnect`，候选连接会继承当前静态 netif；
- 候选不是 DHCP，可能拿不到该候选网络的有效 IP，或误用旧网段地址；
- 当前没有在 tryconnect 入口明确拒绝或强制 DHCP trial。

**建议**：静态 IP 模式下明确拒绝 `network.tryconnect`，或为 trial 明确定义“临时 DHCP”语义；不要在未定义时继续使用当前 netif。

### 3.3 DNS 残留

`main/wifi.c:580-587` 只在 DNS 非空时设置 MAIN/BACKUP，没有空值清理。

建议：

- 静态 DNS 为空时，显式清空 MAIN/BACKUP；
- 切回 DHCP 后确认 DHCP 下发的 DNS 覆盖旧值；
- 增加切换后的 DNS 读取校验。

## 4. 恢复层（P0/P1）

### 4.1 启动期静态配置失败可能 abort/重启循环（P0）

启动路径：

```c
/* main/wifi.c:2385 */
ESP_ERROR_CHECK(app_apply_wifi_config());
```

`app_apply_wifi_config()` 在以下情况返回错误：

- `esp_wifi_stop/set_mode/set_config/start` 失败；
- `app_configure_sta_static_ip()` 解析或 `esp_netif_set_ip_info()` 失败。

`ESP_ERROR_CHECK` 会 abort，可能导致设备反复重启。静态配置属于持久化配置，一旦保存了运行时无法应用的参数，恢复只能依赖 BLE/重新烧写。

**这比“静态 IP 配错后上不了网”更严重，应作为 P0 修复。**

### 4.2 配置保存无回滚

`config_apply_patch()` 先保存 NVS 再更新内存（`main/config_apply.c:837-843`），NET 域的 apply 是空操作（`main/config_apply.c:698-700`），由上层按 `CFG_EFFECT_REBOOT` 重启。

`config.set` 响应固定：

```json
{"saved":true,"applied":false,"restart_required":true,"rollback":"none"}
```

（`main/cmd.c:1238-1250`）

没有：

- 旧配置持久化快照；
- pending/candidate 状态；
- 启动后验证失败自动回滚；
- 断电恢复路径。

### 4.3 IP 冲突检测不可见

`app_sta_ip_conflict_check_task()`（`main/wifi.c:397-449`）在 `IP_EVENT_STA_GOT_IP` 后、`sta_use_static` 时启动：

- 对自身 IP 发 3 次 ARP 请求；
- 等待约 1s；
- 如果 ARP 条目 MAC 不是自身 MAC，置 `s_wifi.sta_ip_conflict=true`；
- 不改变连接、不自动断开、不回退 DHCP。

关键问题：

- `network.status` 构建函数（`main/cmd.c:643-715`）**没有输出 `sta_ip_conflict`**；
- 也没有 `sta_use_static`、静态 IP/gateway/netmask/DNS 或 `network_config_state`；
- 注释说“状态接口透出”，实际未实现；
- `esp_wifi_get_mac()` 失败时，只要有 ARP 条目就会被判冲突（`main/wifi.c:429-433`）；
- 没有区分 `unknown/clear/conflict`，App 无法知道“尚未检测”；
- 冲突后没有动作，只留下一个不可见标志。

## 5. 建议的修复顺序

### P0：先保证不会失联/重启循环

1. 移除静态配置失败路径上的 `ESP_ERROR_CHECK` abort；启动时失败应保留 BLE 救援并进入明确失败状态。
2. 静态配置保存前做完整语义校验（掩码连续、网关同网段、IP 不是网络/广播/网关地址）。
3. 静态模式下拒绝或明确隔离 `network.tryconnect`。
4. 统一 DNS 设置/清理，切换静态/DHCP 时验证 DNS。
5. 为静态配置设计持久化 pending/回滚，至少保证启动失败能恢复旧配置或安全 DHCP。

### P1：运行时可观察性和事务

1. `network.status` 增加：
   - `sta_use_static`
   - `sta_gateway`
   - `sta_netmask`
   - `sta_dns`（main/backup）
   - `sta_ip_conflict`: `unknown/clear/conflict`
   - `network_config_state`: `dhcp/static/pending/fallback`
2. 明确 ARP 检测时机、超时和误报处理；未检测返回 `unknown`，不能默认 `false`。
3. 静态配置失败的回滚/回退状态进入 status 和日志。
4. 客户端把 `invalid_config` / `invalid_argument` 映射为配置校验失败，不要显示 Wi-Fi/MQTT 超时。

### P2：接口补齐

1. 为 v1 增加明确的静态 IP 命令，或明确文档说明“静态 IP 仅 v0”；
2. 如果继续使用 v0 `config.set`，在 App 侧做字段完整性预校验；
3. 记录重启后的预期 IP、网关、DNS 和验证结果。

## 6. 需要独立验证的技术问题

以下不能只靠代码推断，需板级/IDF 行为验证：

1. `esp_netif_set_ip_info()` 在静态路径是否触发 `IP_EVENT_STA_GOT_IP`；若不触发，状态和冲突检测都不会启动。
2. `esp_netif_dhcpc_stop()` 失败后继续 `set_ip_info` 的实际行为。
3. 静态 DNS 置空后，`ESP_NETIF_DNS_MAIN/BACKUP` 是否真的清空。
4. 静态↔DHCP 切换后 DNS 是否残留。
5. ARP 冲突检测的误报率（代理 ARP、网关/交换设备响应、自身 MAC 获取失败）。
6. 静态配置重启后 `ESP_ERROR_CHECK` 失败是否导致重启循环。
7. 静态 IP 下 `network.tryconnect` 的实际候选 IP 来源和结果。
8. 断电发生在“保存成功、重启前/重启后”时的恢复行为。
