## 0. 结论先行

| 项 | 选择 |
| --- | --- |
| 主机 | **复用现有云主机 `139.9.93.245`**（已跑 ThingsBoard，21883 被占） |
| 端口 | **21884**（与 TB 的 21883 错开一格，误配端口会落回生产 TB 而不是黑洞） |
| broker | **mosquitto 2.x**（替代 amqtt；amqtt 有"连接槽耗尽"历史，见 §8）；**单容器 EMQX 亦可，且调试期更强，见 §13** |
| 加密 | 本期**不开 TLS**（固件用 `esp_crt_bundle_attach`，只能校验公网 CA + 主机名，需域名；见 §10） |
| 鉴权 | MQTT 层**匿名**，靠**云安全组 + ufw 做源 IP 白名单**（原因见 §2，固件只发 username 不发密码） |

一次执行时间约 20 分钟，其中 15 分钟是等安全组生效和装包。

---

## 1. 为什么这样能解决，边界在哪

**能解决**：现在的故障是设备发 SYN 到 PC，PC 的无线网卡在省电态把 inbound 丢了（本项目已复现多次，`nmcli ... powersave 2` 可即时缓解）。设备改成连云主机后，链路是 `设备 → 路由器 NAT → 公网 → 云主机`，**完全不再经过 PC 的无线网卡**，省电问题自然消失。

**不能解决**（别指望它）：
- **DEF-SCAN-001 的 0x222 断链**——那是 WiFi 扫描与 BLE 共存抢射频，属 BLE 侧，跟 broker 在哪无关；
- **BLE 侧的一切问题**（空闲回收、订阅态僵尸）同理；
- **PC 侧测试工具仍走本机网络**，但那是**出站**连接，省电丢包主要影响 inbound，实际不受影响。真正的限制是 PC 休眠时测试就断了——长测仍建议在有电源策略的机器上跑。

---

## 2. 两个来自固件的硬约束（决定了配置长什么样）

以 `main/mqtt.c` 为准：

1. **设备只发 username，不发密码**（`mqtt.c:1683-1684`：`credentials.username = s_config.mqtt_token`，全文件无 `credentials.password`）。
   → broker 若要求"用户名+密码"，设备**必然连不上**。mosquitto 因此在 MQTT 层开 `allow_anonymous true`，靠网络 ACL 收口。
2. **TLS 只能校验公网 CA**（`mqtt.c:1681-1683`：`crt_bundle_attach`），无法注入自签 CA、也不会跳过校验。
   → 想开 TLS 必须有**域名 + 公网证书（Let's Encrypt）**，用 IP 直连会因主机名不匹配握手失败。本期先明文（测试网络、非生产数据）。

其它相关参数：keepalive 45s、`network.timeout_ms=5000`、客户端内建自动重连**已关闭**，由应用层指数退避（200ms→1→2→4→8→16→30s）承担。→ **broker 重启后，设备最迟约 30s 自愈**，这条可当验收项。

## 3. 步骤 A：云主机侧准备

```bash
# 1) 登录云主机，确认 21884 没被占用
sudo ss -ltnp | grep -E ':(21883|21884)\b'
#   期望只看到 21883（ThingsBoard）

# 2) 记录本机公网出口 IP（用于安全组白名单；在「现场那台 PC」上执行）
curl -s https://ifconfig.me; echo
```

**云控制台安全组**只加一条入站：

| 方向 | 协议 | 端口 | 源 | 说明 |
| --- | --- | --- | --- | --- |
| 入站 | TCP | 21884 | `<现场出口 IP>/32` | 只放行跑测试的这条宽带 |

不要开 `0.0.0.0/0`：MQTT 层是匿名的，谁连上谁能给设备下发 RPC。若出口 IP 是动态的（家宽常见），两个选择：
- 用 DDNS 脚本每 5 分钟比对一次并调云 API 更新安全组（云厂商都有 API）；
- 或者退一步：换非默认端口 + 匿名，仅测试期开启，测完关规则（**别长期裸奔**）。

## 4. 步骤 B：装 broker（一条命令）

把 `tools/broker_cloud/` 三个文件传到云主机，然后：

```bash
cd broker_cloud
sudo BROKER_PORT=21884 ALLOW_CIDR=<现场出口IP>/32 bash install_broker.sh
```

脚本做的事（幂等，可重跑）：装 mosquitto → 覆盖 `/etc/mosquitto/mosquitto.conf`（**去掉默认 1883 监听**）→ `Restart=always` → 装 2 分钟健康检查 timer（连续 3 次探测失败才重启，避免抖动）→ 可选写 ufw → 自检。

关键配置（`mosquitto_iothub.conf` 摘要）：

```conf
listener 21884 0.0.0.0
allow_anonymous true          # 因为设备不发密码，见 §2
max_connections 64
max_queued_messages 500
persistence false             # 测试 broker 不需要落盘
sys_interval 10               # 供 smoke 读 $SYS/broker/uptime
```

> **不要给这个 listener 加 `password_file`**：一旦要求密码，设备（无密码）就登不上，而报错只会是 `not authorized`，很容易误判成"网络不通"。

## 5. 步骤 C：验证（本机或云端都行）

```bash
bash tools/broker_cloud/smoke_mqtt.sh 139.9.93.245 21884 <设备当前的token>
```

五项全 PASS 才算过：

| # | 检查 | 失败含义 |
| --- | --- | --- |
| 1 | TCP 可达 | 安全组/ufw/监听地址 |

| 5 | `v1/devices/me/telemetry` 回环 | TB 主题正常（设备 backend=tb_selfhost 走这条） |

## 6. 步骤 D：把设备指过去（BLE，小程序 mqttcfg 页）

设备当前：`backend=tb_selfhost`、`host=139.9.93.245`、`port=21883`、`use_tls=false`。

1. 小程序「设备页 → MQTT 配置」，**只改端口**（host 本来就是这台云主机）：
   - `host`：`139.9.93.245`（不变）
   - `port`：`21884`
   - `use_tls`：关
   - `token`：留空 = 保留原值（固件 `empty_keeps`）
2. 保存 → 看返回：`saved=true`、`applied=true`；若 `restart_required=true` 就按提示重连一次。
   （v1 `config.set` 的 `mqtt_port` 走 `args.patch`，页面已做差异下发。）
3. **串口判据**（这两行出现即成功）：

```
I (xxxx) mqtt: Starting MQTT: uri=mqtt://139.9.93.245:21884, client_id=..., token_len=N, tls=no, will=v1/devices/me/attributes
I (xxxx) mqtt: MQTT connected: subscribed RPC + shared attrs, requested initial attrs
```

失败常见形态：`Error transport connect`（安全组没放行/源 IP 不符）、`not authorized`（误加了密码认证）、URI 里还是 21883（patch 未生效）。

> 若设备现在指向的是 `117.131.99.2:21883`（历史配置），那 host 也要改成云主机 IP——`config.set` 时同时下发 `mqtt_host` + `mqtt_port`。

## 8. 为什么换 mosquitto 而不是把 amqtt 搬上去

| 项 | mosquitto | amqtt（现用） |
| --- | --- | --- |
| 连接槽可靠性 | 稳定长跑 | **有过"残留进程连接槽耗尽"记录**（`v0彻底删除_设备验收报告` §5：3 小时未重启后设备连不上，重启即愈） |
| 部署 | 系统包 + systemd | venv + yaml + 自写启动 |
| 认证扩展 | 插件/ACL | 更灵活，但本期用不上 |
| 6h soak 适配 | 无需干预 | 建议加"每日定时重启"兜底 |

要沿用 amqtt（例如脚本依赖其行为）也可以：把 `broker.yaml` 放 `/opt/iothub-amqtt/`、venv 装同版本、systemd `Restart=always`，**并加一条 `OnCalendar=*-*-* 04:00:00` 的每日重启 timer**，规避连接槽泄漏。端口同样用 21884。

## 10. 以后要加密（附录，需要域名）

前提：有域名解析到该云主机（Let's Encrypt 不给 IP 签发）。

```bash
# 云主机
apt-get install -y certbot
certbot certonly --standalone -d mqtt.example.com        # 8883/80 需临时放行 80
cat >> /etc/mosquitto/mosquitto.conf <<'EOF'
listener 8884 0.0.0.0
certfile /etc/letsencrypt/live/mqtt.example.com/fullchain.pem
keyfile  /etc/letsencrypt/live/mqtt.example.com/privkey.pem
EOF
systemctl restart mosquitto
# 证书续期后自动重载
echo 'deploy-hook "systemctl reload mosquitto"' > /etc/letsencrypt/renewal-hooks/deploy/mosquitto.sh
chmod +x /etc/letsencrypt/renewal-hooks/deploy/mosquitto.sh
```

设备侧：`host=mqtt.example.com`、`port=8884`、`use_tls=开`（`crt_bundle` 会校验证书链与主机名，域名必须一致）。⚠ 开 TLS 后固件任务栈从 4096 升到 6144（`mqtt.c:1674`），常驻堆多 2KB，当前余量偏紧，需在预算里确认。

## 12. 运维注意

- **日志**：`/var/log/mosquitto/mosquitto.log`，加 logrotate（daily、rotate 7、`copytruncate`），避免 6h soak 撑爆磁盘。
- **连接数**：`max_connections 64`；异常增长通常是测试脚本没 `disconnect`（历史坑）。
- **不要开放 1883/21883 以外的默认端口**，测试期结束立即收缩安全组。
- **别让安全组规则长期挂在 `0.0.0.0/0`**——匿名 broker + 公网 = 任何人都能给设备下发 RPC 命令。

## 13. 备选：单容器 EMQX（结论：**能提供完整测试环境**，且调试期比 mosquitto 好用）

一句话结论：**broker 层完整够用**，且开箱即可接受设备的"仅用户名"连接——EMQX 5 在**未配置任何认证器时默认放行所有客户端**；本方案再显式关一次 listener 认证（`enable_authn=false`）做双保险。

### 13.1 "完整"要分层看

| 层 | 测试需要什么 | 单容器 EMQX |
| --- | --- | --- |
| MQTT 协议层 | 3.1.1、QoS0/1、LWT、clean session、retain | ✅ 全支持（设备 `clean_session=true`、QoS1、有 LWT，均无压力） |
| 设备契约层 | `v1/devices/me/telemetry`、`.../rpc/request/+`、`.../rpc/response/<id>`、`.../attributes`、`iothub/<MAC>/data/up|down` | ✅ 纯主题路由，全部满足；41 例 runner 只依赖这一层 |
| ThingsBoard 语义层 | 遥测入库、属性下发/应答、在线状态计算、规则链 | ❌ **没有**。设备连上后，`attributes/request` 不会有人回、遥测不入库、TB 看板无数据 |

→ 做**设备回归 / 故障注入 / soak**（即现在这套 41 例 + 注入脚本的用法），EMQX 完全够；要验"TB 入库/属性同步"就必须连真 TB（`139.9.93.245:21883`），那是另一类测试。

### 13.2 部署（compose，推荐）

```bash
cd tools/broker_cloud
docker compose -f docker-compose.emqx.yml up -d
docker compose -f docker-compose.emqx.yml logs -f | head -30   # 等 "EMQX 5.8.x is running now"
```

或裸 docker：

```bash
docker run -d --name iothub-emqx --restart unless-stopped \
  -p 21884:1883 -p 127.0.0.1:18083:18083 \
  -e EMQX_NODE__NAME=emqx@127.0.0.1 \
  -e EMQX_LISTENERS__TCP__DEFAULT__ENABLE_AUTHN=false \
  -v emqx-data:/opt/emqx/data \
  emqx/emqx:5.8
```

验证与设备切换完全复用 §5/§6：`smoke_mqtt.sh 139.9.93.245 21884 <token>`，设备只改 port=21884。

### 13.3 三个必须做对的点

1. **端口必须错开**：同机 TB 占 21883，EMQX 映射 `21884:1883`。别图省事直接用 1883。
2. **别启用任何认证器**：EMQX 加一个 password_based 认证器后，设备（无密码）会立刻被拒，现象只有 `not authorized`，极难判别。已用 `enable_authn=false` 兜底。
3. **内存**：EMQX 是 Erlang VM，空载常驻约 **300–500MB**；与 ThingsBoard（Java，通常 2GB+）同机时先看 `free -m`。1C1G 别考虑，2C2G 起。
4. **Dashboard 别暴露公网**：`18083` 只绑 `127.0.0.1`（compose 已如此），用 `ssh -L 18083:127.0.0.1:18083` 访问；首次 `admin/public` 立即改密。

### 13.4 调试期为什么比 mosquitto 强（这是选它的主要理由）

| 能力 | 用途 |
| --- | --- |
| Dashboard → Clients | 直接看设备**是否真的连上**、clientid、keepalive、上下行字节——正好治当前"设备连不上"这类只能靠串口猜的问题 |
| Dashboard → Subscriptions | 确认设备订阅到了 `v1/devices/me/rpc/request/+` 与 `iothub/<MAC>/data/down`，一眼看出主题配错 |
| Dashboard → Retained | 看 LWT/属性残留，判断"设备掉线但 broker 还留着旧值" |
| Trace（按 clientid 抓包） | 对单个设备逐包记录 CONNECT/SUBSCRIBE/PUBLISH/DISCONNECT，比串口日志完整，DEF-SCAN 那类问题取证时很有用 |
| REST API | `/api/v5/clients`、`/api/v5/topics` 可脚本化取数，便于自动化验收 |

mosquitto 只有日志文件，要同等信息得抓包。

### 13.5 什么时候仍选 mosquitto

- 只要一个"哑 broker"，机器很小（1C1G）；
- 不想引入 Docker；
- 长跑只要连通性、不需要观测面板。

两者对本项目是**功能等价、可互换**的（同端口、同主题、同匿名语义），切换只改设备端口配置，脚本不用动。

```bash
docker compose -f docker-compose.emqx.yml down          # 停止，保留数据卷
docker compose -f docker-compose.emqx.yml down -v       # 连数据卷一起删
```
