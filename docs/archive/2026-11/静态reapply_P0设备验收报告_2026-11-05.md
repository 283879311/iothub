## 4. C/D/E —— 埋点与恢复链：**3/3 全部触发超时并靠候选重试救回**

这是本轮最重要的证据。三轮 `runtime_restart` 的串口序列完全同构（以第 1 轮为例）：

```
I (98935)  apply_begin mode=static source=runtime_restart
I (99035)  apply_await_start gen=2
E (101055) apply_start_timeout gen=2, gate stays closed
W (101055) recover action=retry_candidate begin (candidate==lkg==persistent)
I (101095) apply_await_start gen=3
I (101515) sta_start_evt gen=3
I (101515) apply_start_released gen=3
I (101515) apply_cfg: started (gen=3)
I (101515) sta_start_evt gen=3          ← 同代第二次事件
I (101515) net_config_state=static
W (101535) recover action=retry_candidate result=ok
```

计数：`apply_start_timeout`=3、`retry_candidate begin`=3、`retry candidate result=ok`=3、`gate_set by apply failure`=3、`offline_gate_clear`=3、`sta_start_evt`=7、无 `retry_candidate` 失败、无 abort/Guru/assert。

**判读**

- **C PASS**：`sta_start_evt` 逐次可见；apply 次数（boot 1 + 运行期 3）与释放次数一致，无“apply 完成但无事件”的静默路径。
- **D PASS（自然样本）**：候选 == LKG == 持久配置时，超时后**恰好一次** `retry_candidate`，随即成功；IP 保持 `.50`、`cfg_state=static`。若没有本修复，这 3 次都会走 `lkg_equals` 跳过 → DHCP 救援 → `.28`（即原缺陷复现路径）。
- **E PASS**：超时后 `gate_set by apply failure`，直到重试的 `sta_start_evt` 才 `offline_gate_clear`；同代第二次事件走非 await 分支被忽略，**未出现第二个 `apply_start_released`**——代际串扰修复按预期生效。

**但必须写清：根因未消除。** 运行期 re-apply 的重连 **3/3 仍未在 2s 内收到 `WIFI_EVENT_STA_START`**，P0 只是把它变成了“可恢复”。这与原观察项结论一致，也直接构成 P1 方向 2 的硬数据依据：不能继续依赖“等事件”，应改为 `esp_wifi_start()` 后探测真实 STA 状态。

**新观察（需 P1 一并处理）**：每个成功代都出现 **两次** `sta_start_evt gen=N`（gen=3/5/7 各 2 次）。由于日志里的 gen 取自运行时计数器，**迟到事件会被标成新代号**，因此无法从日志判定第二次是“重复投递”还是“上一代迟到事件”。这不影响功能（首个事件释放门控时驱动确已 start），但说明“靠事件 + 代号”判完成本身不可靠——P1 应改为状态探测，并顺手把 gen 标注换成事件发生时刻的真实驱动状态。

## 5. F —— N06 MQTT 全链路：PASS（38/40 PASS，0 FAIL，2 SKIP）

**方法**：设备 MQTT 临时指向本机 amqtt `192.168.1.19:21883`（BLE v1 `config.set`，`mqtt_host`/`mqtt_port`），跑 40 例后改回 `139.9.93.245:21883` 并复验在线。

| 项 | 结果 |
| --- | --- |
| 用例总数 | 40（`summary: total=40, passed=38, failed=0, skipped=2`） |
| SKIP | N03、N07（静态 IP 锁下的预期跳过） |
| **N06a/b/c** | **PASS**：tryconnect 真 AP 受理 → 到达 got_ip/success → apply 提交 success |
| 与 a792 基线对比 | 完全一致（同为 38/38 PASS + 2 SKIP） |
| 凭据处理 | SSID/口令只经环境变量传入 runner；口令长度 10，未出现在任何日志/报告 |

N06 的 apply 同样命中 2s 超时并靠候选重试救回（串口 `apply_start_timeout gen=2` → `retry_candidate` → `started gen=3`），说明该路径在 MQTT 源事务下也成立，且不影响 N06 判定。

**排障记录（避免误判为防火墙）**：首次指向本地 broker 时设备报 `Error transport connect`；ufw 放行后仍失败。真实原因是**上一轮遗留的 amqtt 进程连接槽耗尽**（3 小时未重启）；重启 broker 后立即连通。因此本轮 ufw 放行并非必需，测后已提示恢复防火墙。

## 6. 偏差与事件记录（如实）

1. **误连 65D8（只读）**：首次 `base` 采样用了 Wi-Fi MAC `…C8:E4` 匹配 BLE 地址，落空后回退到首台 `IotHubBLE-` 设备，实际连到 65D8 并执行了 `device.info` + `network.status` 两次**只读**查询。未发任何写命令、未改配置、未烧写。已修正：工具默认值改为 `B0:A7:32:28:C8:E6`，并新增 `--expect-device IotHub-C8E4` 白名单，不匹配直接中止。
2. 串口日志首行 `rst:0x1 (POWERON_RESET)` 来自烧写后复位，非异常复位。
3. 本轮**未**做 EN 硬复位实验，不涉及 T5 V2 结论。
