### 3.4 分片期间 operation.get（非阻塞 PASS，严格版未复现）

流程：

1. v1 `network.tryconnect`（TQ2017，历史误写；真实目标 `TQ2018`；两者当时均不可见）→ `op-E16A53332022A60F`，accepted；
2. 同 `idempotency_key` 重发 → 同一 operation；
3. 不同 key 在活动期重发 → `busy`；
4. 发 `config.get`（1184B / 5 分片）；
5. 在长响应首片到达后发 `operation.get`。

实测时间线：

```text
长响应首片:        105.408s
operation.get 发出: 105.572s
operation.get 返回: 105.681s   (latency 108.9ms)
内容:              {"operation_id":"op-E16A...","state":"connecting","error":"none"}
tryconnect 受理:    104.240s
tryconnect 终态:    3.736s 后，failed / ap_not_found
```

结论：

- operation.get **没有等 15s 试连结束**，试连仍在 connecting 时就返回了；
- 但受固件 **200ms 命令限频** 和 MTU 256 影响，5 分片按 20ms 间隔约 100ms 传完（整个响应含命令处理在 105.526s 完成），operation.get 实际在长响应完成后 **0.046s**（首片后 0.164s）才发出，不是严格的分片间隙中；
- 你的验收口径允许“响应排在长响应之后”，所以该项按**非阻塞 PASS** 记录；若要求严格“分片期间”，需要用 MTU 23（更接近 Android 微信）或更长响应复测。

TQ2017（历史误写；真实目标 TQ2018）不可见，tryconnect 终态是 `ap_not_found`（不是 `wrong_password`）；`apply` / `cancel` 对该失败候选返回 `operation_state`，符合契约。

### 3.5.1 操作槽生命周期（源码确认）

- `APP_OPERATION_MAX_SLOTS = 4`（`main/operation.h:10`），静态表，不占堆；
- 候选 TTL：accepted 20s、got_ip 300s；终态保留 **600s（10 分钟）**（`main/operation.c:20-22`）；
- `app_operation_start()` 先回收 `now - terminal_ms >= 600s` 的终态槽；worker 每秒也会回收一次（`main/operation.c:160-181, 228, 532`）；
- 有 active（accepted/connecting/got_ip/committing）操作时，新 start 返回 **`busy`**；4 个槽都在终态保留期内时，返回 **`no_slot`**（`ESP_ERR_NO_MEM` 映射）；
- active 操作永远不会被回收；没有手动 clear API；终态过期后由 worker/下次 start 自动腾槽；
- 客户端遇到 `no_slot` 应提示“设备操作记录已满，请稍后重试”，不要假设新操作已创建，也不要尝试清理 active 操作；终态记录 10 分钟后自动释放。

> **2026-10-24 源码变更注记（T5 期间批次）**：`main/operation.c` 已改为「满表**且无活动
> operation** 时覆盖最老终态记录受理新请求（纯 FIFO）」，`no_slot` 退出正常路径；终态保留
> 维持统一 600s（原"分级保留 120s/600s"中间版经评审后于 2026-10-25 回退）。本节上述
> `no_slot` 相关描述对应 2026-10-23 固件（b42fe49）；新语义已实测：见 §3.5.2.1（12/12 PASS）。

疑似冲突点（待源码修复确认）：

- `app_wifi_connect_best_saved_profile()` 的自动重连扫描与 BLE `network.scan` 的 `app_wifi_perform_scan()` 并发，未串行化；
- `app_wifi_try_connect_common()` 在 `s_wifi_connect_task != NULL` 时直接返回 busy，BLE 救援 tryconnect 会被自动重连挡住；
- BLE 命令没有“暂停自动重连、取得 Wi‑Fi 独占权”的机制。

修复任务 T5（建议先做，再删 AP 回退）：

1. BLE `network.scan`/`network.tryconnect` 进入时设置 rescue/suspend 标志，阻止新的自动重连调度；
2. 等待当前 `s_wifi_connect_task` 退出，串行化 `app_wifi_perform_scan()`；
3. tryconnect 救援路径不再因 `s_wifi_connect_task` 返回 busy，预扫在独占状态下执行；
4. 命令结束/失败后恢复自动重连；
5. 复测坏 SSID + 无 IP + MQTT down：scan 能看到 TQ2018 → tryconnect → apply → TQ2018/MQTT；等待 >90s 仍保持 `mode=sta`、BLE 可救援；
6. 通过后再移除 AP 自动回退与 `net_mode=AP` 持久化，并复测。

设备当前已恢复：TQ2018 DHCP `192.168.43.63`、`sta_use_static=false`、MQTT connected。无 Web/AP 配置通道；AP 自动回退仍保留，待 T5 通过后删除。
