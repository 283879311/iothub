# 网络配置自动切换与 MQTT 事务方案评审备忘（只读）

> 日期：2026-11-03
> 范围：方案第六节策略、operation 状态机、回滚/校验能力、BLE/MQTT 双通道并发。
> 方式：仅只读核对现有固件；**未改代码、未烧写、未操作设备**。
> 结论：**策略接受**；事务骨架和 operation 查询可复用；互联网验证层与 MQTT 验证阶段是从零新建；第二阶段前必须先完成阶段 0，并补齐双通道规则。

## 0. 结论摘要

1. 自动轮询、失败回原 SSID、后台退避、BLE 兜底：**接受**；候选列表复用现有 profiles，不新建候选管理。
2. MQTT 切换事务化、失败回滚、结果经 `operation.get` 查询：**接受**；现有 operation 框架可复用。
3. 但“加 4 个状态”不是只改枚举：必须同步改迁移表、active/terminal/cancel 判定、TTL、状态名、错误映射和客户端兼容。
4. `network.apply` 当前是“NVS 写完即 SUCCESS”，Wi-Fi/MQTT/互联网验证完全不在提交条件里；互联网探测代码为零。
5. MQTT 开闸不能把 `APP_CLOUD_ALLOW_NET_CMDS` 置 1；必须做事务化命令白名单，并封堵 `.async` 内部入口旁路。
6. 双通道规则中“按域各自允许”与当前**全量配置快照回滚**冲突：事务失败会覆盖并发修改的另一域。必须改为事务期间阻止配置写入，或做按域快照/合并。
7. 静态 IP 和 BLE 连接期间，现有 profile 扫描回退本来就被禁用；自动轮询不能假设这两种场景下可切换候选。

## 2. 方案假设与固件现实的差距

### 2.1 状态机：不是“加四个枚举”

需要同时定义：

- `ACCEPTED → CONNECTING → GOT_IP → INTERNET_CHECKING → MQTT_CONNECTING → COMMITTING → SUCCESS`
- 失败分支：`INTERNET_CHECKING/MQTT_CONNECTING/COMMITTING → ROLLING_BACK → ROLLED_BACK`（回滚失败才落 `FAILED` 或专用错误）
- `FAILED` 与 `ROLLED_BACK` 的语义分离：前者未提交或不可回滚，后者已提交但验证失败且回滚成功。
- 每个新态的 `is_active`、`is_terminal`、`can_cancel`、TTL/deadline、`app_op_state_name`。
- 客户端兼容：`operation.get` 会返回新状态字符串；旧 App 必须至少能显示未知态，不能崩溃或误判终态。
- `app_operation_error_t` 增加 `MQTT_UNAVAILABLE`、`INTERNET_UNVERIFIED` 等；v1 映射显式加入。
- `failure_reason` 与现有 `operation.get.error` 的关系要先定：建议复用同一个枚举，避免两套分类漂移；若协议必须新字段，则由同一枚举映射。

### 2.2 apply 成功语义必须改

当前 `network.apply`：

1. snapshot；
2. 写 NVS；
3. 保存 profile；
4. `app_wifi_schedule_restart()` 投递 Wi-Fi re-apply；
5. 立即置 `SUCCESS` 并返回 `applied=true`。

实际 Wi-Fi re-apply 由 `wifi_restart` 任务稍后执行，失败走 M1 恢复链；operation 完全不知道结果。新方案必须增加：

- apply 完成事件/回调（成功/失败/被 drain 放弃）；
- operation worker 在验证完成前不得置 SUCCESS；
- 明确的阶段超时（Wi-Fi 连接、IP、互联网、MQTT 各自预算）；
- 回滚完成后再置 `ROLLED_BACK`，不能提前清 job/上下文。

### 2.3 互联网探测层从零开始

现有代码没有 ping/DNS/HTTP 探测。需要新建一个可取消、有时限、低资源占用的探测模块，并明确：

- 探测目标：DNS 解析 + TCP 连接 MQTT broker 主机/端口，或受控 HTTP 端点；不要依赖单一公网服务。
- 探测失败与“MQTT 凭据错误”分开：前者 `INTERNET_UNVERIFIED`，后者 `MQTT_UNAVAILABLE`。
- 探测必须可被 cancel/expire 打断，不能阻塞 operation worker 或 BLE 事件循环。
- 失败后回滚顺序：停 MQTT → 恢复旧配置 → 重启旧 Wi-Fi → 验证旧链路；不能只写回 NVS 就宣称回滚成功。

### 2.4 MQTT 开闸：事务白名单，不是宏

`APP_CLOUD_ALLOW_NET_CMDS=1` 会同时放开 `config.set` 的 net/MQTT/BT/UART/admin 域，不符合“云端不能自己开自己”的哲学。阶段 0 应改为：

- MQTT 只允许：`network.tryconnect`、`network.apply`、`network.cancel`、`operation.get`（以及只读 `network.status`）。
- MQTT 仍禁止：`config.set` 的 net/MQTT/BT/UART/admin 域、`network.profile.delete`、`network.restart`、写 NVS 配置。
- 所有入口按 source + 命令 + 域三维白名单；未知/未列命令默认拒绝。
- `.async` 内部入口只允许协议适配层和内部 child 调用；外部客户端直接调用 `.async` 一律拒绝，不能依赖调用方自觉，也不能误禁 BLE v1 映射。
- `s_net_async_apply_internal` 是进程级 bool，不是安全边界；阶段 0 要把它改成不可被外部并发利用的内部执行上下文。
- `app_operation_owner_t` 没有 MQTT：`main/cmd.c:343/404` 当前把非 BLE 源映射成 HTTP。阶段 0 必须新增 MQTT owner，并明确其幂等键、取消权限和 BLE 断连时的存活规则。

### 2.5 双通道并发：现有“按域并行”不安全

当前快照/回滚是整份 `config + profiles`。场景：

1. MQTT 发起 network 事务，snapshot 保存旧 config；
2. BLE 并发 `config.set` 改 MQTT 域；
3. network 事务失败，`snapshot_restore()` 恢复整份旧 config；
4. BLE 刚改的 MQTT 域被静默覆盖。

因此：

- **阶段 1/2 建议事务期间阻止所有 `config.set` 写入**（至少 net/MQTT/BT/UART/admin 域），返回 `busy`；这是最简单且可证明的规则。
- 若必须“按域并行”，则快照必须按域保存/恢复，并在恢复时做 merge；这是更大的改造，不建议在阶段 1 做。
- `config.set` 的 `CFG_EFFECT_REBOOT` 还会重启芯片、丢 operation，必须在事务期间拒绝。

### 2.6 候选轮询不能假设 profile 扫描总是可用

- 静态 IP：`main/wifi.c:1043` 明确跳过 saved-profile fallback，避免把 A 的静态地址套到 B；自动轮询若仍按 profiles 切换，必须新增策略（静态模式只试正式 SSID，或切换时显式清静态标志并重新分配）。
- BLE 连接期间：`main/wifi.c:1054` 跳过扫描，只做 formal fast path；自动轮询在 BLE 兜底场景下不能依赖扫描。
- 这两条会直接影响“候选列表按序试”的状态机和超时设计，阶段 1 开始前必须定策略。

### 2.7 cancel 与最后 profile

- 当前 `app_cmd_net_cancel_async` 不校验来源；开闸后必须显式实现：BLE 可取消任意网络事务；MQTT 只能取消自己发起且链路仍可用的事务；HTTP 按现有策略。
- `network.profile.delete` 目前只在 BLE/HTTP 可达；MQTT 开闸前加“至少保留一个可用 profile”，并把删除纳入事务锁，避免切换中途删掉回滚目标。
- MQTT 通道禁删最后一个 profile 的建议接受；实现上放在 config 层做不变量，而不是只放在命令层。

## 3. 接受的双通道规则（修订版）

| 规则 | 结论 | 实现要点 |
| --- | --- | --- |
| 单操作槽互斥 | 接受 | 复用 `app_operation` 全局 active 检查；`s_net_async` 只作为网络 job 上下文，不另造第二把锁 |
| config.set 并发 | **需修正** | 事务期间阻止 net/MQTT 域写入；不要假设“按域并行”安全，除非快照改为按域 |
| cancel 单边性 | 接受目标，但当前未实现 | 显式 owner/source 校验；BLE 可取消 MQTT 事务，MQTT 不能取消 BLE 事务；不依赖“链路已断” |
| 禁删最后 profile + 失败回滚 | 接受 | config 层不变量；删除/切换纳入同一事务锁；回滚目标 profile 不可被并发删除 |

## 4. 分期与退出条件

| 阶段 | 内容 | 退出条件 |
| --- | --- | --- |
| 0（前置） | MQTT 入口 v1 化；source/命令/域白名单；封堵 `.async` 旁路；cancel 所有权；config.set 事务期拒绝；v1 错误码映射 | 负向测试：MQTT `config.set` 被拒、`.async` 外部调用被拒、跨源 cancel 被拒、事务中 config.set 返回 busy；现有 BLE/HTTP 路径不回归 |
| 1 | 4 个新态 + FAILED/ROLLED_BACK；apply 完成回调；互联网探测；MQTT 连接验证；failure_reason；候选轮询/退避 | 状态迁移单测覆盖所有失败分支；静态 IP/BLE 场景策略明确；apply 未完成不得 SUCCESS；超时可取消 |
| 2 | MQTT 事务切换开闸；新 MQTT 会话回报终态；operation 查询扩展；双通道规则落地 | MQTT 发起成功/失败/回滚均可查询；回滚不覆盖并发域；断链后结果可恢复查询 |
| 3 | 小程序 errors.js、状态映射、T3 远程切换观察卡、operation.get 轮询 | 新旧客户端兼容；未知状态可显示；错误码不再落 internal_error |

## 5. 待决策（阶段 0/1 前）

1. 静态 IP 下候选轮询策略：只试正式 SSID，还是切换时放弃静态地址？
2. BLE 连接期间是否允许 profile 扫描；若不允许，自动轮询的候选范围如何限定？
3. 互联网探测目标与超时预算（DNS/TCP/HTTP；是否允许公网依赖）。
4. `failure_reason` 复用 `operation.get.error`，还是新增字段并双写？
5. MQTT 切换后新会话如何关联原 operation（固定结果 topic + operation_id，还是云端轮询 `operation.get`）？
6. 回滚范围：整份 config 还是按域；若整份，事务期间必须全局阻止配置写入。
7. 旧 App 遇到新状态字符串的行为（至少 unknown 不崩溃）。

## 6. 给对方的一句话回复

策略接受；事务骨架和 operation 查询现有基础比方案假设的更好，可直接复用，但互联网验证层和 MQTT 验证阶段是从零新建；第二阶段开工前必须先完成阶段 0（MQTT 入口 v1 化 + 事务化白名单，封堵 `.async` 旁路），并补齐双通道规则（单槽互斥、config.set 与全量快照的冲突、cancel 所有权、禁删末 profile）——这几条不定，第一阶段的状态机设计会返工。
