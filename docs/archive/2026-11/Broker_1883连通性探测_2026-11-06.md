## 4. 两条必须知道的风险

### 4.1 多设备串扰（实测确认，不是推测）

```
dev-A 订阅 v1/devices/me/rpc/request/+   → 收到 {"method":"config.get"}
dev-B 订阅 v1/devices/me/rpc/request/+   → 也收到 {"method":"config.get"}
```

TB 里 `v1/devices/me/...` 的 `me` 由 TB 按 token 解析成**该设备私有命名空间**；
到了哑 broker 上它就是**字面主题名**，所有设备共享。后果：

- 两台设备同时连 → 一条 RPC 两台都执行；遥测也无法按主题区分来源（只能看 payload）
- **测试期铁律：只让被测的那一台连**，其余设备不得指向该 broker
- `iothub/<MAC>/data/up|down` 按 MAC 分，**无此问题**（实测 dev-B 收不到 dev-A 的 down）

### 4.2 匿名开放 + Dashboard 公网暴露

- 任何人无需凭据即可订阅所有主题（含设备遥测）、向 `rpc/request/+` 下发命令
- `18083` Dashboard 公网可访问，EMQX 默认 `admin/public`；`/status` 无认证泄露节点名
- 建议至少做三件：① 改 Dashboard 密码；② 18083/1883 安全组限制来源 IP；③ 确认这台
  EMQX 的归属（自己/同事部署？是否另有项目在用？）

## 5. TB 语义缺口（测试边界）

| 能力 | 有/无 | 影响 |
| --- | --- | --- |
| token 校验 | ❌ 任意 username 都接受 | 测不出"错误 token 被拒"；鉴权类用例无效 |
| 遥测入库 / 历史查询 | ❌ | "TB 在线"、看板、数据回放均不可用 |
| 属性下发应答（attributes/response） | ❌ 无人应答 | 属性类用例会一直等到超时 |
| 在线状态计算 | ❌ | 只能靠 MQTT 连接本身判断 |
| 规则链 | ❌ | 无 |

→ **设备侧回归 / 故障注入 / soak：够用**；**平台语义类验证：必须用 21883 的真 TB**。

## 6. 切换到该 broker 的操作

设备侧（BLE → mqttcfg）：只改 **port 21883 → 1883**，host 不变，`use_tls` 关闭，token 保留。
串口预期：

```
Starting MQTT: uri=mqtt://139.9.93.245:1883, ..., tls=no, will=v1/devices/me/attributes
MQTT connected: subscribed RPC + shared attrs
```

工具侧：`mqtt_ack_gate_inject.py --host 139.9.93.245 --port 1883`（默认 21883，需显式改）。
