## 1. Q1：GOT_IP → MQTT CONNECTED 完整调用链（已由源码确认）

两条触发路径，同入 `app_mqtt_apply_config()`：

**A. 开机**：`main.c:105-106 app_mqtt_start` → `app_mqtt_apply_config`
→ **STA 无 IP 时拒绝建 client**（`mqtt.c` apply 入口 `waiting_sta_ip` 守卫，
真机 boot 日志可见 `mqtt_last_error="waiting_sta_ip"`），client 保持 NULL。

**B. 拿到 IP 后**（主路径）：

```
esp_wifi 连接成功
├─ wifi.c:3802-3803 注册的 wifi 处理器（先注册先执行，boot-7 < boot-10）
│    GOT_IP 分支：写运行态 → link_gen++ → app_netcheck_start(gen)   (wifi.c:2170-2190)
└─ mqtt.c:1944-1951 注册的 mqtt 处理器
     IP_EVENT_STA_GOT_IP 分支：app_mqtt_schedule_restart()          (mqtt.c IP 分支)
       → mqtt_restart 任务（3072B/prio5）：backoff[step] 延时（2/5/10/20/30s）
       → app_mqtt_apply_config()：stop 旧 client → esp_mqtt_client_start
         → esp-mqtt 内部任务完成 TCP/TLS + CONNACK
       → MQTT_EVENT_CONNECTED（esp-mqtt 事件任务上下文）
         → app_mqtt_lock() 内 s_mqtt.connected=true、fatal_error=false、
           s_restart_backoff_step=0（mqtt.c:1352-1373）
```

注册顺序决定同一事件上 wifi 处理器先于 mqtt 处理器执行（esp_event 对同一
loop/base/id 按注册序分发——框架语义；注册先后由 `main.c` boot-7/boot-10 顺序
源码确认）。**推论（对 §3.5 重要）**：netcheck 的 start 发生在 mqtt 的
schedule_restart 之前/同窗口，二者不互斥。

## 2. Q2：MQTT 会话能否绑定 link_gen？（现状：无关联——真缺口）

- `grep link_gen/generation main/mqtt.c main/mqtt.h` = **0 命中**：MQTT 侧完全
  不感知链路代次。`s_mqtt.connected` 是全局单槽布林，无会话身份。
- **为什么现网流程下"旧会话污染新链路"基本不可达（源码时序论证）**：
  tryconnect 在连接候选前先 `esp_wifi_disconnect()` 旧链路并等
  `APP_WIFI_TRY_OLD_DISC_BIT`（wifi.c tryconnect CLEANUP_OLD 段）；STA 断开
  事件里 mqtt 处理器**同步调 app_mqtt_stop → stop_clients，入口即在锁内置
  `s_mqtt.client=NULL; s_mqtt.connected=false`**（mqtt.c stop_clients 前段，
  12s/4s 的任务等待在置位之后），候选连接的 GOTIP 严格晚于该事件 → netcheck
  启动时全局 connected 必为 false。
- **残余风险（如实）**：stop_clients 会在事件循环里同步等待最长 4s+12s，
  期间整个默认事件循环被阻塞；若旧 client 的 CONNECTED 事件在此窗口排队，
  处理顺序仍在 stop 置位之后，不会把 connected 写回 true（CONNECTED 处理器
  不检查 client 是否已被判死——**此处是唯一理论缝隙**：迟到的
  MQTT_EVENT_CONNECTED 会在锁内把 connected 置 true。esp-mqtt 停止中的
  client 是否还会派发 CONNECTED，属 esp-mqtt 内部行为，**尚需实验核实**）。
- **最小关联机制提案（P2 增量）**：`app_mqtt_apply_config` 创建 client 时
  记录当时的 `s_wifi.link_gen` 快照（`s_mqtt.session_link_gen`），新增
  `uint32_t app_mqtt_session_gen(void)`；netcheck 阶段 2 的"在线"判据改为
  `connected && session_gen == link_gen`。改动约 10 行，落在 mqtt.c 单文件。

## 3. Q3：域名解析实际路径（已由源码确认，含阻塞上限）

当前上机实现（`main/netcheck.c`）：

- **IP 字面量**：`dns_gethostbyname` 对字面量同步返回 ERR_OK 并直接写地址
  （lwIP `dns.c` `ipaddr_aton` 快路径，无条件前置），**不查 DNS** —— 符合
  任务书 2.2 情况 A；
- **域名**：`dns_gethostbyname` 异步（ERR_INPROGRESS + 回调），netcheck 任务
  100ms 轮询，受**总预算 25s** 约束 —— DNS 在总超时与取消设计内，符合 2.2
  "特别要求"（真机已验：诊断行 `dns host='139.9.93.245' err=0`）；
- **取消收敛**：DNS 轮询 100ms 可中断；最长有界步 = 单次 TCP select 2.5s
  → 取消 ≤3s，**不承诺 DNS 内部重试时长**（lwIP 内部 DNS_TMR 重试可能超过
  3s，但我们不等它——deadline 一到即按未解析处理，归 `INTERNET_UNVERIFIED`）；
- **多地址**：`CONFIG_LWIP_DNS_MAX_HOST_IP=1`（sdkconfig:2362）—— lwIP 本
  配置只返回单地址，"多地址耗尽预算"问题在此配置下不存在（框架事实，
  若未来调大需补有限尝试策略）；
- **对照 getaddrinfo**：任务书要求的阻塞审查结论 = 评审 P1-1 时已确认
  `getaddrinfo` 阻塞不可取消，故实现改用异步 `dns_gethostbyname`；
  esp-mqtt 自身的解析走 `getaddrinfo`（esp-tls 内部），与 netcheck 探测
  路径相互独立，netcheck 的结论不代表 esp-mqtt 解析行为，二者通过
  "TCP 可达 + 会话在线"间接耦合。

## 4. Q4：store_trial 是否写正式 NVS？（已由源码确认：不写）

- `app_cmd_net_store_trial`（cmd.c:214-243）只写 **RAM 静态结构
  `s_net_trial`**（id/ssid/password/operation_id/cfg_txn token/expires_ms/
  owner/valid），在 `app_cmd_net_job_lock()` 临界区内完成；无任何
  `app_config_save`/NVS 调用。trial 生命周期 300s、单槽、断连/取消/过期即清。
- 全部正式 NVS 写点（grep `app_config_save|snapshot_*`）：
  - cmd.c:2024 —— `config.set` 域（非 trial 路径）；
  - cmd.c:2360-2412 —— **internal `network.apply` 分支**：
    `app_config_snapshot_save()` → `config_apply_patch()`（patch 内部
    `app_config_save` 先落 NVS，config_apply.c:838）→ profile 保存 →
    成功 discard / 失败 `snapshot_restore()`。
- **时序结论**：NVS 写入只发生在 internal network.apply；该分支只能从
  `app_cmd_net_apply_async` 到达，而后者有 worker 验证门（cmd.c:472-473，
  `ok_for_gen || wait(25s)` 通过才置 GOT_IP）+ apply 兜底（cmd.c:770-778，
  当前代次验证不成立按阶段拒绝）。**"验证成功前候选配置入 NVS"不可能发生**；
  失败路径走判别点 B cleanup（`rescue=restore_persistent`）+ 快照恢复，
  掉电重启读到的是正式配置 —— 任务书 6.3 的担心在当前结构下不成立。
  （真机 R-NET-2 待跑，作为设备侧终证。）

## 5. Q5：tryconnect 成功后运行态是否完整更新？（已补齐，附一处口径差）

- 候选 GOT_IP 归属点（wifi.c:1747-1772）：已补写
  `sta_connected/sta_has_ip/sta_ip(来自 esp_netif)/connected_ssid` +
  `link_gen++` + 启动 netcheck —— 试点写在 tryconnect 状态锁外、DONE 事件位
  置位前，锁序无嵌套；MQTT 的 `waiting_sta_ip` 拒启缺口已消除（真机已验）。
- **口径差（任务书 §5）**："generation 必须由 Wi-Fi 层准确传递，不允许
  tryconnect 返回后读全局 gen 猜归属"。当前 cmd.c worker 在
  `try_connect_ip` 返回**后**读 `app_wifi_link_generation()`（cmd.c:471）。
  论证：trial 存续期内不可能出现更新的链路（teardown 即非 OK 返回），所以
  读到的 gen 必为候选 gen；但若 GOT_IP 与 worker 返回之间恰好断链换代，
  worker 读到新 gen → wait 对不上 → 保守 FAIL —— 结果正确、语义不算
  "猜归属"。**P4 最小改法**：`app_wifi_try_connect_ip` 增加出参
  `uint32_t *link_gen_out`（DONE 置位点原样带出），worker 改用之，
  消除论证依赖。

## 6. Q6：`app_wifi_schedule_restart()` 有无完成通知？（无）

- `app_wifi_schedule_restart`（wifi.c:3740 附近）只 notify/创建
  `wifi_restart` 任务（wifi.c:3691-3745）；任务 apply 成败仅有日志
  （`apply_begin mode=… source=runtime_restart` / `restart apply abandoned
  (drain)`），**无事件位、无回调**。
- 影响：R2 回滚（cleanup → schedule_restart）后，操作方无法等待
  "旧链路恢复完成"，只能靠 GOT_IP 事件自然驱动后续（netcheck 会随新
  GOT_IP 自动再验）。**当前设计已按此现状工作**；如需等待语义，属于
  wifi_restart 任务的事件化改造（超出本批，建议不纳入）。
