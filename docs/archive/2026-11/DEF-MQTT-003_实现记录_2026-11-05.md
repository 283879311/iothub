## 1. 改动（一处，cmd.c）

`app_cmd_net_async_cleanup()`，判别口径按评审结论 **B**：

```c
app_cmd_net_job_lock();
/* 单点决策:状态读取与 trial 检查同一临界区 */
restore_persistent = (app_operation_state(op) != APP_OP_COMMITTING);
if (s_net_trial.valid && strcmp(...) == 0) {
    app_cmd_net_trial_clear();
}
app_cmd_net_async_clear_job();
app_cmd_net_job_unlock();

if (restore_persistent) {                 /* 锁外异步恢复 */
    ESP_LOGW(TAG, "rescue=restore_persistent op=%s (cleanup without commit)", ...);
    (void)app_wifi_schedule_restart();    /* 只 schedule,不阻塞 */
}
```

- 不变量："这次清理没有提交新配置" ⇔ `state != COMMITTING`；EXPIRED/CANCELLED/FAILED 均成立。
- **实测等价性**：expire 选中的 op 永远非 COMMITTING（`set_state(COMMITTING)` 置 `deadline_ms=0`，expire 跳过），cancel 也拒绝 COMMITTING ⇒ B 在可达路径上是 A 的严格超集，**零额外重启**。
- 恢复走既有 restart 链；不进 LKG/DHCP 救援链，不改 M1 语义。

## 2. 行为矩阵

| 场景 | op 状态（cleanup 时） | 结果 |
| --- | --- | --- |
| cancel/expire 时已 `got_ip` | GOT_IP → EXPIRED/CANCELLED | **恢复持久配置**（本修目标） |
| apply 已接管（COMMITTING） | COMMITTING | 不恢复（apply 侧不调 cleanup；此分支为防御） |
| apply 失败（COMMITTING→FAILED） | FAILED，**不经过 cleanup** | 不出现 rescue（R2 严格口径） |
| expire 时仍在 CONNECTING | CONNECTING → EXPIRED | **恢复**（B 相对 A 的超集；代价为零） |
| BLE 断连且 op 在 active | active → cancel → cleanup | **恢复**（A 也覆盖：cancel 在终态化之前调 cleanup） |
| BLE 断连且 op 已终态/NULL | fall-through 直清 | 不经过 cleanup（残余缺口，单独观察） |

## 4. 缺口修正与残余项

- **原表述的"BLE 断连缺口"比实际窄**：`app_operation_cancel` 在终态化**之前**调 cleanup（`cancel_post_cleanup` pause 钩子即证据），断连时 active op 走 `can_cancel → cancel → cleanup`，trial 由 cleanup 亲手清掉——A 也覆盖这条路径；fall-through 直清只在 op 为 NULL/已终态时可达。
- **A/B 共同的残余缺口（本批不修，单独立项观察）**：`run_fn` 自然失败路径（`operation.c:598-613`）直接置 FAILED、**不调 cleanup**；若失败发生在 got_ip 之后，设备留在试验网络且 cleanup 永不运行。BLE 断连 fall-through 同理。需要"cleanup 之外"的机制（run_fn 失败尾部恢复）。

## 6. 风险

- `schedule_restart` 与紧随其后的新 tryconnect 可能竞争 WiFi 所有权（restart 任务 claim OP_APPLY）：新 op 会得到 `busy`/aborted，需在 R1/R3 里观察一次。
- 恢复是异步的（restart 任务），`network.status` 在 cleanup 后 1–3s 内才回到 `.50`，R1 判据需留时间窗。
