## 2. 阶段 0 接口规则（确认）

### 2.1 来源与命令边界

只对“网络配置域”新增 MQTT 事务白名单，其他 MQTT 命令维持现状。

| 来源 | 允许 | 禁止/拒绝 |
| --- | --- | --- |
| BLE v1 | `network.tryconnect/apply/cancel`、`operation.get`、既有只读命令 | 不变 |
| MQTT | `network.status`（只读）、`network.tryconnect`、`network.apply`、`network.cancel`（仅自有事务）、`operation.get`（自有事务） | `config.set` 的 net/MQTT/BT/UART/admin 域；`network.profile.delete`；`network.restart`；`network.scan`；`diag.*`；`.async` 外部调用 |
| HTTP | 维持现网配置页行为 | 不变 |
| 内部 child | 仅内部派生的 `network.apply` 路径 | 不得作为外部来源的旁路 |

规则：

- `network.apply` / `network.cancel` 的 v0 外部入口与 `.async` 入口都必须在**同一张 source/命令/域白名单**下判定；不得只改 v0 分支。
- `network.apply.async`、`network.tryconnect.async`、`network.cancel.async` 只接受**已认证协议适配层**（BLE v1 / MQTT v1 映射）和内部 child 调用；外部客户端直接以 `.async` 方法名调用一律 `guard_rejected`。不得依赖 `s_net_async_apply_internal` 这个进程级 bool，也不能把现有 BLE v1 映射一起禁掉。
- 增加 `APP_OPERATION_OWNER_MQTT`；不再把非 BLE 源统一映射为 HTTP（`main/cmd.c:343/404`）。
- MQTT 事务的幂等键、operation 查询可见性、cancel 归属按 owner 定义。
- 错误枚举增加 `APP_OPERATION_ERR_MQTT_UNAVAILABLE`、`APP_OPERATION_ERR_INTERNET_UNVERIFIED`、`APP_OPERATION_ERR_STATIC_IP_PINNED`、`APP_OPERATION_ERR_LAST_PROFILE`；对外 v1 code 统一小写 snake_case：`mqtt_unavailable`、`internet_unverified`、`static_ip_pinned`、`last_profile`。
- 命名约定：内部枚举用 `APP_OPERATION_ERR_*`，协议错误码用 v1 现有风格的小写字符串；v1 映射不得再统一回落 `internal_error`。评审讨论中的大写写法仅作概念名，以本节小写 code 为准。

### 2.2 事务期间配置写入

接受评审建议，阶段 1/2 采用最容易验证的规则：

> **任一网络事务 active 时，所有 `config.set` 写入统一返回 `busy`。**

原因：当前 `app_config_snapshot_save/restore` 是整份 `config + profiles`，不是按域快照；允许其他通道写入会在回滚时覆盖并发修改。按域并行、合并和按域快照不在阶段 1/2 范围。

同时：

- 事务期间 `config.set` 即使只改 GPIO/UART 等域也拒绝，避免全量回滚覆盖；后续若确需并行，另行评审按域快照。
- 事务期间禁止可能触发 `CFG_EFFECT_REBOOT` 的配置写入，避免芯片重启丢失 RAM operation。
- `network.profile.delete` 在事务期间同样返回 `busy`；config 层增加“至少保留一个可用 profile”的不变量。

### 2.3 cancel 权限

- BLE：可取消任意网络事务，用于现场救援。
- MQTT：只能取消 `APP_OPERATION_OWNER_MQTT` 且仍可取消的事务；不得取消 BLE/HTTP 事务。
- HTTP：维持现有策略。
- 不依赖“MQTT 链路已断”作为权限事实；`app_cmd_net_cancel_async` 必须做真实 owner/source 检查。
- BLE 断连清理只处理 BLE owner；MQTT owner 的 operation 在 BLE 断开后继续，结果通过 MQTT/`operation.get` 查询。

**判定时点与所有权快照：**

- `owner` 在 `app_operation_start` 创建事务时写入 operation 结构，之后不因 BLE 连接/断开、MQTT 重连或当前命令来源而改变。
- cancel 必须**同时**校验“当前调用者的可信身份/认证状态”和“operation 创建时保存的 owner”，两者缺一不可。
- 当前调用者身份只能取自传输层认证上下文（BLE v1 token/会话、MQTT 已认证会话、HTTP 认证），不得由请求 JSON 自报 owner/source。
- 未认证或身份不明的调用者一律拒绝，不进入 owner 比较。

| 当前调用者 | 事务 owner | 判定 |
| --- | --- | --- |
| 已认证 BLE | BLE / MQTT / HTTP | 允许 |
| MQTT | MQTT | 允许 |
| MQTT | BLE / HTTP | 拒绝 |
| HTTP | HTTP | 允许 |
| HTTP | BLE / MQTT | 拒绝 |
| 未认证或身份不明 | 任意 | 拒绝 |

- BLE 已认证会话是现场救援通道：可取消任意 active 网络事务。
- MQTT 只能取消 `owner=MQTT` 的 active 事务；即使当前 MQTT 连接是后建立的，也不能取消 BLE/HTTP owner 的事务。
- HTTP 只取消 `owner=HTTP` 的事务；内部 child 不提供外部 cancel 入口。
- BLE 断连不释放 MQTT owner 的 operation、trial、幂等键或终态；该事务继续推进，终态保留 600s。

### 2.4 阶段 0 最终出口检查

阶段 0 完成必须同时通过：

- `.async` 外部入口封堵；BLE v1 合法适配路径仍可用；
- MQTT owner 创建、查询、取消链路可验证；
- BLE 跨 owner 取消 MQTT/HTTP 事务可验证；
- MQTT、HTTP 跨 owner 取消均被拒绝；
- 未认证/身份不明调用者取消被拒绝；JSON 自报 owner 不生效；
- BLE 断连不影响 MQTT owner 事务，trial、幂等键、终态仍存在；
- 事务期间所有 `config.set` 返回 `busy`；
- 最后一个可用 profile 不允许删除；
- `ip_mode` 非法组合被拒绝；静态 IP + `keep` + 不同 SSID 返回 `static_ip_pinned`；
- 原有 BLE、HTTP 功能无回归。

## 3. 静态 IP 与 BLE 连接策略（确认）

### 3.1 静态 IP

现状：`main/wifi.c:1043` 在 `sta_use_static` 时明确跳过 saved-profile 扫描，避免把 A 的静态地址套到 B。阶段 1 采用：

1. **默认：静态 IP 绑定正式 SSID，不自动轮询其他 profiles。** 候选轮询只在 DHCP 模式启用。
2. 若要切换到不同 SSID，请求必须显式携带 `ip_mode="dhcp"`；`allow_leave_static` 不是 v1 参数，出现即拒绝。未携带 `ip_mode` 或 `ip_mode="keep"` 时返回 `static_ip_pinned`，不扫描、不连接候选。
3. 显式离开静态模式时，事务按现有 `network.apply` 语义强制 `sta_use_static=false`、`net_mode=sta`，以 DHCP 验证新 SSID；成功后才持久化 DHCP 与新 SSID。
4. 失败回滚必须恢复完整快照：静态 IP 字段、原 SSID、原 profile；不得把静态地址留给候选 SSID。
5. 若未来要“静态 IP + 新 SSID”，必须显式提交新的静态 IP/网关/掩码/DNS 并单独校验，不纳入阶段 1。

#### 3.1.1 规范字段与冲突处理

**唯一规范字段：`ip_mode`。** 阶段 1 只接受 `"keep"` 和 `"dhcp"` 两个值；`allow_leave_static` 不作为 v1 参数，也不做兼容别名。

| 输入 | 判定 |
| --- | --- |
| `ip_mode` 省略 | 等价 `"keep"` |
| `ip_mode="keep"` + 当前静态 + 目标 SSID 等于正式 SSID | 允许；保持静态模式 |
| `ip_mode="keep"` + 当前静态 + 目标 SSID 不等于正式 SSID | 拒绝 `static_ip_pinned`，不扫描、不连接候选 |
| `ip_mode="keep"` + 当前 DHCP | 保持 DHCP |
| `ip_mode="dhcp"` | 明确允许离开静态模式；事务强制 `sta_use_static=false`、`net_mode=sta`，以 DHCP 验证；成功后才持久化 DHCP |
| `ip_mode` 为其他值，包括 `"static"` | 拒绝 `invalid_argument`；阶段 1 不支持事务内重配静态地址 |
| 只提供 `allow_leave_static` | 拒绝 `invalid_argument`，错误信息提示改用 `ip_mode="dhcp"` |
| `allow_leave_static` 与 `ip_mode` 同时出现 | 拒绝 `invalid_argument`；不做优先级合并，避免两种解释 |
| 事务参数携带 `sta_static_ip`/网关/掩码/DNS | 阶段 1 拒绝 `invalid_argument`；静态地址重配另行设计 |

`ip_mode` 放在 `network.tryconnect` 的请求参数中，在事务创建时解析并固定，随后 trial、commit、rollback 都读取同一份事务参数，不再重新解释客户端输入；`network.apply` 只按已保存的模式提交，apply 阶段不得再接受另一个模式字段。

**SSID 比较规则：**

- 判断是否“切换 SSID”时，必须比较**解析后的最终目标 SSID**与**当前正式配置 SSID**，不能比较请求里是否携带了 `ssid` 字段。
- 省略 `ssid`、使用当前 profile、使用 profile 标识等输入，必须先解析为最终 SSID，再做静态 IP 锁定判断。
- 解析后的目标 SSID 与正式 SSID 相同，才允许 `ip_mode="keep"` 的静态模式路径；不同则必须显式 `ip_mode="dhcp"`。

**trial 与 commit 的模式一致性（阶段 1 设计必须解决）：**

- 现有 `app_wifi_try_connect_common` 只设置 SSID/口令，不切换 netif 的静态/DHCP 模式；不能假设 `ip_mode` 在 trial 阶段已生效。
- `ip_mode="dhcp"`：trial 必须以 DHCP 模式验证；若当前是静态模式，设计必须明确何时释放静态地址，避免“用旧静态 IP 试连、提交后变 DHCP”的不一致。
- `ip_mode="keep"` + 当前静态 + 同 SSID：trial 与 commit 都必须使用现有静态地址，不能用 DHCP 试连后提交静态。
- trial 记录的模式/地址结果必须与 apply 提交的一致；不一致时拒绝 apply，不得只依赖 apply 再强制改写。

### 3.2 BLE 连接期间

现状：BLE 连接期间 `allow_profile_scan=false`（`main/wifi.c:1054`），自动回退只走 formal fast path；显式 `tryconnect` 仍可指定 SSID 并扫描连接。

阶段 1 采用：

1. **显式单目标切换**：BLE 连接期间允许，BLE 不因 Wi-Fi 切换而关闭；不得同时修改 BT 域配置。
2. **自动候选轮询**：BLE 连接期间不启动多 profile 扫描回退；只尝试当前正式 SSID/明确单目标，失败后进入退避，BLE 保持兜底。
3. BLE 断开后，才恢复 DHCP 场景的 saved-profile 自动回退。
4. BLE 断开不取消 MQTT owner 事务；BLE owner 事务按现有规则处理（COMMITTING 前可取消，COMMITTING 让其完成）。

## 4. 阶段 1 冻结前必须产出的设计物

1. 完整状态迁移表：`ACCEPTED → CONNECTING → GOT_IP → INTERNET_CHECKING → MQTT_CONNECTING → COMMITTING → SUCCESS`，以及 `ROLLING_BACK → ROLLED_BACK/FAILED`。
2. 每个新态的 `is_active`、`is_terminal`、`can_cancel`、TTL/deadline、状态名、错误枚举。
3. apply 完成事件/回调契约；Wi-Fi、IP、互联网、MQTT 四阶段超时和取消路径。
4. 回滚顺序：停 MQTT → 恢复快照 → 重启旧 Wi-Fi → 验证旧链路；回滚失败单独记录。
5. 失败原因分层：Wi-Fi 连接失败、IP 获取失败、`internet_unverified`、`mqtt_unavailable` 分开，不能只报 `network.apply failed`。
6. 旧客户端兼容：`operation.get` 新状态字符串至少按 unknown 安全显示，不误判终态。

## 5. 对“互联网与 MQTT 独立验证”意见的确认

接受，并作为阶段 1 的硬约束：

- `operation.get` 保留阶段结果：`wifi_connected`、`ip_acquired`、`internet_verified`、`mqtt_connected`，以及最后失败阶段和错误码。
- `internet_unverified` 与 `mqtt_unavailable` 分开；MQTT 内部再区分连接超时、认证失败、broker 不可达（错误码在阶段 1 冻结）。
- MQTT `CONNECTED` 不能作为 `internet_verified=true` 的证据；互联网探测必须独立执行并单独记录结果；反之，互联网可达也不能推断 MQTT 可用。
- operation 终态是“本次切换事务”的结果；SUCCESS 后链路再次断开属于新的运行态事件，不回写已终态 operation。
- `failure_reason` 建议复用现有 `operation.get.error` 枚举，另加 `stage_results`；不建立第二套并行错误分类。
- MQTT broker 变更时旧会话无法回报；终态结果保留 600s，并由新会话/`operation.get`/BLE 查询兜底。若新 broker 不可达，不得宣称“已通过新 MQTT 会话回报”。
