- **#16 受控手工卡**（`pwdchange`）：临时口令内存生成 + `finally` 恢复 + 恢复后原口令登录验证；
  全程断言 `sessions_invalidated:true` 与 G1 token 清空（两次改密 = sessionInvalidations +2）。
  流程实现抽在 `acceptance.pwdChangeControlled()`，可被自测端到端驱动；口令一律不入报告。
- **#15 手工记录卡**（`mtu`）：自动采集平台/微信版本、`wx.setBLEMTU(512)` 实际返回、

- **G1 设计修正（2026-10-26 自测发现）**：`sessions_invalidated` 去重从 1s 时间窗口改为
  **按响应 id 去重**——受控改密卡"改密→恢复"两次作废可能间隔 <1s，时间窗口会漏掉第二次。

## 4. M 层：手机侧怎么跑（执行顺序）

分四段，前一段不绿不进下一段——避免把"环境问题"和"固件缺陷"混在一份报告里。

**M0 环境登记**（对应执行表 §1）
手机型号 / Android 版本 / 微信版本 / 小程序 commit / 协商 MTU / notify 分片实测值 / 日期 / 执行人。
MTU 这一栏必须写实测，不能写"未协商"糊过去。

**M1 基础连通**（#1 #2 #3 #15）
扫描 → 连接 → 四特征属性 → 订阅 → `device.info`（`protocol_versions`）→ `auth.login`
（记 token 长度 32、`expires_in=600`）→ 记录 `wx.setBLEMTU` 实际返回值与协商后 MTU。
这一段也是查"Android 定位权限/定位服务"的地方，扫不到设备先查这里，别急着报固件缺陷。

**M2 命令面**（#4 #5 #9 #7 #10 #6）
先跑 10 次 `network.scan`、10 次 `config.get`（看分片数与 JSON 完整性），
再跑长响应期间的 `operation.get`、cancel 幂等、duplicate/busy/槽位覆盖，最后错误口令。
错误口令放最后，因为它会污染 operation 槽的观测。

**M3 数据面与状态迁移**（#12 #13 #8 #14 #11 #16 #17）
DATA 矩阵 → 断连重连 token → 成功配网 apply → 无 AP 救援 → **最后做改密**。
改密的顺序是刻意的：#16 会把所有会话作废，放在最后就不用反复重登；
且改密必须用临时口令并在 `finally` 里恢复原口令，恢复后再验一次"原口令可登录"。

## 5. 回填规则（这一节是防止表格被填成"看起来 PASS"）

**状态只允许四个值**：`待测` / `PASS` / `FAIL` / `BLOCKED`。
- 不允许 `SKIP` 计入通过（执行表 §7 已写）。
- 不允许"部分通过"——一项里只要有一个子断言没过，就是 `FAIL` 并写清是哪一条。
- `BLOCKED` 必须写阻塞原因（无设备 / 无权限 / 依赖未修）。

**"关键证据"列的硬要求**：必须是从小程序报告里**能原样搜到**的值，不写概括词。
- 好：`10/10 次 id 全匹配，分片 56，最大帧 1107B`
- 差：`长响应正常`

**脱敏**：token、管理员/Wi-Fi 口令、SSID、BSSID 一律不入表、不入报告文件。
执行表 §1 已定，回填时逐行检查一遍。

**证据文件**（执行表 §8 建议的命名，我建议先落原文再填表）：

```
tools/ble_p0/results/t4a_android_<YYYYMMDD_HHMMSS>.txt   # 小程序导出报告原文，只读不改
tools/ble_p0/results/t4a_android_<YYYYMMDD_HHMMSS>.json  # 脱敏后的结构化汇总（可选）
docs/T4_A_Android微信验收_2026-10-26.md                  # 回填后的执行表
```

小程序导出的是文本报告，落盘靠复制粘贴，**没有自动通道**（小程序写不到 PC 文件系统）。

| 串口 | `/dev/ttyUSB0`（UART0 控制台/烧录）、`/dev/ttyUSB1`（UART1 数据） |

**WorkBuddy 沙箱内的预期基线（2026-10-26 实测）**：`ls /dev/ttyUSB*` 为空、`bluetoothctl` 不存在、
`/usr/bin/python3.12` 不存在（venv 解释器断链，`.venv-bleak/bin/python` 无法执行）、`git` 不存在。
以上各项在沙箱内失败属预期，不是环境异常；失败即按 §9.7 对应行标 `BLOCKED`，不要试图在沙箱内修复。

### 9.2 硬件与端口

| 端口 | 用途 | 参数/注意 |
| --- | --- | --- |
| `/dev/ttyUSB0` | ESP32 UART0：ESP_LOG 控制台 + `idf.py flash` | 115200 8N1；烧录会复位；不要与 monitor/capture 同时占用 |
| `/dev/ttyUSB1` | UART1 外部数据面（GPIO17 TX / GPIO18 RX） | 115200 8N1；用于 `t3_uart1_datapath.py --uart-port /dev/ttyUSB1`；**不要拿它烧录** |
| `hci0` | PC BLE central（BlueZ） | 仅旁证；不能替代 Android 微信 |

两个串口都是 **CP2102**，`/dev/serial/by-id` 可能只有一个稳定链接；不要只靠 by-id 区分，按当前 `ttyUSB0/ttyUSB1` 和启动日志确认。当前用户 `tc` 在 `dialout` 组；若打开失败先查组/权限，不要直接 `sudo`。

设备标识：经典 MAC `b0:a7:32:28:c8:e4`（Wi-Fi/OTA），BLE 地址 `B0:A7:32:28:C8:E6`；PC BLE 脚本和手机扫描都用后者，不要混用。

串口占用/复位注意：

```bash
fuser -v /dev/ttyUSB0 /dev/ttyUSB1   # 烧录/监视前确认没有 capture/monitor 占用
```

- 串口抓包用 `tools/capture_serial.py`，它会保持 `dtr=False/rts=False` 并清 HUPCL；用 `cat` 或默认 pyserial 可能把板子复位。
- 打开串口仍可能触发一次复位，日志以该次启动为起点。
- `idf.py monitor` 与 `flash` 不能同时占用 `/dev/ttyUSB0`。
