## 0. 两个失败类别（贯穿全方案的分类原则）

| 类别 | 定义 | 例子 | 恢复路径 |
| --- | --- | --- | --- |
| **A. 配置应用失败** | Wi-Fi/netif/DHCP/DNS API 返回错误，或参数未过校验 | `esp_netif_set_ip_info` 失败、缺 `sta_static_ip`、`dhcpc_stop` 失败 | 配置层处理：拒绝保存 / 启动回滚 / fallback DHCP |
| **B. 配置应用成功但网络不可用** | API 全部成功，但地址冲突/网关不可达/DNS 不通 | ARP 冲突、网关无响应 | 运行时观察：状态上报 + 人工/回滚介入，不自动反复重试 |

所有 P0/P1 工作都按这个分类设计：A 类必须"不可能把设备带进不可恢复状态"；B 类必须"可见、可判、可人工恢复"。

## 阶段 1（P0）：启动安全 + 校验 + 持久化回滚

### 1.1 启动失败不再 abort

**现状**：`main/wifi.c:2385` `ESP_ERROR_CHECK(app_apply_wifi_config())`，静态配置应用失败 → abort → 重启循环。

**设计**：新增带结果的启动路径，失败按"恢复动作"处理，不中止系统：

```text
app_start_wifi():
    err = app_apply_wifi_config_boot()          /* 新封装，不 abort */
    if err == ESP_OK:
        正常继续
    else:
        record_boot_wifi_failure(err)           /* 失败阶段+错误码，进 status/日志 */
        attempt_wifi_fallback()                 /* 见 1.1.1 */
        /* 无论 fallback 成败，继续启动 BLE/MQTT/UART —— BLE 救援永远可用 */
```

**1.1.1 fallback 次序**（保证 netif 不停留在半配置状态）：

```text
attempt_wifi_fallback():
    1) 尝试恢复 DHCP：
       esp_netif_dhcpc_stop 忽略 ALREADY_STOPPED →
       esp_netif_dhcpc_start（若已 STARTED 视为成功）→
       esp_wifi_set_config(旧 SSID/口令) → esp_wifi_start
    2) 若 DHCP 恢复失败（esp_wifi_start 等硬错误）：
       esp_wifi_stop() 归位，置 network_config_state="offline_pending_config"
       —— 设备保持离线待配置，BLE 完全可用；不重启循环
    3) 不自动清除静态配置字段（保留现场供诊断），仅本启动会话按 DHCP/离线运行
```

**1.1.2 失败记录**：新增 `wifi_boot_failure{stage, esp_err}` 写入运行时（stage ∈ {wifi_stop, set_mode, set_config, static_parse, static_set_ip, wifi_start}），`network.status` 暴露（阶段 2），日志 `ESP_LOGE`。

**验收**：注入非法静态 IP（如掩码非法或 IP=网关，见 1.2 拦截前用 NVS 直写构造），设备必须：单次启动、无 abort 循环、BLE 可连可配置、`config.get` 仍显示静态字段、重启后仍能进入该状态。

### 1.2 应用前完整语义校验（配置层 A 类拦截）

**位置**：`main/config_apply.c` 的 `cfg_validate_static_ip_cross()`（现 242-285 行）扩展；`config_apply_patch` 与 `config_apply_json_validate` 两条路径自动共用。

新增规则（**不假设 /24**，按实际掩码计算）：

1. 掩码连续性：掩码主机位必须全 1 前缀（`~ntohl(mask)+1` 为 2 的幂且非零）。
2. IP 与网关同网段：`(ip & mask) == (gw & mask)`。
3. IP ≠ 网络地址（`ip & mask` 不得等于网络号本身……即 `ip` 主机位非全 0）。
4. IP ≠ 广播地址（主机位非全 1）。
5. IP ≠ 网关。
6. DNS 非空时合法（已有）。

错误文案带字段名（复用现有 `err_size` 机制），保证 App 能映射为"配置校验失败"。

**验收**：v0 `config.set` 分别提交 `255.0.255.0` 掩码、跨网段网关、IP=网络地址、IP=广播、IP=网关，均被拒且 `changed=[]`、NVS 不落盘。

### 1.3 持久化 pending/rollback（核心）

**问题**：`config_apply_patch` 先 `app_config_save` 再换内存（`main/config_apply.c:837-843`），NET 域 apply 为空操作、靠 reboot 生效。断电/启动失败时旧配置已被覆盖，无回滚。

**设计**：NET 域 reboot-effect 补丁改为"两段提交"：

```text
VALID_CONFIG（现有 NVS 主配置，永远是"最近一次验证通过的配置"）
     ↑ confirm                                   │失败/超时
     │                                           ↓
PENDING_CONFIG ──重启应用──→ 网络验证窗口 ──→ ROLLBACK_TO_VALID
```

**NVS 键**：

- 现有主配置键：不动，含义升级为 VALID；
- 新增 `cfg_pending`：候选配置 blob + `pending_boot_id`（写入时自增的序号）；
- 确认即删除 `cfg_pending`。

**流程**：

```text
提交侧（config_apply_patch，net 域且 effect==REBOOT 且有实际变更）:
    save VALID 原样不动
    写 cfg_pending = 新配置
    内存切到新配置（供响应与重启后初值一致）
    返回 restart_required=true（现有响应字段不变）

启动侧（app_start_wifi 之前）:
    if cfg_pending 存在:
        以 pending 为当前配置应用（走 1.1 的可失败启动路径）
        进入验证窗口（见下）
    else:
        以 VALID 应用

验证窗口（成功路径）:
    GOT_IP（静态或 DHCP）且 ARP 冲突检测结束（或非静态直接通过）且
    [可选：网关 ARP 可达] → 删除 cfg_pending（confirm）

失败路径（任一）:
    - 启动应用失败（1.1 fallback 仍失败）
    - 窗口超时（默认 90s，覆盖现有 90s 启动连接窗口）无 GOT_IP
    - ARP 冲突 = conflict
    → 恢复 VALID：内存与 NVS 主配置不动（主配置从未被覆盖，只需）
       内存换回 VALID 配置 → 走 1.1 fallback（DHCP 优先）
       network_config_state="rollback_static"
       日志 ESP_LOGW + status 暴露
```

**断电/复位安全**：

- `cfg_pending` 落盘先于重启 → 任一时刻断电，重启都能看到 pending 并走验证/回滚；
- `pending_boot_id` 防"同一次 pending 反复回滚"：回滚后清 pending；连续 N 次（建议 3）pending 失败则不再自动应用 pending，直接以 VALID + DHCP 启动并记录（防闪烁循环）。

**与 `empty_keeps` 的交互**：pending blob 是完整配置快照，不依赖 patch 语义，规避空串保留旧值的歧义。

**验收**（板级）：

| 用例 | 预期 |
| --- | --- |
| 正确静态参数 + 重启 | GOT_IP → confirm，pending 删除，重启后仍静态 |
| 静态参数语法合法但网关不可达（B 类） | GOT_IP 成功、窗口通过（无网关强制项）→ confirm；冲突/超时路径由 1.4 覆盖 |
| NVS 直写非法静态 → 重启 | 单次启动失败记录 → fallback DHCP → rollback 状态可见 |
| pending 应用失败 → 重启 | 回 VALID + DHCP，BLE 可用 |
| pending 窗口内断电 | 再次上电仍走 pending 验证/回滚，不丢 VALID |
| 连续 3 次 pending 失败 | 第 4 次起直接 VALID + DHCP，状态可见 |

### 1.4 静态模式下 tryconnect 隔离（调用侧 guard）

**现状**：`app_wifi_try_connect_common()` 不改 netif；静态候选继承静态地址，结果未定义。

**设计（阶段 1 取拒绝，最安全）**：`network.tryconnect` 入口（`main/cmd.c` 同步与 async 两处）在 `sta_use_static==true` 时直接返回新错误串 `static_ip_mode`（v0 字符串；v1 映射 `forbidden`，走现有 `app_ble_cmd_v1_error_code` 表新增一行）。

- **不改 `main/wifi.c` 的 tryconnect 生命周期**；
- 拒绝发生在 `app_wifi_try_connect_common()` 之前，无锁/状态交互；
- "trial 临时 DHCP"语义留到后续版本再评审，本期不实现。

**验收**：静态模式下 BLE 发 `network.tryconnect` → 立即 `static_ip_mode`/`forbidden`；DHCP 模式不受影响（回归一次错误口令用例确认无变化）。

### 1.5 DNS 设置/清理统一

`app_configure_sta_static_ip()`（`main/wifi.c:539-594`）修改：

- DNS1/DNS2 为空 → 显式 `esp_netif_set_dns_info(MAIN/BACKUP, {0})` 清空，不再跳过；
- 每次设置后 `esp_netif_get_dns_info` 回读校验，失败记录 stage 错误（进 1.1 的失败链，允许回滚）；
- `dhcpc_stop` 失败（非 ALREADY_STOPPED）→ 记 stage 错误并中止静态应用（触发 1.1 fallback），**不再带病继续 `set_ip_info`**；
- 切回 DHCP 时：DHCP 续约覆盖 DNS 属 IDF 行为，加入阶段 3 板级验证项（清零后由 DHCP 覆盖）。

**验收**：静态 DNS 空 → 回读为 0.0.0.0；设置非空 → 回读一致；`dhcpc_stop` 失败注入 → 不落半配置。

## 阶段 2（P1）：运行时可观察性

### 2.1 `network.status` 新增字段

```json
{
  "sta_use_static": true,
  "sta_static_ip": "192.168.1.50",
  "sta_gateway": "192.168.1.1",
  "sta_netmask": "255.255.255.0",
  "sta_dns_main": "192.168.1.1",
  "sta_dns_backup": "",
  "sta_ip_conflict": "clear",          /* unknown | clear | conflict */
  "network_config_state": "static"     /* dhcp | static | pending | rollback_static | offline_pending_config */
}
```

实现要点：

- 配置字段从 `s_config` 快照（现有 `app_config_lock` 模式）；
- `sta_ip_conflict` 改为三态：检测任务未跑 = `unknown`，结束无冲突 = `clear`，冲突 = `conflict`（`runtime.h` 现有 bool 升级为枚举，`main/cmd.c:643-715` 构建函数补输出）；
- ARP 检测自身 MAC 获取失败（`main/wifi.c:429-433`）时置 `unknown` 并记日志，不得默认判冲突；
- `network_config_state` 由阶段 1 的启动/回滚/confirm 路径驱动，是唯一状态源（避免多处写）。

### 2.2 冲突检测语义固化

- 时机：仅静态模式下 GOT_IP 后启动一次（现状保留）；
- 超时：3×400ms 探测 + 1s 等待（现状保留），结果只影响状态不触发断网；
- 误报缓解：自身 MAC 比对保留；`esp_wifi_get_mac` 失败 → `unknown`；
- B 类边界写明：conflict 不自动断网/回滚（阶段 1 回滚只由"应用失败/无 GOT_IP"触发；conflict 是否触发回滚列为开放问题，默认不触发，由用户经 BLE 处理）。

**验收**：DHCP 模式下所有新字段存在且 `sta_use_static=false`、`conflict=unknown`；静态模式三轮采样字段一致；冲突用例（同网段另置同 IP 设备）报 `conflict` 且连接不中断。

## 附录 A：第二轮评审补充（2026-11-02，方案冻结条件）

评审结论：阶段 1 启动安全/两段提交/tryconnect 隔离/DNS 语义校验/阶段 2/阶段 3 均通过，附以下约束；M0 已执行（见 [静态IP_M0取证报告](静态IP_M0取证报告_2026-11-02.md)）。

### A.1 启动恢复状态机（固定次序，不允许无条件重启兜底）

```text
1) 读取并校验 VALID 配置
2) 若存在 cfg_pending：判定其归属（pending_boot_id / 待确认标记）
3) 应用 pending；失败 → 记录 stage+errno（wifi_boot_failure）
4) 恢复 VALID；VALID 为静态且应用失败 → 降级 DHCP（仅本次启动会话）
5) DHCP 初始化仍失败 → 离线待配置（offline_pending_config），BLE 救援可用
6) 禁止用无条件重启掩盖任何恢复失败
```

**降级 DHCP 是运行时救援，不得改写 NVS 的 VALID 配置**；静态字段保留现场，`network_config_state="fallback"` 供排查。

### A.2 两段提交确认条件与断电表

- **确认条件**：窗口内 GOT_IP **且** `sta_ip_conflict == clear` 才 confirm；`unknown` 不等于 `clear`，不得确认（进入超时/回滚路径）。
- **窗口起点**：配置应用成功（`esp_wifi_start` 返回 OK）、开始网络验证时起算，不从 boot 计时。
- **失败计数**：`pending_boot_id` 按启动周期计数；确认成功、pending 删除后归零；连续 3 个启动周期失败 → 熔断（直接 VALID+DHCP 启动并记录）。
- **断电恢复表**（实施时必须逐点验收）：

| 断电时机 | NVS 状态 | 上电行为 |
| --- | --- | --- |
| VALID 写入前 | 旧 VALID | 正常启动 |
| VALID 写入后、pending 写入前 | 新配置已是 VALID（现有 config_apply 语义） | 直接应用，无 pending |
| pending 写入后、重启前 | VALID + pending | 上电走 pending 验证 |
| pending 应用中 | 同上 | 走 pending 验证/回滚 |
| 窗口内、confirm 前 | 同上 | 同上 |
| confirm（删 pending）后 | 仅 VALID | 正常启动 |
| 回滚执行中 | VALID 未动 | 上电重走 pending 验证（或已熔断则 VALID+DHCP） |

### A.3 tryconnect guard 必须全入口

M0#3 已确认调用点全集：`main/cmd.c:1875`（v0 同步）与 `main/cmd.c:275`（v1→async worker）；v1 映射经 `main/ble_cmd.c:346-348` 汇入 async。guard 落在 `main/cmd.c` 两个调用点（或统一前置 helper），覆盖所有入口；不触碰 `main/wifi.c` 生命周期。可独立实施。

### A.4 语义校验与特殊掩码

按实际掩码计算（不默认 /24）；**/31、/32 本期明确拒绝**并返回带字段名的错误（设备场景无点对点需求，显式拒绝优于套用普通子网规则）；DNS 空值显式清零+回读；`dhcpc_stop` 失败立即中止静态应用。IDF 在静态设置时已自动清 DNS（esp_netif_lwip.c:2053-2055，M0#1），显式清零保留为双保险。
