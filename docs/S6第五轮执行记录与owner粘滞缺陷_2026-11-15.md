## 2. 决定性发现：Wi-Fi owner 自第一轮起粘滞在 CLEANUP

### 2.1 证据（串口，同一份日志）

```
# 唯一一次 owner 进入 CLEANUP（第一轮，BLE 断连触发取消）
I (8122661) wifi: op_owner: TRYX -> CLEANUP by tryconnect_release waiter=0 requested=0
# 此后 3.5 小时再无任何 owner 转移：
#   op_owner 行共 36 条，最后一条即上条
#   全日志计数：cleanup complete=0、cleanup failed=0、cleanup watchdog=0
# 三轮 tryconnect 全部撞同一状态：
W (15096691) wifi: owner denied: caller=tryconnect_begin reason=wait_timeout owner=CLEANUP   # 第三轮
W (18790271) wifi: owner denied: caller=tryconnect_begin reason=wait_timeout owner=CLEANUP   # 第四轮
W (20499911) wifi: owner denied: caller=tryconnect_begin reason=wait_timeout owner=CLEANUP   # 第五轮
```

⇒ 第三/四/五轮的 `connect_failed` **不是 AP 问题、不是稳定性门禁问题**，而是
**owner 自第一轮起永久停在 CLEANUP**，任何 STA 操作（tryconnect）都无法取得所有权。

### 2.2 代码定位（dc254d5）

| 位置 | 事实 |
| --- | --- |
| `wifi.c:326 app_wifi_owner_step_ev()` | **只有这个包装函数**在 `act==NOTIFY/HANDOVER` 时设置 `s_wifi_restart_kind = CLEANUP` 与 `s_wifi_cleanup_started_ms`（约 340–345 行） |
| `wifi.c:254 app_wifi_owner_step_locked()` | 纯状态迁移，**不含**上述记账 |
| `wifi.c:635 app_wifi_tryconnect_release()` | 直接调用 `step_locked(RELEASE_TRYX)` → owner 迁移到 CLEANUP，但 **restart_kind 仍为默认 APPLY、`s_wifi_cleanup_started_ms` 仍为 0** |
| 同函数尾部 | `app_wifi_restart_wake()` 失败仅 `ESP_LOGE` 记录，**无回退到 NONE 的分支** |
| `wifi.c:4418 restart 任务` | 读 `s_wifi_restart_kind`；因是 APPLY，走 APPLY 分支（不产生 cleanup 终态）→ **owner 永不释放** |
| monitor 看门狗 | 依赖 `s_wifi_cleanup_started_ms != 0`；因未被置位 → **看门狗不生效**（日志 0 次 watchdog，实测吻合） |

**结论**：B1/C2 handover 的记账被放在了 `step_ev`，而释放路径用的是
`step_locked` → 交接后 restart 任务类型错误 + 看门狗失效 → owner 永久 CLEANUP。
这是**本轮修复（0eb30ce）引入的路径缺口**，不是偶发。

## 3. 影响

1. **expired / op-V 分支在本设备上不可达**（直到 owner 清态）——三轮窗口因此全部空转；
2. 该缺陷会让**现场任何 BLE 断连打断 tryconnect 后，设备永久无法再发起 STA 操作**（只能靠重启恢复），属**用户可感知故障**（换网、重连全失效）；
3. 协议层不可观测（`network.status` 无 owner 字段），只能从 console 看见——现场排障困难。

## 4. 修复建议（待评审/另立任务）

**最小修**：把 handover 记账 **移入 `app_wifi_owner_step_locked()`**（或在该函数内
提供统一出口），使所有调用者（含 `tryconnect_release`）在 `act==NOTIFY/HANDOVER`
时同时设置 `s_wifi_restart_kind=CLEANUP` 与 `s_wifi_cleanup_started_ms`；
并为 `restart_wake()` 失败增加**回退到 NONE**（与 C2 的"schedule 失败回退 NONE"一致）。
**增强**：`network.status` 增加只读 `wifi_owner` 字段（评审 C 项），使同类粘滞可被机器观测。

## 5. 复测前置

owner 是 RAM 状态 → **需重启 C8E4 清态**（并重置 uptime 锚点，需重新建立稳定窗口基线）。
重启后若不在 tryconnect 期间断 BLE，本轮流程可正常执行；但**缺陷未修前，同类故障会复发**。
