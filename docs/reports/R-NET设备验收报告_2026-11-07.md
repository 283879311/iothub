## 3. 过程中发现的新缺陷（如实记录）

### F1（实锤）：poke 打不断 restart 任务的高退避 delay

churn 期间 MQTT 重连反复失败把 `s_restart_backoff_step` 顶到高档（20/30s）。
恢复 broker 后 netcheck 的 `app_mqtt_poke_restart()` 只把 step 归零 + notify——
**notify 不会打断 restart 任务正在执行的 `vTaskDelay(20~30s)`**，请求只是排队。
实锤序列（uptime）：269.4s GOT_IP → 创建 restart 任务 → 273.6s `mqtt not up after grace -> poke restart`
→ **此后到 293.7s 无任何 attempt/Starting 日志** → 293.7s 任务被 stop 位杀掉（见 F2）。
净效果：churn 后 MQTT 不自愈，需要再等一个完整退避周期 + 一次链路循环才恢复
（本次 794s 时 `ok gen=43` 自愈确认，非永久卡死）。
**修法（P2，约 10 行）**：restart 任务的退避 delay 分片化（≤1s 步进，每片检查 notify/step/stop）。

### F2（疑点）：stop 位来源不明

293.7s 重启任务以 `Restart task exiting on stop event` 退出，但该位唯一 setter 是
`app_mqtt_stop`（mqtt.c:1587），其唯一调用者是 STA_DISCONNECTED 处理器——而 264s 后
无任何 Wi-Fi 事件。`app_mqtt_stop` 在 `has_restart=false` 时也不置位。setter 无法解释，
原始日志已归档待复现取证。与 F1 叠加造成"MQTT 停摆 ~8 分钟（264s→794s 自愈）"。

### 过程性修复（harness/broker 工具侧，非固件）

- **mini_broker.py（新，`tools/broker_local/`）**：路由型最小 MQTT 3.1.1 broker
  （amqtt 已被 teardown 清掉且 venv pip 损坏）。两个真 bug 当场修：固定头误读 2 字节

## 7. 【增补】N06 撞出结构性冲突：R2 门 vs tryconnect 拆链模型（2026-11-07 12:0x）

### 7.1 现象与机制（串口完整证据，`serial_n06.log`）

新镜像 `cfcc1d25…` 上 N06（tryconnect 真实 AP）三次运行全部回滚：

```
71.8s 候选拿到 IP → 试用路径启动 netcheck(gen4)
72.4s try_connect_common 收尾：按冻结设计拆候选(disconnect+restore old_cfg)
      └─ 拆链事件落回主路径(此时 trial 已 release) → gen++ + cancel(gen4)
72.4s worker 返回 TRY_OK → 等 gen4 判决 → CANCELLED → 二次 R5 → 回滚
      (rescue=restore_persistent，两次运行均触发)
```

**根因**：tryconnect 模型 = "验证可连 → **立即拆候选** → 回旧网"，候选链路在
TRY_OK 时刻已不存在；R2 门要求"在候选链路上完成 broker 验证后才交付
GOT_IP"，验证需 4-8s，拆链在 0.5s——**门结构性必输**。阶段 0 评审备忘
（§背景 line 22/27）早已预告此依赖（"缺 INTERNET_CHECKING 状态与 apply
完成回调"）。

**附带收获**：两次回滚把 **netcheck-fail → FAILED(INTERNET_UNVERIFIED) →
rescue=restore_persistent → 旧链路重验 settle** 的 R2 失败全链在真机跑通了
（触发源是 GOT_IP 后路由未就绪瞬态 + 拆链竞态，同一代码路径）；36/1/3 的
唯一 FAIL 即此，其余 37 项在新镜像上无回归。

**影响面**：当前镜像上所有走到 GOT_IP 的 tryconnect op 都会回滚（BLE/MQTT
同）。C8E4 静态锁定不受影响（tryconnect 被 pin）；**65D8（DHCP）升级前必须
先修**。auto-poll(R1) 与 apply 兜底不受影响。

### 7.2 处置选项（需裁定）

| A 回退 | 撤 tryconnect 路径的 worker 门，GOT_IP 回"候选可连"语义；R1/apply 兜底保留 | R2"验证后才提交"落空（回阶段 0 语义），~5 行 |
| **B 有界推迟（推荐）** | 冻结流的"拆链必然发生"保留，但 TRY_OK(require_ip) 且 netcheck 在飞时，拆链**推迟到判决出炉**（上限 25s，可被 cancel 打断）；netcheck 增加按代次归档的终局快照（done_gen/outcome，不被新 start 覆盖）；worker 改读快照 | ~40 行；期间设备停在候选 AP（P3 已记录的预期行为）；不碰事件归属状态机 |

## 11. 【panic 根因与闭环】SCAN_DONE 互斥量跨任务信号 → 二值信号量（2026-11-08 11:5x–12:2x）

### 11.1 事故与根因

干净环境（MM 已卸载）fullflow×3 全部失败：串口取证 `reset_reason: "panic"` +
`assert failed: xTaskPriorityDisinherit tasks.c:5156`，op 表随重启清空导致客户端
`not_found`（客户端预算误判假象，真因在固件侧）。痕迹 ×16（ELF 27361e822 三轮）。

**根因是 R-SCAN-3 的实现错误（我侧）**：SCAN_DONE 跨任务信号用了
`app_mutex_ensure`（互斥量）——事件任务 give、命令任务 take。互斥量的
优先继承协议要求 give 者=持有者，give≠持有即触发断言 panic。跨任务信号
的正确原语是二值信号量（无所有权语义）。

### 11.2 修复（commit 5c271ae，镜像 `1.3-5c271ae` / build_sha `e69b224a7`）

`main/wifi.c`：`s_scan_done_sem` 改 `xSemaphoreCreateBinaryStatic`（一次性
创建，事件任务 give、命令任务 take），删除 `s_scan_done_mux` 与三处
`app_mutex_ensure` 包装；保留 take 前排空陈旧计数与 15s 有界等待。

> **镜像身份勘误（2026-11-08 12:4x）**：本节初稿记 `936dcbe8f`——那是构建
> 中间态（链接两遍之间）对 ELF 的陈旧测量。稳定身份以设备自报
> `device.info.build_sha` 为准：`5c271ae` 镜像 = **`e69b224a7`**（bin sha
> `e31d8c7d2`），与烧写产物现算一致。后续一律以"设备自报 = 现算"双对账为准。

### 12.1 现象（用户套件 12:38 报告 `5/7`，BLE 源）

### 12.2 根因：P6 快照读活标志，而拆链正在摧毁它

拆链后读活标志 = 自伤竞速：判决真值（read_done 判决，worker 在手）被丢弃。

| --- | --- | --- |
| MQTT 源（BLE 仅广播）轻载 | worker ~30ms 内赢 | apply 放行（我 3/3） |
| BLE 连接态（套件轮询，NimBLE 洪泛） | 事件延迟 ~60ms，worker 输 | P6 全 false → gate 误拒（用户轮） |
