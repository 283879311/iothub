内部状态流程（**唯一实现** `read_mac_flow()`，回滚门禁复用同一函数）：

0. **协作锁按串口唯一**：`capture_serial.py` 启动即持
   `/run/lock/iothub_serial_<规范化端口名>.lock` 的 `flock(LOCK_EX)`（取不到 → 退出码 3，
   不打开串口）；门禁用 `port_identity.port_lock_path()`（**同一函数**）计算同一路径来
   试探/持有。**同串口不同日志路径的两个采集争同一把锁**，第二个拒绝启动。
1. 检查录制链（六子项）——不完整则**不停录制、不读 MAC**，直接失败；
2. 停录制（`serial_capture_ctl.sh stop <port> <log>`）；停后用**三态判定**
   （`capture_state()`，独立于完整链校验）：
   - **RUNNING**：端口锁被持有 / 旧版采集的 `<log>.lock` 仍被持有 / PID 文件进程仍存活
     → 不读 MAC；
   - **COOPERATING_CAPTURE_STOPPED**：端口锁可取得且无 PID 进程存活
     → **仅表示"协作采集已停"**，可进入第 3 步（仍需满足第 3 步的两个条件）；
   - **UNKNOWN**：锁打不开/加锁出错、PID 文件存在但不可解析、无 log_path、scanner 异常
     → **不读 MAC，STOP**。
   **语义边界（必须如实理解）**：`COOPERATING_CAPTURE_STOPPED ≠ PORT_FREE`。
   协作锁只约束遵循本协议的进程（本仓库采集与门禁），**不能排除** minicom、手工 `cat`、
   其它 esptool、旧版/非本仓库程序仍占用串口。因此证据里 `port_free_proven` **恒为 false**，
   校验端强制要求它为 false；任何把该状态描述成"端口已证明空闲"的说法都超出代码能力。
   **UNKNOWN 是终止态**：不读 MAC、不启动录制、不继续任何测试，标记"设备/录制状态待人工处置"，
   人工确认（端口无进程占用且设备可正常启动）后方可重新执行步骤 0。
   stop 命令返回失败但三态为 COOPERATING_CAPTURE_STOPPED 时**仍必须恢复**；
3. **两个互相独立的读 MAC 条件（缺一即拒绝）**：
   a) 本流程按**串口**唯一**成功持有端口锁**（读 MAC 期间任何协作采集都无法启动；
      锁在 `esptool run` 完成后、重启录制前释放）；
   b) `--attest-no-external-holder "<说明>"`：操作者显式声明无外部工具占用该串口。
      这是**授权前提**，不是软件证明；说明原文写入证据 `attestation_note`；
4. `esptool read_mac`；
5. **无论 read_mac 成功/失败/MAC 不符，都执行恢复**：`esptool run` → **释放端口锁** →
   重启录制 → 等待新 boot 证据（`rst:0x1`/`app_init ELF SHA`，≤15s）；
6. 成功条件 = MAC==65D8 **且** 端口锁已持有 **且** 操作者已声明 **且** run 成功
   **且** 录制重启成功 **且** 新 boot 证据出现；
7. 恢复证据写 `<evidence-dir>/mac_read_flow.json`（attempted）与
   `mac_read_flow.final.json`（**最终状态**，成功后二次写入以保证磁盘与返回值一致）；
   **写入失败即判失败**，并**尽力把失败结论回写首份证据**（避免磁盘残留"无结论"快照）；
   恢复后再次三态校验必须为 RUNNING，否则判失败；启动前先确认未在运行（避免重复 start）；
8. **门禁消费端强制校验**（`port_identity.validate_final_evidence()`）：
   `run_id`（**时间 + uuid8，唯一**）/ `port` / `mac` / `evidence_write_result=="ok"` /
   `mac_ok` / `state_after_stop==COOPERATING_CAPTURE_STOPPED` /
   `port_lock.acquired is True` / `external_holder_attested is True` /
   `port_free_proven is False` / `errors` 为空 / 恢复字段（`state_after_restore==RUNNING`、
   `run_app_ok`、`capture_restarted`、`new_boot`、`record_written`）/ 时间新鲜度 ≤240min
   **全部**通过；任一项不符即判失败。**证据目录必须本轮全新**：目录内已存在
   `mac_read_flow.final.json` / `mac_read_flow.json` / `mac_record_gate.json` /
   `rollback_gate_last.json` 任一 → 直接 rc=2 拒绝（防旧终态冒充本轮）；
9. 失败时明确输出"设备/录制状态不可确认，不得继续"。

步骤 1 的 `preflight --emit-anchor` **必须同时给 `--mac-record`**，校验记录
（严格 `version==1`（排除 bool）/端口/日志目录/MAC==65D8/时间戳数值/新鲜度）
通过后才写锚点（`mac_ok=true`），否则 **rc=2 拒绝写出**。

`esptool read_mac` 要求"协作采集已停 **且** 端口锁已由本流程持有 **且** 操作者已声明
无外部占用"（三者合起来才有资格读），流程已内置停/启录制与先取锁；它会让芯片进下载模式。
因此：**步骤 0 内**先校验录制链（运行中）→ 停录制（记计划内 gap）
→ 持端口锁 `read_mac`（记录 MAC）→ `esptool run` 回 app → 释放锁 → 重启录制 → 再做六维 ×2。
该 MAC 作为步骤 1 锚点的 `mac` 字段与回滚门禁的比对基准。

**证据归档要求**：每轮采集必须记录 ①BLE 采集时间戳 ②对应 console 行号
③console uptime——写入 `000_identity_gate.json`；仅记录结论不足以复核。

辅助证据（非实时）：POWERON 锚点（phaseA 日志）、`baseline_before_flash.json`。
**"六维身份 ×2"采集方法与 console 关联**：同一 BLE 会话内**间隔 20s 的两次独立
采集**（每轮各含 device.info/device.status/network.status/config.get 原始帧）；
两次逐维比对。**与 console 证据的关联**：BLE 可直接证明维度 1/2/3/6；
维度 4（串口映射）与维度 5（boot 会话）**必须结合 console 日志**——每轮采集
记录时刻，与该时刻 console 的 uptime 时间戳交叉核对，确认两轮落在同一 boot
会话内。**六维中有两维不能仅靠 BLE 命令证明**，必须结合 console 证据。

## 3. 停止条件与异常闭环

**两类 STOP 语义（区分）**：

| 语义 | 含义 | 后续动作 |
| --- | --- | --- |
| **测试 STOP** | 立即停止后续测试步骤与新的故障注入；保存当前证据 | **进入恢复路径**（§3.1，授权范围内） |
| **恢复失败 STOP** | 回滚烧录或回滚后身份反证失败 | 停止所有其他操作，标记设备未恢复，等待进一步处理 |

### 3.1 恢复路径触发范围（**所有已改变/可能改变设备状态的异常**）

**触发范围**：

| 触发点 | 情形 |
| --- | --- |
| FI 烧录 | esptool 写入中断/报错（设备可能部分写入） |
| 烧录后身份反证 | `device.info.build_sha ≠ 55c00628f` |
| R4a / R4b / R6 | 任一测试失败 |
| 录制中断 | **非计划**中断（进程退出/设备异常）且证据链无法恢复；**计划内 gap**（烧录/复位前后按流程停启录制并记 `flash_gap.log`）**不算**录制中断 |

**例外（可直接 STOP，无需回滚）**：烧录前门禁失败、尚未写入 Flash 且无设备状态改变。

R4a / R4b / R6 任一项失败时：**允许回滚，但不允许继续后续测试。**

恢复路径（按序执行，全部在本授权范围内）：

| R | 动作 | 判据 |
| --- | --- | --- |
| 1 | `diag.m1hook {action:"clear"}`（清除残留注入）→ `status` 确认 `restart_wake_fail=0 && cleanup_hold_ms=0` | 不符 → 记录并继续（注入残留如实标注） |
| 2 | **回滚门禁（强制前置，v2 芯片 MAC 口径）**：`rollback_gate.py --port /dev/ttyUSB1 --log-dir <本轮目录> --anchor-file <步骤1锚点> --bin <回滚镜像> --expect-bin-sha256 047e…ea41 --evidence-dir <本轮证据目录>` → **rc=0 才**执行 `flash_frozen.sh`。判定链：①锚点可解析+新鲜+端口/日志目录一致+**锚点 MAC == 65D8** ②回滚 BIN sha ③录制链六子项(script/port_arg/log_arg/fd_port/fd_log/running) ④日志 fresh+boot_marker ⑤**停录制后 `esptool read_mac` == 锚点 MAC == `10:97:bd:d3:65:d8`**（芯片 eFuse MAC，**app 挂掉也可读**；不用 dev:inode/st_rdev/by-id）⑥dmesg 补充（可读且见 USB 事件则拒绝） | 门禁 rc≠0 → **恢复失败 STOP**（禁止写入）；**不得**因回滚 BIN sha 正确推定设备正确 |

**门禁实现约束（v7）**：①锚点必须是**非空字典**且含 `version/port/log_dir/mac/checked_at_unix`并按类型校验（空 `{}`、缺字段、类型错误、过期均拒绝）②阈值 `--max-anchor-age-min` / `--usb-events-min` **不得放宽**（>240 直接 rc=2）③**无 `--force-mac-read` 之类旁路**④读 MAC 走**同一** `read_mac_flow()`（含 finally 恢复与新 boot 证据），恢复结果写 `<evidence-dir>/mac_read_flow.json` + `rollback_gate_last.json`；**证据写入失败即判失败**；`--evidence-dir` 为必填；`--skip-restore` 仅跳过"等待新 boot 证据"，仍会 run+重启录制
| 3 | 复位进 app → BLE 反证 `device.info.build_sha == a7e04b6a9` | 不符 → **恢复失败 STOP** |
| 4 | 确认 `trial=idle`、无活动 op、`mqtt_connected=true` | 不符 → **恢复失败 STOP**（不宣称恢复） |

**恢复失败时**：停止所有操作、保留全部证据（含冻结副本与 esptool 日志）、上报等待人工处理——设备标注为"未恢复"。

### 3.2 其余停止条件

1. 烧录对象与授权 SHA-256 不符（写入前紧邻复查拦截）→ **不写 Flash**；
2. 烧录后 `build_sha` ≠ `55c00628f` → **立即 STOP（含恢复路径）**；
3. 录制链不完整或证据缺失 → STOP；
4. 任何超出本申请范围的操作需求 → STOP 上报，不自行扩大。

## 3.3 operation_id 采集与关联（R4a/R4b/R6 通用规则）

1. **唯一来源**：每轮 tryconnect 的**受理响应** `data.operation_id`；
2. **非空校验**：取得后立即判空；缺失/为空 → **STOP**（不猜测、不用旧 ID）；
3. **单轮唯一**：记录到本轮证据（`000_ops_registry.json`，含 op 与步骤映射）；
   后续 cancel / `operation.get` **必须使用同一 ID**，发送前比对；
4. **三方关联**：BLE 受理响应、串口 `operation: accepted <op>`（行号+uptime）、
   `operation.get` 返回的 `id` —— 三者一致才认定同一 operation；不一致 → STOP；
5. R4b 步骤 7 的 `operation.get → failed/cleanup_failed` **必须使用同一 ID**；
6. **R6 同样适用**：触发 cleanup 的 op-ID 也登记进 `000_ops_registry.json`，
   其 `operation.get` 终态确认同样按 ID 一致性检查——R6 不得只记 cancel 响应
   与日志而遗漏所取消的 operation。

- R4a/R4b/R6 均以 `CLEANUP_FAILED` 粘性结束（属**预期结果**）；阶段 B 结束后执行步骤 10 回滚到功能镜像即清态；
- 若 FI 镜像异常无法启动：重烧回滚镜像（同脚本）；
- `erase-flash` 不在本授权内，如需另行申请。

## 6. 边界

请求：对 **65D8** 烧录 FI 镜像、复位、BLE/MQTT 测试命令、`diag.m1hook` 注入/清除、串口录制、临时复位、阶段末回滚烧录。
**不含**：C8E4 任何主动操作（仅 ttyUSB0 被动取证）、65D8 的 expired/op-V、`erase-flash`、配置变更、烧录其他镜像、并发操作。
授权仅覆盖**本轮单次**执行；执行完毕设备回冻结管理状态。
