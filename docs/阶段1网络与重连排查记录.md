# 阶段 1：网络与 MQTT 重连排查记录

> 日期：2026-10-21
> 固件：`feature/shared-config-cmd`，修复提交 `681d89b`
> 前置：G2 apply 已切到 `CMCC-502`，DHCP 获得 `192.168.1.42`；MQTT broker 已切到新地址

本轮边界：只处理网络/MQTT 重连，不改 Web、LittleFS、OTA，不做堆优化。

## 1. 对照测试：BLE 空闲时的网络与堆

硬重启后、BLE 未连接时：

```text
mqtt: Starting MQTT: uri=mqtt://...:21883
mqtt: MQTT connected
diag: heap free=15264 largest=14848 t=8s  ble_adv=1 ble_conn=0 mqtt=1
diag: heap free=13968 largest=9216  t=62s ble_adv=1 ble_conn=0 mqtt=1
```

手机连上 BLE，但两分钟不发送任何命令：

```text
bt_gatts: central connected ...
diag: heap free=13884 largest=9216 level=normal
mqtt_outbox=0 mqtt_shed=0
```

BLE 连接本身只带来约 100B 的可见堆变化；BLE + MQTT 并存时仍能稳定在
free≈13.9KB / largest≈9.2KB。此前把低堆直接归因于 BLE 连接是不成立的。

## 2. 低堆与 Web 登录活动的关联

旧日志中，堆从约 13.9KB 跌到 1.3KB 的时间段与 HTTP 登录/配置页请求重合：

```text
httpd_txrx: httpd_sock_err: error in send : 11
iothub: Client disconnected during login page: ESP_ERR_HTTPD_RESP_SEND
iothub: http get #1 / ...
httpd_parse: Unable to allocate the scratch buffer
httpd_parse: parse_block: request header too long
diag: heap new low: free=1376 largest=480
```

同一时段 MQTT 出现 `Writing didn't complete`、`No PING_RESP`，随后
`select() timeout`。因此当前证据更支持：**Web 登录/页面活动是触发堆塌缩的主要因素，
网络 broker 路径本身可用**。按本轮边界，Web 未修改。

## 3. 已修复：MQTT 重连自激循环

BLE 空闲测试中，一次正常的 MQTT 写超时后出现约每 8 秒一次的重建：

```text
MQTT_EVENT_DISCONNECTED
mqtt restart attempt (backoff step 1)
MQTT connected
MQTT_EVENT_DISCONNECTED
...
diag: heap free=2452 largest=1344 level=critical
```

根因：`app_mqtt_stop_clients()` 先把 `s_mqtt.client` 置 NULL，再 stop/destroy
旧客户端；旧客户端随后补发的 `MQTT_EVENT_DISCONNECTED` 仍会调度下一次 restart，
形成“stop 旧客户端 → 收旧事件 → 重启 → 再 stop”的循环。

修复 `681d89b`：断连事件只在 `event->client == s_mqtt.client`（当前客户端）时
才调度重连；旧客户端事件记录为 `stale client, ignored`，不再参与重连。

当前已烧录，启动验证：

```text
mqtt: MQTT connected
diag: heap free=14976 largest=14336 t=8s ble_conn=0 mqtt=1
```

## 4. 修复后强制重连验证

手机重新连接 BLE 后，先 `config.get` 查询，再通过 `config.set` 切换
`mqtt_backend` 强制走一次 MQTT stop/restart：

```text
I (462804) ble_cmd: rx method=config.set id=23
W (464834) mqtt: mqtt restart attempt (backoff step 1)
I (464944) mqtt: Starting MQTT: uri=mqtt://139.9.93.245:21883 ...
I (465724) mqtt: MQTT connected: subscribed RPC + shared attrs
I (482414) diag: heap free=13816 min=1588 largest=9216 level=normal
             mqtt_outbox=0 mqtt_shed=0
```

结果：

- 只有一次 `restart attempt`，一次 `MQTT connected`；
- 没有 `MQTT_EVENT_DISCONNECTED` 风暴，也没有 `stale client` 循环；
- BLE 保持连接，MQTT 恢复后 heap 回到约 13.8KB、largest 9.2KB；
- 遥测丢弃计数保持 0。

## 5. 阶段 1 结论

1. Wi-Fi、DHCP、IP 和 broker TCP 路径可用；新 broker 在 BLE 空闲时能稳定连接。
2. BLE 连接本身不是堆塌缩原因（约 100B 可见变化）。
3. 旧日志中的 1.3KB 堆低谷与 Web 登录/HTTP 页面活动重合；按本轮边界未修改 Web。
4. MQTT 重连自激循环已修复并由强制重连验证通过。
5. 当前 BLE + MQTT 稳态 heap≈13.8KB、largest≈9.2KB，未触发用户设定的
   “长期停留在 5KB”条件，因此不启动通用堆优化。

## 6. 遗留观察

- `min=1588` 的历史低点发生在本次强制重连前，当前 free/largest 已恢复，
  未观察到持续压力；若再次出现，需要单独归因。
- 此前 BLE 空闲时出现过一次 MQTT 写超时（`Connection already in progress`），
  1.3s 内自愈；本次修复后未复现，继续观察是否为 AP/broker 抖动。
- Web 登录路径仍可能导致堆塌缩，本轮按要求不处理。

## 7. 2026-10-27：运行时断网重连收口（现场验证 PASS + 残余缺口登记）

### 7.1 修复与现场验证

- 修复 `fa6182c`：启动窗口外断网后，原事件驱动链条在 `no untried saved AP left`
  处永久终止（不再产生断连事件，AP 恢复后无人再扫）。boot monitor 扩展为
  生命周期守卫：5/10/30/60s 封顶重试，每轮清 `attempted_mask`、fast path 先行，
  单一 `schedule_connect_task` 入口；BLE 连接期间跳轮（退避档暂停不重置）；
  `s_wifi_rt_armed` 只在启动窗口关闭后置位（防 STA_START 前抢跑）。
- 板上回归 `68ab9bc`：BEACON_TIMEOUT → 3 直连 → 一轮扫描 → 监视器 cycle 1–11
  （60s 档 ×8）→ AP 恢复 → cycle 11 回连 `got_ip` t=563s；BLE 门控实测
  （会话横跨到期点零 cycle，断连后 260ms 恢复 step=3）。
- **现场验证 PASS（2026-10-27 晚，用户操作）**：TQ2018 关闭 2–3 分钟后恢复，
  设备自动回连。同轮串口健康启动段已归档：
  `tools/ble_p0/results/runtime_retry_boot_20261027.log`（fast_path 1.3s 发起 →
  STA_CONNECTED 1.8s → GOT_IP 2.8s，118s 内零断连、MQTT 正常发布）。

### 7.2 串口端口枚举会翻转（运维注意）

2026-10-27 实测：USB 枚举顺序变化后 **UART0 落在 `/dev/ttyUSB1`**、UART1 落在
`/dev/ttyUSB0`（与 10-26 相反）。烧录/抓包前必须验证：对候选口跑
`python3 -m esptool --port <候选口> chip-id`，能读到 MAC `b0:a7:32:28:c8:e4`
的是 UART0。esptool 每次运行都硬复位设备并会打断进行中的 BLE 会话。

### 7.3 镜像核对方法与构建元数据陷阱

- 板上镜像核对：读 ota_0（0x10000，长度取自启动日志 app 大小）与
  `build/iothub.bin` 比 SHA256——2026-10-27 比对一致（`a247f8f2…`），确认板上
  运行当前构建。
- **陷阱**：增量构建不重编 `esp_app_desc.c.obj`，启动日志 `Compile time` 可能
  停留在旧构建日期（当时显示 Oct 23），不能作为版本证据。处置：①验收构建用
  clean build；②`PROJECT_VER` 改为配置期从 git 读取（`1.2-g<短SHA>[-dirty]`，
  `.git/HEAD|.git/index` 变化触发 cmake 重跑），启动日志/`device.info.firmware`/
  MQTT 遥测 fw_version 三处随之可辨识。
- flash 内残留一份旧构建的 core dump（app ELF SHA `92fade34a…`，与当前 ELF
  不匹配），非当前运行崩溃，暂不处理。

### 7.4 残余缺口登记（不阻塞 T4-A，修复另行立项）

以下三条均已源码定位、未修；共同点是"低概率触发、一旦触发运行期无自愈"。
现场回归（7.1）未覆盖它们，修复须各自带故障注入回归，勿与验收构建混提。

1. **D1 `s_wifi_sta_connecting` 卡 true**：fast_path/`connect_profile_index`
   先置 true 再调 `esp_wifi_connect()`；API 同步返回错误或后续扫描失败遗留时，
   无断连事件来清零。启动期会被 90s 失败路径收口（`stop_startup_connect_window`
   清标志），**运行期无超时回收**——一次踩中即永久停止调度。缓解方向：所有同步
   失败路径立即清零 + monitor 加 ~30s connecting 看门狗。
2. **D2 `apply_wifi_config` 早退后无人重跑**：set_mode/set_config/静态 IP/
   `esp_wifi_start` 任一失败直接 return（boot 路径有 `ESP_ERROR_CHECK` abort；
   `network.apply` 的 restart 路径只打一行错误即放弃）。monitor 只会重试
   connect，不会重跑 apply/start。缓解方向：apply 失败按退避重跑整个
   apply/start；增加 `sta_started` 门，STA_START 前运行期分支不跑。
3. **关联成功但无 IP 死点**：`STA_CONNECTED` 置 `sta_connected=true`，
   `sta_has_ip` 只在 GOT_IP 置位；运行期分支要求两者皆 false，DHCP 失败/
   热点不发地址时永久停在"关联无 IP"。未注册 `IP_EVENT_STA_LOST_IP`；启动
   90s 失败路径只停窗口不 `esp_wifi_disconnect()`。缓解方向：15s IP 宽限 +
   超时断开重试 + LOST_IP 处理。

**BLE 门控口径（既有决策，验收按此判读）**：BLE 连接期间运行期监视器跳轮，
退避档暂停（不重置）；BLE 会话内断网只保证事件链的 3 次直连 + 一轮 profile
扫描，不保证周期重试；BLE 断开后从暂停档继续。2026-10-27 现场验证在 BLE
未连接状态下进行。

### 7.5 附带事件：小程序断联（0x213）归因

2026-10-27 晚一次"小程序突然断联"经串口取证为**手机侧主动断开**
（`central disconnected (reason=0x213)`），触发链：`data.loopback` → DATA TX
退订/重订 → `network.status` 被设备拒 `auth_required`（同会话 83s，未到
600s TTL，设备侧无清 token 事件）→ 小程序退订并断链。设备侧鉴权行为符合
A 阶段契约，无需改动；修复在小程序侧（token 会话管理，WorkBuddy 负责）。
证据：`tools/ble_p0/results/ble_disconn_0x213_20261027.log`（已脱敏：
peer MAC/SSID/IP/broker 均掩码；无 token/口令内容）。
