# E1/E3 执行卡（DEF-MQTT-002 短期修验证，2026-11-05）

> 目的：用故障注入构建造出"run_fn 阻塞期间 op 到期"，验证解耦的 `op_expire` 任务与 R5 防线。
> 镜像：FI `884d4e6c08d034ccbe03e082741c7a9bf6b01eb9cad5b82f726b9ba235e1cbe7`（E1）
> 　　　FI+C1 `1721fe1caa36d9676f764c3dc08d678ebd16357c40ab765493db6a71d8c5490e`（E3）
> 生产镜像（非 FI）：`1237f0148b10154304ebb2e67a9cd4085d4a2ac2f081c23daad201ee736360c3`
> —— 与已验收 `eade9470…` 逐字节比较**只有 64 字节差异**：app descriptor 的 ELF-SHA（32B）与镜像尾部 SHA（32B，拆成 15+17 两段），可执行内容相同（源码行号位移导致 DWARF/ELF 哈希变化）。

## 1. E1：阻塞期间到期（核心）

### 布防顺序（必须严格按序）

1. 烧 FI 镜像；设备 MQTT 指向本地 broker（amqtt 或 `mqtt_ack_gate_inject.py --mode normal --pass <真实口令>`）。
2. BLE v1：`diag.m1hook` `{"action":"connect_hold","timeout_ms":10000}` → 期望 `hook_armed connect_hold ...`（若已有 hold 未结束会返回 `busy`）。
3. BLE v1：`diag.m1hook` `{"action":"op_ttl","timeout_ms":3000}` → 期望 `op_ttl override value_ms=3000 (one-shot)`。
4. 立即经 MQTT 下发 `network.tryconnect`（SSID=CMCC-502，真实口令）。

> 旋钮护栏：`timeout_ms` 必须 ∈ [500, 60000]，越界回 `invalid_param`；一次性，用完回落 45000（DEF-NET-001 起默认 45000=15s 连接+25s 验证+余量；此前为 20000）；**不触碰 GOT_IP_TTL（300000）**。

### 预期串口序列（判据）

```
W  hook_armed connect_hold ...            (布防)
W  op_ttl override value_ms=3000 (one-shot)
I  operation: accepted op-XXXX ttl=3000ms got_ip_ttl=300000ms
W  op_ttl applied accepted_ttl=3000ms (next op only)
I  cmd: async tryconnect ssid='CMCC-502' op=op-XXXX
W  hook_connect_hold_begin path=... seq=1 gen=1 timeout=10000ms     ← run_fn 进入阻塞
W  operation: expire op-XXXX cleanup=ok                            ← t≈3s，run_fn 仍在阻塞
I  mqtt: defer_end site=expire/terminal depth_before=0
W  operation: expire op-XXXX cleanup=ok 之后槽应空闲
W  hook_connect_hold_end path=... (released) 或 hook_connect_hold_timeout ...   ← t≈10s
I  cmd: async tryconnect op=op-XXXX stale after wait (gen=1 state=6), no job touch   ← R5 防线
```

**判据**
- E1-a：`expire ... cleanup=ok` 出现在 `hook_connect_hold_begin` 之后、`hook_connect_hold_end/timeout` 之前（run_fn 仍阻塞）——解耦实证；
- E1-b：cleanup 里的 `try_cancel` 返回 true 但**打不断 hold**（hold 循环只看 `hold_release`/deadline），所以 run_fn 一定跑到 10s，日志顺序不应出现"expire 后立即 stale"；
- E1-c：`stale after wait ... no job touch` 出现在 hold 结束之后（R5 generation 复核生效）；
- E1-d：期满后立即经 BLE 再发一次 `network.tryconnect`，应 `accepted`（槽已释放，非 `busy`），随即 `network.cancel` 收尾。

### 反例（出现即 FAIL）

- `expire` 出现在 hold 结束之后（解耦任务没独立跑）；
- `stale after wait` 缺失（R5 未生效）；
- 二次 tryconnect 返回 `busy`（槽泄漏）；
- abort/Guru/看门狗。

## 2. E3：`expiring` 并发闸（FI+C1）

1. 烧 FI+C1 镜像，同样布防 `op_ttl=3000` + `connect_hold`；
2. 在到期前用 `diag.testhook` 在 `expire_post_cleanup` 处 pause；
3. 并发再发 `network.cancel`（或第二次 expire 触发）；
4. 判据：只允许一个 cleanup 执行（第二个被 `expiring` 挡住并返回 `invalid_state`），pause 释放后状态唯一终态、无双重清理日志。
