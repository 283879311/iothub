# 协议契约整改方案（2026-11-10）
> **状态**：ACTIVE（契约 v1.1 基线 + Phase 跟踪）（文档状态标定 2026-11-14，定义与索引见 [docs/README.md](README.md)）


> 触发：小程序侧指出"很多问题源于协议不明确、约定不规范，改来改去"。
> 本方案不改任何一方代码（除 §3 的 3 个增量口子），先立契约，再谈实现。

## 0. 根因结论

不是某一方不守约定，而是**没有可执行的契约**：

1. 约定散落在三处——代码注释、聊天记录、测试期望。三处一旦不一致，就以"谁测出来谁算"为准；
2. **语义变更不升版本**：`got_ip` 从"拿到 IP"升级为"IP+联网+MQTT 就绪"（DEF-NET-001）发生在 wire 版本 `1.0` 内部，客户端无从感知；
3. 字段形状/终态集合/TTL/快照规则**从未成文**，双方各自实现"合理的假设"，冲突时只能靠真机事故定案。

本轮 2026-11-07～11-10 的每一类返工都能归到上面三条。

## 2. 整改目标物：契约四件套

### 2.1 机器可读契约（单一事实源，已提交）

`contract/v1/`：

| 文件 | 内容 |
| --- | --- |
| `errors.json` | **47 条**错误码（shell 25 / op 14 / both 8，无重复）：scope、class（auth/input/transient/capacity/state/op_terminal/internal）、重试预算、双轨 wire 形状 |
| `states.json` | op 状态机（9 态/4 终态）、转移表、TTL、got_ip 语义、stages 规则、operation.get schema |
| `timing.json` | 传输/认证/操作/netcheck/WiFi/BLE 链路/恢复退避全部常量 + 客户端派生预算 |
| `commands.json` | 信封格式 + 13 条命令的 args/data/errors/timeout/语义注释 |

**规则：契约优先于代码。** 代码与契约冲突以契约为准；改语义先改契约。

### 2.2 人读契约

由 `contract/v1/*.json` 生成为 `docs/协议契约_v1.md`（表格化，随契约版本发布）。
双方评审、签字都在这一份上做，不再在聊天记录里"口头约定"。

### 2.3 双向一致性测试

- **固件侧**：host 测试新增 schema 校验——用契约 JSON 校验固件产出的 golden 响应样例
  （现有 `tests/` 可直接扩展，无需真机）；
- **客户端侧**：Node 测试直接消费同一份 `contract/v1/*.json`（拷贝或 submodule + 版本戳），
  其 fixture 必须通过 schema；不一致即测试红；
- **联调 conformance**：固定 30 个 wire 用例（请求→期望字段/形状/终态），双方各自跑，
  任何一方红都不许合入。

### 2.4 变更流程（防"改来改去"的核心）

| 变更类型 | 版本动作 | 要求 |
| --- | --- | --- |
| 纯 bugfix，wire 无变化 | patch（契约文件不改） | 正常评审 |
| 新增可选字段 / 新增错误码 | **minor（1.0→1.1）** | 双方同批上线；客户端必须容忍未知字段/未知码 |
| 改既有字段含义、取值集合、时序预算、args 名、error 形状 | **minor + 冻结清单审查**；破坏性则 major（2.0） | 提前一版发公告；旧客户端行为定义 |
| 删除字段/改形状 | major | 协商窗口 ≥ 1 个迭代 |

**铁律**：任何"已有字段含义/取值集合/时序预算"的改动，**不升版本 = 回归缺陷**，
无论改动多小。`got_ip` 语义升级就是反例（1.0 内做，客户端无从感知）。

**变更提案模板（1 页）**：动机 / 线上现状 vs 目标 / wire 差异 / 兼容性与迁移 /
受影响的测试用例 / 双方签字。**先在契约文件里改，再改各自代码。**

## 3. 分阶段落地（本周）

### Phase 0（今天，已完成）：契约基线草案
- `contract/v1/*.json` 四件 + 本方案；
- 双方只读核对，逐条对 §5 的 7 项签字或提异议；
- **不写代码、不改行为**。

### Phase 1（签字后 1-2 天）：固件 3 个增量口子（全部向后兼容）
1. `operation.get` 增 `finished_uptime_ms`（可选字段）——客户端耗时复核不再依赖墙钟；
2. `operation.get` 增 `error_detail:{code,message}`（与 `error` 并存）+ `stages_source:"snapshot"|"live"`；
3. 终态后 stages 不再回落零值：保留最后快照（或至少 `stages_source` 可判）。

### Phase 2（同批）：客户端对齐 3 项
1. 终态集合加入 `expired`（轮询跳出 + 文案）；
2. `wifi_config_offline` / 快速 `connect_failed` 按 transient 处理（1.5s×3）；
3. #13 卡与 provision 成功判据统一为 `internet_verified && mqtt_connected`。

### Phase 3（2-3 天）：CI 闸
- 固件 host 测试 + 客户端测试各自消费 `contract/v1`；
- 契约校验失败 → 阻止合入；
- `device.info` 增 `contract_sha`（契约文件哈希），真机一眼看出两端是否同源。

## 4. 需要双方签字的 7 条（冻结基线）

1. **终态集合** = {success, failed, cancelled, expired}；
2. **error 双轨形状**保留至 2.0，1.1 并行新增 `error_detail`；
3. **args 命名冻结**：`operation_id` / `ssid` / `password` / `idempotency_key`；
4. **瞬态码白名单与重试预算**：`busy` 1.5s、`wifi_config_offline` 1.5s×3、快速 `connect_failed`(≤4s) 重试 1 次；`rate_limited` 350ms；
5. **stages 语义**：只在 `got_ip` 当次断言；终态后不断言（1.1 起带 `stages_source`）；
6. **计时表**：45s / 300s / 600s / 25s / 200ms / 90s·300s idle reap（以 `timing.json` 为准）；
7. **身份绑定**：`device_id` 尾号匹配 + 连后 `device.info` 校验，禁止 any 降级。

签字后本组条目即为 **v1.1 基线**，后续任何改动按 §2.4 流程走。
