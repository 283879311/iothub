## 2. V2：cut 注入（闸门机制 PASS，路径覆盖 FAIL）

注入结果（`v2_inject.log`）：

```
18:54:21 -> request .../rpc/request/9001
18:54:26 PUBLISH .../rpc/response/9001 {"id":"inj-…","ok":true,...}
18:54:26 !! cut mode: closing socket WITHOUT PUBACK (response)
```

设备侧（`serial_v1_v2.log`）：

```
I (257237) resp ack gate armed msg_id=64281
W (258237) resp_ack_timeout msg_id=64281
I (272377) defer_end site=op_set_state/terminal depth_before=0   ← 15s defer 定时器路径
W (279227) resp ack gate released msg_id=64281 (timeout)
```

**闸门三件套行为正确**：武装→1s 超时→重启前放行（timeout），全程无阻塞。

**但路径覆盖不成立（关键发现）**：现场那次断链的日志是

```
176591 wifi:state: run -> init
176611 mqtt: STA disconnected, stopping MQTT client
176611 wifi: tryconnect: ssid='CMCC-502' ... scan=1
```

——**没有任何 `mqtt restart attempt`**。真正拆链的是 **tryconnect 试验自己的 WiFi 断开（为扫描）**，不是 MQTT rebuild。闸门插在 MQTT 重启任务上，对这条路无效；本次 cut 是 broker 主动断链，恰好等于"闸门能覆盖的那半"。

**结论**：闸门位置需要前移到 **tryconnect worker 的第一次 WiFi 动作之前**（worker 不在 esp-mqtt 事件任务里，可安全等待）；MQTT 重启点的闸门可保留作第二道。

## 3. V3：安全网（FAIL，结构性）

- 本次 cut 的 trial 因注入口令错误在 15s 内 `4WAY_HANDSHAKE_TIMEOUT` → 走 **failed 终态**（`defer_end site=op_set_state/terminal`），未经过期路径；
- 现场原始孤儿（`op-A50F…`）日志：`accepted`（ttl=20s）→ `-> connecting`，**到 t=195s 都没有 `expire`**（串口全程可见）；
- 代码根因确认：`operation.c` 的 worker 是**单任务**，循环里 `expire_one()` 之后同步调用 `run_pending()` → `run_fn(op, ctx)`（`operation.c:551-582`）。tryconnect 的 run_fn 阻塞在试验里时，**同一任务的 1s 节拍停摆，`expire_one` 无法执行**——20s TTL 不可能生效。
- 这与评审假设 (b)"worker 被 run_fn 占住"一致，属**结构性**问题：TTL 改多短都没用。

**建议另立案**：DEF-MQTT-002「operation worker 被 run_fn 独占 → TTL 安全网失效」。选项：独立 expiry 任务/定时器、或 run_fn 改非阻塞 + 状态机驱动。

## 4. V7：+4.95s 悬案（已获解释）

现场 `restart deferred`（171641）后的 4.95s 事件是 **WiFi 试验的断连**（176591 `run -> init`），不是 MQTT defer 被提前放行；本次 V2 中唯一的 `defer_end` 出现在 +15.2s（defer 定时器路径，`depth_before=0` 是定时器已清零）。**没有发现提前放行的调用点**，悬案关闭。

## 5. 按评审要求停止

V4–V7 未继续执行（V3 是安全网直接证据，未通过 → 当场停，不靠重启继续）。设备已恢复，未做任何"现场修补"。
