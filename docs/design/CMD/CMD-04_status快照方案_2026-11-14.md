# CMD-04 · status 快照改造方案（2026-11-14）

> 目标（cmd_refactor_plan CMD-04）：**锁持有期间无 cJSON 分配；字段兼容**。
> 方法：全 cmd.c 系统性扫描（python 状态机：lock→unlock 区间内计数 cJSON_
> Create/Add）+ 逐函数直读核实（扫描器对**嵌套锁段**有漏计——operation_status
> 的 runtime/mqtt 嵌套锁把 depth 提前归零，直读为准）。

## 1. 现状普查：锁内 cJSON 全景

execute_method 内联（2 段）**；其余构造函数已是快照后构建模式（照抄即可的
先例已在仓内）。

## 2. 已合规构造函数的捕获模式（照抄先例）

仓内已有两种成熟模式：
- **分域拷贝**（gpio/uart/device_status/get_config）：每域一次
  `lock → 拷贝到局部 → unlock`，全部局部就绪后构建；
- **单域短锁**（network_status 的 rssi 段）：锁内只快照判定位，驱动查询
  （`esp_wifi_sta_get_ap_info`）在锁外执行。

## 3. 改造设计（逐构造函数）

### 3.1 `app_cmd_build_network_status`（CMD-04b，4 段）

快照结构（栈上局部聚合体，不新增全局/类型导出）：

```
runtime 域（一次 runtime_lock，1 次结构拷贝）:
    sta_connected / sta_has_ip / sta_ip[16] / last_disconnect[24] /
    connected_ssid[33] / connected_profile / net_verified / net_verify_stage[12]
config 域（一次 config_lock）:
    sta_ssid[33] / password_set / net_mode / persistent_use_static / persistent_static_ip[16]
mqtt 域（一次 mqtt_lock）:
    mqtt_connected / mqtt_last_error[64]
trial 域（一次 job_lock）:
    trial_ready(bool，ready 判定) / trial_id[20] / trial_ssid[33]
```

构建顺序**保持现状**（runtime → nc stats → rssi → config → cfg_state →
mqtt → trial），wire 输出逐字段一致。

### 3.2 `app_cmd_net_operation_status`（CMD-04b，最大单债）

难点：构建中的**分支判定依赖锁内数据**（owner 校验、have_snapshot、trial
匹配、stages 回落）。方案：**单次 job_lock 快照"判定所需全集"，锁外判定+构建**：

```
job_lock 一次性捕获:
    op_found(bool) / state / error / terminal_ms / owner /
    active + job_operation_id + st_*×4（have_snapshot 判定用）/
    trial_valid + trial_id/ssid（trial_id 匹配判定用）
job_unlock
锁外（纯函数）:
    owner 校验 → not_found（返回路径与现一致）
    构建 operation_id/state/error/error_detail/finished_uptime_ms/
    trial 块/stages 块（source 判定用快照值）
```

- **锁内零 cJSON**；锁内耗时从 ~20 次堆分配降到 ~12 字段拷贝（<10µs）；
- `live` 回落段的 `runtime/mqtt` 捕获**保持锁外分段**（现状即如此，无新锁序）；
- 返回值路径（NULL/resp）语义不变。

### 3.3 `app_cmd_execute_method` 内联 2 段（CMD-04c，小）

trial 状态响应（3 Add）与 trial patch（2 Add，含 password）：job_lock 内
快照 trial_id/state/ssid/password → 锁外构建。patch 含明文口令的构建移出
锁内（顺带消除"持锁处理明文"的味道）。

### 3.4 `app_cmd_net_apply_async` COMMITTING 段——**明确不动**

该段的"持锁执行内层 apply"是 R2-P0 的核心语义（cleanup 在 job 锁上等待，
GOT_IP TTL 过期/BLE 断连取消被串行化在 apply 一致终态之后）。其中的
`cJSON *p` 构造移出锁外**技术上可行**（trial_id 先快照），但会改变临界区边界，
需 R2-P0 语义重审——**本轮不做，登记为 CMD-06 迁移时的合并议题**。

## 4. 一致性与锁序分析

- **域内一致性**：runtime 域 8 字段单锁内一次拷贝（比现状"逐字段 Add 期间
  同锁持有"更强——现状本来就一致，快照化不劣化）；
- **跨域一致性**：`connected_ssid`（runtime）与 `sta_ssid`（config）现状即
  非原子（两个锁分别取），快照化**不改变**跨域 skew 特性（客户端语义已容忍：
  "回退时二者不同"是文档化行为）；
- **锁序**：捕获顺序保持现状（runtime → netcheck API → get_ap_info 锁外 →
  config → cfg_state → mqtt → trial/job），全部**单锁顺序捕获、无嵌套**，
  不引入新锁序；
- **`s_ops_mux` spinlock**：operation_status 快照化后，job 锁内的
  operation API 调用（find/get_status）仍在——spinlock 临界区极短且无 cJSON，
  不受影响。
