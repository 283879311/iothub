# 缺陷立案：BLE 广播消失（`adv=0 conn=1`）连接句柄悬挂
> **状态**：ARCHIVED（已修复闭环）（文档状态标定 2026-11-14，定义与索引见 [docs/README.md](README.md)）


> 编号：**DEF-BLE-001**；状态：**立案（只读代码分析 + 现场证据归档）**。
> 本文不包含任何设备操作；复现与验证需单独批准。
> 关联：`docs/T4_验收失败分析_2026-11-04.md` §3.1。

## 1. 现象

累计多次 BLE 会话后，设备停止广播（小程序扫不到设备），但 Wi-Fi/MQTT 全正常；硬复位（RTS/EN）后立即恢复 `adv=1 conn=0`。已复现 2 次（T4 第三轮失败、MQTT 真机回归收尾）。

现场串口（1s diag 节拍）：

```
diag: heap free=43968 ... | wifi mode=1 ch=3/0 adv=0 conn=1 role=ble ...
```

对端：历史连接日志 `peer_ota=F8:A2:D6:CD:BD:94`（本主机适配器）；主机侧 BlueZ 已无该设备记录（`disconnect` 报 not available）。

## 2. 关键推断：`conn=1` 不是估算值

`adv/conn` 两个字段直接取应用层标志，不是协议栈查询值：

- `main/diag.c:64` → `ble_conn = app_ble_gatts_connected() || app_ble_gattc_connected()`
- `main/bt_gatts_nimble.c:450-453` → `app_ble_gatts_connected()` 返回 `s_connected`

因此 `conn=1` 等价于 **`s_connected == true`**（peripheral 侧）。

`s_connected` 只在 `main/bt_gatts_nimble.c:239`（CONNECT 成功）置 `true`；清零点只有两处：`:294`（DISCONNECT）与 `:356`（`app_ble_gatts_reset()`）。后者仅由 `app_ble_dataplane_reset()`（`main/transport_ble.c:43-49`）在 BLE 数据面停/重启路径调用，**广播看门狗不调用**。

旁注：`conn=1` 是 `gatts||gattc` 的或值。本次现场对端为本机适配器（peripheral 角色），适用 gatts 半边；若后续在 central 角色（`app_bt_start_central`）复现，需单独看 gattc 半边。

结论：现场那一刻，**设备侧从未收到并处理 DISCONNECT 事件**。这不是"广播状态机坏了"，也不是"标志不同步"——标志与"未收到断连"是自洽的。

## 3. 为什么看门狗救不回来

`main/bt.c:507-570` 的广播看门狗：

- `main/bt.c:522`：`bool connected = app_ble_gatts_connected() || app_ble_gattc_connected();`
- 同一函数：`if (s_central_mode || connected || !ble_hs_synced() || authoritative) { silent_ticks=0; return; }`

即 **`connected==true` 时看门狗直接清零退出**。这与现场 `conn=1` 是同一个标志——所以看门狗从设计上就不可能覆盖这个场景，`adv_retry_count` 也不会增长。这解释了"广播消失后一直不恢复、只能硬复位"。

## 4. 两个假设与判别

| 假设 | 内容 | 判别（只读，需一次构建） |
| --- | --- | --- |
| **H1（主判）** 对端僵尸链路 | 主机 BlueZ 删了设备对象，但主机控制器仍持有 ACL，链路层持续应答空包 → 永不过监督超时 → 设备侧无 DISCONNECT 事件，链路真实存在 | 在 diag 行加 `conn_find=0/ENOTCONN`（`ble_gap_conn_find(BLE_HS_CONN_HANDLE_NONE,&desc)`）：`0` 且 `s_connected=1` → H1 成立 |
| **H2** 事件丢失 | 链路已断，NimBLE host 未投递 DISCONNECT → 标志悬挂 | 同上查询返回 `BLE_HS_ENOTCONN` 而 `s_connected=1` → H2 成立（栈缺陷） |

H1 概率显著更高：`CONN_UPDATE` 日志（`main/bt.c:214-221`）已打印协商后的 `supervision_timeout`；若对端在链路层仍应答，超时机制根本不会启动。

## 5. 建议处置（分批，均不改动 P0 候选）

**批次 1（诊断，随下一次常规构建，不单独烧写）**

1. diag 行尾追加 `conn_find=`、`gatts_conn=`、`last_rx_ms=`（距最近一次 ATT 写/读的毫秒数）；
2. `device.status.ble` 增 `conn_find`、`peer_addr`（`ble_gap_conn_find` 的 `peer_id_addr`）；
3. `adv watchdog` 在 `connected==true` 且 `last_rx_ms > 90s` 时打一次 `conn_stale_suspect`（**只报不动**）。

**批次 2（策略，需 H1/H2 定性后二选一）**

- H1：空闲断链策略——`last_rx_ms > T` 且**无 notify 订阅**时 `ble_gap_terminate(handle, BLE_ERR_REM_USER_CONN_TERM)`，随即恢复广播。T 建议 90s；有订阅时不动作，避免误杀正常静默会话；
- H2：一致性自愈——diag 节拍发现 `s_connected==true` 但 `conn_find==ENOTCONN` 时清零标志并重启广播。

**批次 3（可选，协议层）**：小程序 30s 心跳 + 设备 90s 无心跳断链；属交互协议变更，需与小程序版本一起发。

## 6. 复现脚本草案（需批准后执行）

主机侧（Linux，BlueZ/bleak）：循环 200 次 `connect → 订阅/读写 → 进程被 kill -9（不发 disconnect）`，每次间隔 1s；每 20 次读一次 `device.status.ble` + 抓串口。判据：出现 `adv=0 conn=1` 即复现，保留 `conn_find` 与 `last_rx_ms`。

不在本立案内执行；不复位、不烧写、不改配置。

## 7. 影响与边界

- 影响：设备"失联"——小程序侧表现为扫码无设备，需物理复位；Wi-Fi/MQTT 不受影响，故远程侧无感知。
- 不阻塞：v1-only 迁移结论、静态 re-apply P0（两条独立链）。
- 不改变：T4 第三轮 FAIL 的定性（根因即本缺陷，非协议实现错误）。
- 关闭判据：批次 1 完成 H1/H2 定性 + 批次 2 落地 + 200 次 kill -9 循环无 `adv=0 conn=1` 残留。
