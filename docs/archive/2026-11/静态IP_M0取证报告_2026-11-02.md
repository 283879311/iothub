## 取证 1：静态 `esp_netif_set_ip_info` 是否触发 `IP_EVENT_STA_GOT_IP`

**结论：会触发，但时机在 STA 连接成功时，不在 `set_ip_info` 调用时。90s 验证窗口可以依赖现有 GOT_IP 事件。**

IDF 源码链：

1. `components/esp_netif/lwip/esp_netif_lwip.c:2034-2088`（`esp_netif_set_ip_info_api`）：
   - 要求 DHCP client 状态为 `STOPPED`，否则返回 `ESP_ERR_ESP_NETIF_DHCP_NOT_STOPPED`（:2050-2052）；
   - **附带行为**：DHCP client 停止状态下设置 IP 时执行 `dns_clear_servers(true)`（:2053-2055）——lwIP 在静态设置时自动清空 DNS；
   - 仅当 `p_netif != NULL && netif_is_up(p_netif)` 才立即 post GOT_IP（:2064-2086）。本固件启动流程在 `esp_wifi_stop()` 之后、`esp_wifi_start()` 之前调用（`main/wifi.c:1910-1956`），此时 netif 是 DOWN 的，**该立即 post 不发生**。
2. `components/esp_netif/esp_netif_handlers.c:35-80`（`esp_netif_action_connected`）：
   - STA 连接成功 → `esp_netif_up` → 因 netif 带 `ESP_NETIF_DHCP_CLIENT` flag 且 `dhcpc_status == STOPPED`，读取已存的静态 `ip_info`，`esp_netif_is_valid_static_ip()`（非 any）通过后 **post `IP_EVENT` + `esp_netif_get_event_id(ESP_NETIF_IP_EVENT_GOT_IP)`**（:58-74）；默认 STA netif 的该 event id 即 `IP_EVENT_STA_GOT_IP`（`include/esp_netif_defaults.h:50`）。
   - 若静态 IP 无效（any），走 `:76` "invalid static ip" 错误日志，**不 post 事件**——这正是 1.1 启动安全要拦截的场景之一。
3. 默认 STA netif 模板带 `ESP_NETIF_FLAG_EVENT_IP_MODIFIED`（`include/esp_netif_defaults.h:47`），`set_ip_info` 的立即 post 分支（如 netif 恰好 up）同样可用。

**对本方案的影响**：

- M1/M4 的验证窗口以"STA 连接成功后的 GOT_IP 事件"为判据成立；窗口起点按评审意见从"配置应用成功、开始网络验证"计起（即 `esp_wifi_start` 返回 OK 之后）。
- 静态 IP 无效时连接后**不会有 GOT_IP**，只有 "invalid static ip" 日志——90s 窗口超时 + 回滚路径必须以"窗口内无有效 GOT_IP"为失败判据（方案已如此设计）。
- **DNS 残留问题被 IDF 部分化解**：静态设置（dhcpc stopped）时 lwIP 自动 `dns_clear_servers(true)`。方案 1.5 的显式清零+回读仍保留为双保险，但"切换后残留旧静态 DNS"的风险降级。

**历史板级佐证**：`tools/ble_p0/results/` 下的 P0 原始 JSON/日志记录（索引见 `tools/ble_p0/results/README.md`）——v0 静态 IP 命令 PASS（`192.168.43.213`，reboot 后该 IP + MQTT 在线），证明上述事件链在实机成立（设备状态 IP 来自 GOT_IP 事件处理器）。

## 取证 2：`ESP_ERROR_CHECK(app_apply_wifi_config())` 失败实况

**结论：确定性失败 → abort → panic（PRINT_REBOOT）→ 无限重启循环；实机复现待批准，本轮未执行。**

证据：

1. `components/esp_common/include/esp_err.h:115-122`：非 NDEBUG、非 SILENT 分支下，`ESP_ERROR_CHECK` 失败调用 `_esp_error_check_failed()`（内部 abort）。
2. `sdkconfig`：
   - `CONFIG_COMPILER_OPTIMIZATION_ASSERTIONS_ENABLE=y`，`ASSERTIONS_SILENT` 未开 → 走完整 abort 路径（带打印）；
   - `CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y`，`PANIC_REBOOT_DELAY_SECONDS=0` → panic 打印后立即重启。
3. 启动失败可达阶段（`main/wifi.c:1884-1963`）：`esp_wifi_stop/set_mode/set_config/start`、`app_configure_sta_static_ip` 内 `static parse`/`esp_netif_set_ip_info`。`dhcpc_stop` 失败仅告警不失败（:569-572），不构成循环源。
4. **循环机制**：错误静态配置持久化在 NVS；每次上电 `app_start_wifi()` 都会用它失败 → abort → 重启 → 再失败。与运行期失败不同，无人工干预（BLE 在 abort 后不可用）就跳不出循环。

**实机复现状态**：未执行。复现需二选一：向 NVS 直写非法静态配置，或构建故障注入测试固件；两者都突破"65D8 保持 DHCP/不改固件"边界，**待你批准后单独立项**（可在 65D8 上做，也可等 M1 测试构建）。修复前取证价值主要是拿到真实 panic 输出样式；当前"循环"结论由 sdkconfig+源码即可成立。

## 取证 3：静态模式下 tryconnect 候选 IP 来源（源码追踪）

**结论：候选期间会被临时切到 DHCP，trial 结束后 netif 停留在 DHCP 状态；正式连接将以 DHCP 地址运行而 `sta_use_static` 仍为 true——状态分裂，且冲突检测语义被破坏。入口统一 guard 的设计得到源码支持。**

### 入口清单（guard 必须覆盖全部）

| 入口 | 位置 |
| --- | --- |
| v0 同步 `network.tryconnect` | `main/cmd.c:1875` → `app_wifi_try_connect_ip` |
| v1 `network.tryconnect` → 映射 `network.tryconnect.async`（`main/ble_cmd.c:346-348`）→ worker | `main/cmd.c:275` → `app_wifi_try_connect_ip` |

`main/` 内无其他调用点（`app_wifi_try_connect/_ip` 仅定义于 `main/wifi.c:2256/2262`）。**在 `main/cmd.c` 两处调用点（或收敛为一个前置 helper）加 guard 即可覆盖全部入口**，不需要触碰 `main/wifi.c` 的 tryconnect 生命周期。

### 静态模式下的行为链（源码推演，当前 abc193… 构建）

1. trial `STA_CONNECTED` 且 `require_ip` → `app_wifi_tryconnect_on_connected` need_dhcp 分支执行 `esp_netif_dhcpc_stop` + `dhcpc_start`（tryconnect patch 内，约 `main/wifi.c:1497-1516`）→ 候选网络走 DHCP；
2. trial OK；`finish()`（`main/wifi.c:2025-2049`）恢复 wifi config、断开候选、resume 自动重连——**不恢复 netif 静态设置、不重新 stop DHCP**；
3. 之后自动重连回正式 SSID：netif 处于 `DHCP_STARTED` → GOT_IP 来自 DHCP 租约（esp_netif_lwip.c 的 DHCP 回调路径）；
4. GOT_IP 处理器（`main/wifi.c:1841-1881`）发现 `s_config.sta_use_static==true` → 启动 ARP 冲突检测——**对 DHCP 租约地址做"静态冲突检测"，语义错误**；
5. 设备实际以 DHCP 运行直到下次 reboot/apply；`config.get`（static=true）与 `network.status`（DHCP 地址）呈现互相矛盾的状态。

### 判定

- 修复前取证目标（"候选是否继承旧 netif 地址"）已有明确源码答案：**不是继承静态地址，而是被 trial 的 DHCP 重启临时接管并在 trial 后残留**。这比原假设更糟（状态分裂而非简单误判）。
- 无需板级复现即可支撑 1.4 guard 的优先级；实机行为留待 M1 guard 实施后用拒绝路径验证（不再触发该行为链）。
