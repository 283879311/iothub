## 3. A0：生产固件连接参数预检（只读）

条件：连接前用 `MGMT_OP_LOAD_CONN_PARAM (0x0035)` 写入 per-peer 参数 24–40 units / latency 0 / supervision 600，`addr_type = BDADDR_LE_PUBLIC (0x01)`；btmon 从连接前开始；连接后仅发送免 token 的 `device.info`（5 s 一次）。

| 判据 | 结果 |
|---|---|
| `LE Create Connection` | min 30 ms / max 50 ms / latency 0 / supervision 6000 ms (0x0258) |
| `LE Enhanced Connection Complete` | interval 45 ms / latency 0 / supervision 6000 ms |
| 设备策略 | `sup=6000ms -> satisfied, skip update request`（仅此一条） |
| 60 s 静置 | 11 次心跳全部 `ok`，无断链；无 `LE Connection Update`、无远端参数请求 |
| 结束方式 | 我方 `Disconnect`（0x16/0x13），非设备侧超时 |

实现要点（内核源码核实）：

- `mgmt_hdr = {opcode, index, len}`；`0x0015` 是 `GET_CONNECTIONS`（固定长度 0），误用会 `EINVAL`。
- `addr_type = 0` 是 `BDADDR_BREDR`，`load_conn_param` 对非 LE 类型静默 `continue`，但仍返回 `Command Complete status=0`——表现为“成功却无效”。
- 内核 per-peer `hci_conn_params` 在**创建时**拷贝 `hdev` 默认值（默认 supervision 42 = 420 ms）；事后修改 debugfs 不影响已有条目。
- BlueZ 5.72 经 `bt_io_connect(BTPROTO_L2CAP, CID=ATT)` 建链 → 内核 `hci_connect_le()` → `hci_le_create_conn_sync()` 读取 `hci_conn_params`，故上述 MGMT 参数对该路径生效。

文件（证据分支）：`artifacts/c15_a0_a1_20261128/a0/a0_hold_r4.json`、`a0/a0_serial.log`、`a0/a0_btmon_params.txt`。

## 6. 排除项（审核用）

1. 日志中 `password` 字段是 harness `sanitize()` 输出的 `<redacted>` 占位符（恰好 10 字符），不是真实口令；证据包与本文均不含凭据。
2. 设备使用 Kconfig 出厂默认口令（`main/Kconfig.projbuild` 的 `AUTH_DEFAULT_PASSWORD`），本轮**未修改任何凭据或认证配置**。
3. 预跑尝试 1 因把占位符当作口令而 `invalid_credentials`，脚本在**任何写命令之前**退出，无设备副作用；尝试 2 用默认口令完成实验。
4. 0x222 根因在主机侧：per-peer `hci_conn_params` 使用默认 420 ms supervision，触发设备 out-of-policy 参数更新请求且主机侧未完成（依据：`a1/a1_btmon_params.txt` 与主机侧 `hci_conn_params` 默认 420 ms supervision 记录）。设备固件未修改。
5. MGMT 参数条目为内核内存态：适配器下电/重启或重启 bluetooth 服务后失效，需重新写入。

## 9. 追加更正：排除项 #5（MGMT 参数条目生命周期，2026-11-28）

> 本节为后续证据追加说明；**不回改 §6 第 5 项原文**。如与原文表述冲突，以本节限定后的证据结论为准。依据：证据分支 `evidence/p2-connparam-20261128`，rev2 提交 `04162a06749048ebfd63d94f2e27c3c5c2cdb5de`，证据目录 `artifacts/p2_connparam_20261128/`。

### 9.1 更正后的结论

原排除项将“适配器下电/重启或重启 bluetooth 服务后失效”合并表述，范围过宽。P2 rev2 证据要求拆分不同生命周期事件：

- **适配器 power off/on（P2-3）：NOT_COVERED。** 实验脚本两次调用均报告 `Set Powered for hci0 failed with status 0x11 (Invalid Index)`。原因是 `btmgmt -i` 需要数字索引，传入 `hci1` 被解析为索引 0；命令实际未完成 power off/on，脚本却继续执行了后续连接。因此后续观测到的 6000 ms 不能证明 power off/on 后条目保留或丢失。不得据此断言 power off/on 会清除条目。
- **btusb unbind/bind（P2-4）：有限支持条目随 hdev 生命周期结束而丢失。** rebind 后控制器索引由 hci1 变为 hci0；重连初始参数为 interval 30–50 ms、latency 0、supervision 420 ms，支持原 per-peer 参数条目未跨该 rebind 保留的判断。此项只证明 rebind 后的初始参数回落；该连接约 5.2 s 后由主机主动断开，未等待设备发起的参数更新完成，不能判断后续更新结果。
- **重新加载（P2-5）：支持重新写入后恢复。** rebind 后重新执行 `LOAD_CONN_PARAM`，随后连接初始 supervision 为 6000 ms，设备记录 `satisfied`。这证明重新加载可恢复该连接参数，不补足 P2-3 的 power off/on 覆盖。

### 9.2 未被验证的情形与边界

- **仅重启 bluetooth 服务**：本轮没有独立验证，不能等同于控制器 hdev release，也不能据此判断 MGMT per-device 条目的存留。
- **power off/on**：P2-3 未有效执行，仍为 `NOT_COVERED`；若需判定，必须另行授权并按数字 controller index 执行，且以实际命令输出及后续控制器/条目状态核验作为判据。
- 本追加更正只修正 Central 侧 MGMT 参数条目生命周期的证据口径，**不解释 C15-2 原始 BUSY 的根因**，不改变 C15-2 的 `BUSY_REJECTED / NOT_COVERED`，也不改变 CMD-15 的 `TEST_PENDING`。

### 9.4 后续更新：P2-3 重跑（2026-11-28）

本节为追加更新，不改变 §9.1 作为限定时点记录的效力。§9.1 中 P2-3 `NOT_COVERED` 的结论基于 rev2；同日另经授权执行的 P2-3 独立重跑（evidence rev3 `a54da4ffde08afcffc7b84c30ccc676043d07637`，目录 `artifacts/p2_connparam_20261128/p2_3_rerun/`）已补齐该缺口：

- 重跑使用数字索引 `hci0 → 0`；`LOAD_CONN_PARAM` 返回 cmd 0x0035 status 0；
- power off 后 `info` 的 `current settings` 不含 `powered`，power on 后恢复 `powered`，控制器索引与地址不变；
- 重置前后目标设备 `LE Create Connection` 均为 30–50 ms / latency 0 / **6000 ms**，`Enhanced Connection Complete` 均为 45 ms / 0 / 6000 ms；串口两次 `satisfied`，身份均为 `1.3-956afcd`，`0x222=0`。

**更新后的限定结论**：在本次已验证的适配器 power off/on 操作后，已加载的 per-peer MGMT 参数条目仍然保留；结论限定于本控制器、BlueZ 5.72 与本次操作，不外推到其他控制器或其他重启方式。

本节不改变：P2-4 的有限结论（仅 rebind 后初始参数回落 420 ms）、P2-5 的重新加载结论、C15-2 原始 BUSY 根因判断，以及 C15-2 `BUSY_REJECTED / NOT_COVERED` 与 CMD-15 `TEST_PENDING` 状态。
