# BLE 微信小程序交互协议（T4 iOS/Android 真机验收版）

> 适用固件：`feature/shared-config-cmd` @ `4bb492d`（A 阶段 token store），AP 运行时/AP 配置 schema 已删除，STA-only + BLE 配网/救援。
> 文档日期：2026-10-24（2026-10-26 增补 T4-A/T4-iOS 分账与 A 阶段 token 行为）。
> 本文是**小程序侧**协议；设备侧源码依据：`main/ble_cmd.c`、`main/cmd.c`、`main/operation.c`、`main/bt_gatts_nimble.c`、`main/data_pipe.c`。
> **验收分账**：T4-A = Android 单端（可执行）；T4-iOS = 无设备，当前 **BLOCKED**。T4 整体仍未签收；T4-A PASS 不等于 T4 PASS。T3 主机侧结论仍分开：GATT/CMD/DATA 功能 PASS；DATA 端到端可靠性未签收。

## 0. 一句话流程

```
微信扫描 NUS Service UUID
  → 连接
  → 发现 Service + 4 个特征
  → 先订阅 CMD TX(0005)（要用 DATA 再订阅 DATA TX 0003）
  → auth.login 拿 token
  → device.info / network.scan
  → network.tryconnect 起候选
  → operation.get 轮询到 got_ip
  → network.apply 提交
  → config.get / network.status 确认 IP 与 MQTT
  → 断开或继续使用
```

没有 AP/HTTP 配置通道。STA 失败、无 IP、MQTT 断开时，BLE 仍可完成 scan/tryconnect/apply 救援。

## 1. BLE 服务与特征

Service：`6E400001-B5A3-F393-E0A9-E50E24DCCA9E`

| 特征 | UUID | 属性 | 小程序用途 |
| --- | --- | --- | --- |
| DATA RX | `6E400002-B5A3-F393-E0A9-E50E24DCCA9E` | write / write-without-response | 原始数据写入（非命令） |
| DATA TX | `6E400003-B5A3-F393-E0A9-E50E24DCCA9E` | notify | 原始数据回传；需先订阅 |
| CMD RX | `6E400004-B5A3-F393-E0A9-E50E24DCCA9E` | write / write-without-response | JSON 命令写入 |
| CMD TX | `6E400005-B5A3-F393-E0A9-E50E24DCCA9E` | notify | JSON 响应；需先订阅 |

- CMD RX/CMD TX 与 DATA RX/DATA TX 是独立特征，不要混用。
- 设备名：完整名 `IotHubBLE-<4hex>`，短名 `IH-<4hex>`（以实际板为准，测试板 C8E4）。
- 广播含 NUS 128-bit Service UUID，供 `services` 过滤。
- 链路不加密、不配对；鉴权靠应用层 token（明文链路，见 §10）。

## 2. 扫描、连接、订阅顺序

### 2.1 扫描

```js
wx.openBluetoothAdapter()
wx.startBluetoothDevicesDiscovery({
  services: ['6E400001-B5A3-F393-E0A9-E50E24DCCA9E'],
  allowDuplicatesKey: true
})
wx.onBluetoothDeviceFound(...)
```

- 必须按 Service UUID 过滤，不能只按名称。
- 记录 iOS/Android 实际 `name` / `localName`；iOS 可能只显示完整名，Android 可能显示短名或完整名。
- Android 需要微信/系统定位权限及定位服务开启（系统要求，设备侧无法替代）。
- iOS 可能缓存设备；测试时如扫描不到，先在系统蓝牙中忽略旧设备。
- **连接后设备停止广播是正常行为**：连接态下扫描不到目标设备（0 台）不是固件故障，不要在连接后把该现象判为 FAIL/WARN；应在连接前扫描，或断开设备页后重新扫描。设备断连后会恢复广播（T4 重连项已验证）。
- **断开后广播恢复有 ≤6s 看门狗兜底（P0-6）**：正常断开约 30-40ms 恢复广播；极端竞态下固件看门狗在 5-6s 内自动重试（退避最长 30s）。小程序重扫窗口建议 ≥10s；若设备处于未连接状态且 >30s 仍扫不到，记为设备侧缺陷，`config.get.bluetooth.adv_retry_count` 非 0 可佐证看门狗曾介入。

### 2.2 连接与发现

```js
wx.createBLEConnection({ deviceId })
wx.getBLEDeviceServices({ deviceId })
wx.getBLEDeviceCharacteristics({ deviceId, serviceId })
```

- `deviceId` 使用微信返回的值：iOS 是系统 UUID，Android 通常是 MAC；不要跨平台硬编码。
- 找到 Service `6E400001...`，再找四个特征；属性以微信实际返回为准。

### 2.3 必须先订阅 CMD TX

```js
wx.notifyBLECharacteristicValueChange({
  state: true, deviceId, serviceId,
  characteristicId: '6E400005-B5A3-F393-E0A9-E50E24DCCA9E'
})
wx.onBLECharacteristicValueChange(...)
```

**先订阅 CMD TX，再写 CMD RX。** 设备在未订阅 CMD TX 时仍可能处理命令，但响应无法送达；设备只会打 warning，不会重发。DATA 使用前同样先订阅 DATA TX（0003）。

## 3. MTU 与写入分片

- 当前设备 preferred MTU 为 256；真机可能协商为 23/185/247 等，**不要假定 256**。
- 小程序保守做法：**每次 GATT 写不超过 20B**，串行写，等待 `wx.writeBLECharacteristicValue` success 回调再写下一片；需要时片间 20ms。
- 275B 的 v0 `config.set` 会拆成 14 片；长命令不能一次写整包。
- Android 可尝试 `wx.setBLEMTU`，但不要依赖；iOS 通常不提供可控 MTU，20B 最稳。
- 设备 CMD TX 按 `MTU-3` 分片（MTU23→20B，MTU256→253B），每片间隔 20ms；小程序必须按通知逐片重组，不能假定一个通知是一条完整 JSON。
- DATA TX 也按 `MTU-3` 分片，但没有 20ms 片间隔，且没有应用层重试；见 §7。

## 4. CMD 帧格式与 JSON 重组

### 4.1 写入

- CMD RX 是 UTF-8 JSON 行重组器，单行上限 **512B**。
- 推荐每条命令末尾带 `\n`；设备也接受“一次写入恰好是完整 JSON 对象、无换行”的兼容形式。
- 小程序按 20B 分片写入；每片等待 success；不要在 JSON 中间插入其他命令。
- 命令超过 512B 会返回 `line_too_long`，不会执行。

### 4.2 读取

CMD TX 的通知是 JSON 的字节分片，不含长度前缀。小程序应：

1. 按到达顺序把 ArrayBuffer 追加到字节缓冲；
2. 用括号配对（跳过字符串内 `{}`/转义）找到完整 JSON 对象；
3. 对完整对象做 UTF-8 解码 + `JSON.parse`；
4. 按 `id` 匹配请求；
5. 一个缓冲里可能有多个对象（尤其长响应后紧跟 operation.get 响应），逐个处理。

不要对半截 UTF-8/半截 JSON 直接 `JSON.parse`；SSID 可能包含多字节字符。建议用 `TextDecoder` 在完整对象上解码，或使用增量 decoder。

### 4.3 长响应与 FIFO

- 设备 CMD TX 有独立发送队列；一个长响应会连续发完，再发下一条响应。
- 设备命令任务可以在长响应发送期间处理下一条命令（例如 `operation.get`），但**响应通知排在长响应之后**。
- 客户端超时应至少 10s；长响应期间不要重复发送同一命令。
- MTU23 下 `config.get` 约 1107B、约 60 个 20B 分片；`network.scan` 也可能超过 1KB。T4 必须按分片重组，不能按一次 notify 判断完整性。

## 5. 认证与版本

### 5.1 v1 请求/响应

请求：

```json
{"id":"<REQ_ID>","version":"1.0","cmd":"<cmd>","args":{},"token":"<TOKEN>"}
```

成功：

```json
{"id":"<REQ_ID>","ok":true,"data":{}}
```

失败：

```json
{"id":"<REQ_ID>","ok":false,"error":{"code":"<CODE>","message":"<v0_error>"}}
```

- `id` 由小程序生成，字符串或数字均可；响应带相同 id。
- `version` 必须是 `"1.0"`；否则 `unsupported_version`。
- `args` 必须是对象；缺失/类型错误返回 `invalid_argument` 或 `unknown_command`。
- `device.info` 是唯一**不需要 token**的 v1 命令。
- 其他命令都需要 token；`auth.login` 本身不需要 token。

### 5.2 登录

```json
{"id":"2","version":"1.0","cmd":"auth.login","args":{"username":"<ADMIN_USER>","password":"<ADMIN_PASSWORD>"}}
```

成功：

```json
{"id":"2","ok":true,"data":{"token":"<TOKEN>","expires_in":600}}
```

- token 由设备生成，TTL **600s**。
- token 是 **32 位大写十六进制字符串，大小写敏感**；客户端必须原样回传，小写或改写大小写均视为不匹配。
- token 是**连接级**的：BLE 断开后设备立即作废，重连必须重新 `auth.login`。
- 管理凭据由设备部署/现场提供；**不要把真实凭据写入小程序源码或仓库**。测试固件的管理凭据按当前设备配置，T4 现场输入。
- token 只用于本次连接；不要持久化到云端或日志。

### 5.3 token 过期 / 未授权

- 命令返回 `error.code = "unauthorized"` 时：重新 `auth.login`，再用同一请求 id/参数重试一次。
- 不要在 token 失效时重放 `network.tryconnect` 并换新 idempotency_key；先恢复登录。
- 设备 5 次/秒、最短 200ms 间隔；超限返回 `rate_limited`。小程序串行发送，收到后至少等 350ms 再重试。

## 6. 核心命令

### 6.1 `device.info`（无 token）

```json
{"id":"1","version":"1.0","cmd":"device.info","args":{}}
```

`data` 主要字段：

| 字段 | 含义 |
| --- | --- |
| `model` | 固件项目名 |
| `firmware` | 固件版本 |
| `device_id` | 设备 ID（主机名，如 `IotHub-C8E4`） |
| `protocol_versions` | `["1.0"]` |
| `security` | `link_encrypted=false,bonded=false,l2_ready=false,sensitive_writes_allowed=false` |

### 6.2 `config.get`

```json
{"id":"3","version":"1.0","cmd":"config.get","args":{},"token":"<TOKEN>"}
```

- `args.domains` 可选，数组；支持 `network`、`mqtt`、`bluetooth`、`uart`、`gpio`、`web`。
- 响应 `data` 按域返回；这是长响应，必须按 §4.2 重组。
- **AP 配置 schema 已删除**：`network` 不再有 `ap_ssid`、`ap_password_set`、`startup_fallback_to_ap`；不要再依赖这些字段。
- `network` 主要字段：`net_mode`（只可能是 `sta`）、`sta_ssid`、`sta_password_set`、`sta_use_static`、静态 IP 字段、`sta_connected`、`sta_has_ip`、`sta_ip`、`last_disconnect`。
- 口令/token 永远不回明文，只回 `*_set` 布尔。
- `network` 的 `sta_ssid` 来自正式配置；`sta_ip` 是运行时；二者在自动回退时可能不属于同一网络。配置以 `config.get` 为准，运行时以 `network.status` 为准。
- `bluetooth` 域字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `bt_role` | string | 配置角色（当前固件恒为 `ble`） |
| `bt_device_name` | string | 设备名（如 `IotHubBLE-C8E4`） |
| `runtime_mode` | string | 运行态角色（`ble`/`off`；历史 central 已收敛） |
| `adv_active` | bool | 当前是否广播（诊断快照；连接态为 false 属正常） |
| `connected` | bool | 是否有 BLE 连接（peripheral/central 任一） |
| `adv_retry_count` | number | 广播看门狗累计重试次数（P0-6；**非 0 = 看门狗曾介入**，配合 §2.1 的 >30s 不可见判读） |
| `last_error` | string | 最近 BT 错误（`adv_restart:22` 持续出现 = host 级故障需复位；空 = 正常） |

### 6.3 `network.status`

```json
{"id":"4","version":"1.0","cmd":"network.status","args":{},"token":"<TOKEN>"}
```

`data` 字段：

| 字段 | 含义 |
| --- | --- |
| `sta_connected` | 运行时 STA 连接 |
| `sta_has_ip` | 运行时已拿到 IP |
| `sta_ip` | 运行时 IP（可能为 `0.0.0.0`） |
| `last_disconnect` | 最近断开原因 |
| `connected_ssid` | **运行态**实际关联的 SSID（自动回退时与 `sta_ssid` 不同；断连时为空串） |
| `connected_profile` | 运行态 SSID 对应的已保存 profile 下标；`-1` 表示当前 SSID 不在 profile 列表里（如 fast_path 直连正式 SSID）。**仅供诊断**：下标随 `profile.delete` 漂移，不是稳定标识，客户端勿作 key 用（稳定标识用 `connected_ssid`） |
| `sta_ssid` | 正式配置 SSID（config 域，不代表当前连的就是它） |
| `password_set` | 正式配置口令已设置 |
| `mode` | `sta` |
| `mqtt_connected` / `mqtt_last_error` | MQTT 状态 |
| `trial` | `{state:"idle"}` 或 `{state:"got_ip",trial_id,ssid}` |

注意：`operation.get` 返回 `got_ip` 时，`network.status` 可能仍显示 `sta_connected=true / sta_has_ip=false / 0.0.0.0`；客户端应等待 `sta_has_ip=true`（以及 MQTT 自行恢复），不要只凭 apply success 判断。

**重要：`sta_connected=true` 不等于“正式配置的 AP 还连着”。** 非静态模式下，正式 AP 关停/不可达后，设备可能自动连接另一个已保存 profile（例如 CMCC-502 关停后连到 TQ2018）。此时 `sta_connected=true` 是真实的，但 `sta_ssid` 仍是正式配置的 CMCC-502，`sta_ip` 已变成另一个网络的地址；小程序不能只用 `sta_connected` + `sta_ssid` 判断当前 Wi-Fi。应同时看 `sta_ip`、`mqtt_connected` 和运行态 `connected_ssid`。`connected_ssid` 是加法字段（固件已暴露，旧客户端忽略即可）：App 只有在 `connected_ssid === sta_ssid` 时才能判“正式网络在线”；缺失该字段的旧固件只能记“未取证”，不能凭 `sta_connected` + `sta_ssid` 判在线。T4 做“无 IP 救援”测试时，应关闭所有已保存 AP 或先删除其他 profile（如 TQ2018），否则设备会自动回退，测不到真正的 no-IP。

### 6.4 `network.scan`

```json
{"id":"5","version":"1.0","cmd":"network.scan","args":{},"token":"<TOKEN>"}
```

`data`：

```json
{
  "status":"ok",
  "count":2,
  "aps":[
    {"ssid":"<SSID>","rssi":-52,"auth":3,"bssid":"AA:BB:CC:DD:EE:FF"},
    {"ssid":"<SSID2>","rssi":-70,"auth":0}
  ]
}
```

- `auth` 是 Wi-Fi auth mode 数值；`bssid` 可能省略。
- 长响应，按 §4.2 重组；扫描本身可能耗时数秒，客户端超时建议 ≥30s，不要用短于扫描窗口的 2–3s 超时。
- 设备在 STA 失败/无 IP/MQTT down 时仍应能扫描；若 scan 返回 `network_failed`，提示用户稍后重试，不要假设必须连上 AP 才能配网。
- 小程序显示 SSID/RSSI；不要把密码回显到日志。

### 6.5 `network.tryconnect`

```json
{
  "id":"6",
  "version":"1.0",
  "cmd":"network.tryconnect",
  "args":{
    "ssid":"<SSID>",
    "password":"<WIFI_PASSWORD>",
    "idempotency_key":"<KEY>"
  },
  "token":"<TOKEN>"
}
```

成功受理：

```json
{"id":"6","ok":true,"data":{"operation_id":"<OP_ID>","state":"accepted"}}
```

约束：

- 同一时间只允许一个活动网络 operation；已有 active 时返回 `busy`。
- 终态保留统一 **600s**（所有终态相同；保留期内 `operation.get` 仍可查证）。同 `idempotency_key` 的迟到重试在 600s 幂等窗口内返回原终态（检查表第 15 项的 ≥5min 保证不变）。
- 槽满（4 条终态记录都在保留期）且无活动 operation 时，设备**覆盖最老的终态记录**受理新请求，不再返回 `no_slot`；`no_slot` 仅在极端竞态（如 worker 创建失败路径）出现。若真机仍频繁出现 `no_slot`，按旧固件对待：不要当成 Wi-Fi 密码错误。被覆盖的记录不区分终态类型与年龄（纯 FIFO）。
- 相同 `idempotency_key` 重试会返回原 operation，不会重复启动；新事务必须换新 key。被覆盖回收的 operation 再次 `operation.get` 返回 `not_found`。
- 设备候选超时约 15s；accepted TTL 20s，got_ip TTL 300s。
- 密码错误/目标不可见/连接失败最终表现为 operation `failed`，`error` 为 `wrong_password` / `ap_not_found` / `connect_failed` / `timeout`。
- 发起后不要立刻重复 `tryconnect`；先 `operation.get`。

### 6.6 `operation.get`

```json
{"id":"7","version":"1.0","cmd":"operation.get","args":{"operation_id":"<OP_ID>"},"token":"<TOKEN>"}
```

`data`：

```json
{"operation_id":"<OP_ID>","state":"connecting","error":"none"}
```

`state`：`accepted` → `connecting` → `got_ip` → `committing` → `success`；终态还有 `failed`、`cancelled`、`expired`。

`error`：`none`、`wrong_password`、`ap_not_found`、`wifi_scan_failed`、`connect_failed`、`timeout`、`cancelled`、`internal_error`、`cleanup_failed`、`storage_failed`、`rollback_failed` 等。

`got_ip` 时可能带 `trial_id`、`ssid`；apply 必须在这个 trial 有效期内完成（trial TTL 300s）。

轮询建议：500ms 一次；只有终态才停止。不要用固定 15s 一次 sleep 代替轮询。

### 6.7 `network.apply`

```json
{"id":"8","version":"1.0","cmd":"network.apply","args":{"operation_id":"<OP_ID>"},"token":"<TOKEN>"}
```

成功：

```json
{"id":"8","ok":true,"data":{"operation_id":"<OP_ID>","state":"success","saved":true,"applied":true}}
```

- 只允许 `got_ip` 且 trial 有效；否则 `operation_state` / `trial_invalid`。
- 重复 apply 是幂等的：已 success 时返回 success/saved/applied。
- apply 成功不等于 IP 立即可见、也不等于 MQTT 已连；继续用 `config.get` / `network.status` 等待 `sta_has_ip=true` 和 MQTT 恢复。
- apply 后旧临时候选被清理；正式配置只由 apply/config.set 修改。

### 6.8 `network.cancel`

```json
{"id":"9","version":"1.0","cmd":"network.cancel","args":{"operation_id":"<OP_ID>"},"token":"<TOKEN>"}
```

成功：`{"state":"cancelled"}`。重复 cancel 幂等返回 cancelled；已 success/committing 时返回 `operation_state`。取消后终态保留 600s（与其他终态一致），不要立即用同一 operation_id 重新 apply。

### 6.9 `network.profile.list` / `delete`

```json
{"id":"10","version":"1.0","cmd":"network.profile.list","args":{},"token":"<TOKEN>"}
```

`data.profiles` 为 `[{ssid,password_set}]`，不返回口令。`network.profile.delete` 参数 `{"ssid":"<SSID>"}`；不要删除当前正在使用的唯一 profile，除非已准备好重新配网。

### 6.10 `config.set`（v1 与 v0 的边界）

- **v1 `config.set`**：`args.patch` 只接受非 network 域；提交 `sta_*`/`net_mode` 等 network 字段会返回 `invalid_argument`。
- **v0 `config.set`**：用于 network/静态 IP 等字段，例如：

```json
{
  "id":75,
  "method":"config.set",
  "params":{
    "net_mode":"sta",
    "sta_ssid":"<SSID>",
    "sta_password":"<WIFI_PASSWORD>",
    "sta_use_static":false
  },
  "token":"<TOKEN>"
}
```

- `net_mode` 只接受 `sta`；`ap`/`apsta` 返回 `invalid_config`。AP schema 已删除，`ap_ssid`/`ap_password` 字段会被忽略（`changed=[]`），不要再用它们。
- 含静态 IP 的 275B v0 命令必须 20B 分片；`effect:"reboot"` 时设备会在响应后重启，小程序需重新连接/登录。
- 普通配网优先用 `network.tryconnect → operation.get → network.apply`，不要直接拼 `config.set` 网络字段；后者适合静态 IP/固定配置的产线场景。

### 6.11 可选命令

`led.set/toggle`、`relay.set/toggle`、`io.set`、`uart.send`、`auth.admin.set`、`provisioning.pin.set` 已在 v1 白名单，但不是 T4 配网验收必需；按产品权限使用。`auth.admin.set`/`provisioning.pin.set` 属敏感写，当前 `security.sensitive_writes_allowed=false`，不要默认可用。

`auth.admin.set`（v1）映射到设备的 `web.auth.set`；改密成功后响应体带 `sessions_invalidated: true`，设备已作废所有既有 token（含 BLE 与其他本地来源）。设备先构造该成功响应再作废会话，发送路径不读 token，因此客户端应能收到该响应；当前连接的下一条命令需重新 `auth.login`，不要复用旧 token。

## 7. DATA 数据通道

### 7.1 事实

- DATA RX 0002 写入 → `data_pipe` 原始字节队列（深度 16）→ 按路由/DATA TX 0003 发出。
- DATA 是**原始字节管道**，没有应用层帧头、序号、ACK、重传、流控或设备端帧重组。
- GATT 写 success **不代表**数据已送达；DATA TX 未订阅时写入仍可能成功，但数据被丢弃。
- DATA TX 没有 CMD TX 的 20ms 片间延时，也没有失败重试；部分发送时统计仍可能按整块计。
- 断连没有显式 `data_pipe` 队列 flush/会话 ID；T3 未复现旧字节混入，但不能据此宣称结构隔离。
- DATA 多片发送（从 UART/MQTT 注入大帧）未在 T3 直接实测；BLE→BLE 回环下 MTU23 消息不超过 20B。

### 7.2 T4 数据测试

- 订阅 DATA TX 0003；用 `data.loopback`（v1，测试专用）打开 BLE→BLE 回环：
  `{"cmd":"data.loopback","args":{"enabled":true}}`；测试后关闭。
- 单帧 20B、200B/10×20B、600B/30×20B、重复帧、32×20B 突发；逐字节比较。
- CMD 长响应期间同时发 DATA；两路特征独立，不应串道。
- 断连重连后发唯一 marker，确认没有旧字节；记录 pre-marker 是否为 0。
- 记录 DATA notify 长度、丢/重/乱序；如果业务要求可靠传输，小程序必须自行加帧头/序号/ACK/重传，或另立协议。**不要用 GATT 写 success 当端到端 ACK。**

## 8. 典型配网流程（小程序）

1. 扫描 → 连接 → 发现服务/特征。
2. 订阅 CMD TX 0005（需要 DATA 再订阅 0003）。
3. `device.info` → `auth.login`；保存 token。
4. `network.scan`；用户选择 SSID、输入 Wi-Fi 口令（不记录明文）。
5. `network.tryconnect`，key 例如 `prov-<timestamp>-<random>`；保存 operation_id。
6. 每 500ms `operation.get`：
   - `connecting/accepted`：继续；
   - `got_ip`：进入 apply；
   - `failed`：根据 `error` 提示口令/目标/超时；可重新扫描/重试；不要立即复用旧 key；
   - `cancelled/expired`：重试。
7. `network.apply`；成功后轮询 `config.get`/`network.status`，等待 `sta_has_ip=true` 和 MQTT；不要只看 apply success。
8. 如设备重启/断连：重新连接、订阅、登录，再确认 `config.get` 的 `sta_ssid`/`sta_use_static` 与 `network.status`。
9. 退出/失败时 cancel 活动 operation；清理 token；关闭连接。

## 9. 错误码

v1 错误外壳：`{"id":"...","ok":false,"error":{"code":"...","message":"..."}}`

| code | 客户端处理 |
| --- | --- |
| `unauthorized` | 重新 login，重试一次 |
| `rate_limited` | 等 ≥350ms，重试 |
| `invalid_argument` | 修正 args（缺字段/类型/校验失败） |
| `unknown_command` | 升级协议/检查 cmd 拼写 |
| `line_too_long` | 命令必须 ≤512B，重新分包 |
| `invalid_json` | 检查分片/换行/UTF-8 |
| `unsupported_version` | 使用 `version:"1.0"` |
| `busy` | 已有 active operation/trial；先查询或取消，不要新开 |
| `no_slot` | 终态槽占满且未自动回收（新固件槽满会覆盖最老终态记录，正常不再出现）；提示稍后重试，不要清理 active |
| `not_found` | operation 已回收/ID 错误；重新发起（新 key） |
| `operation_state` | 当前状态不允许 apply/cancel；先 operation.get |
| `trial_invalid` | got_ip 的 trial 过期/不匹配；重新 tryconnect |
| `wrong_password` | Wi-Fi 口令错误；用户重新输入 |
| `ap_not_found` | 目标 SSID 不可见；重新扫描 |
| `connect_failed` / `network_failed` | 候选连接失败；可重试 |
| `wifi_scan_failed` | 候选预扫描两次失败（射频/驱动过渡态），未进入连接；稍后重试，不要提示口令或 AP 问题 |
| `storage_failed` / `rollback_failed` / `apply_failed` | 配置保存/回滚失败；保持原配置，提示重试 |
| `internal_error` | 记录日志，重试/复位 |

`operation.get.data.error` 直接返回 `timeout`、`wrong_password` 等操作错误，不经过 v1 错误外壳。

## 10. 安全与凭据

- BLE 链路不加密、不配对；token 是应用层鉴权，明文链路上可被本机嗅探。T4 只做功能验收，不宣称链路机密性。
- Wi-Fi SSID/口令和管理员凭据由现场用户输入；不要硬编码、不要写入日志/结果/仓库。设备不回显口令，只回 `*_set`。
- token 只保存在内存；断开/退出清空；不要上传云端。
- 设备没有 AP 配置通道；AP schema 已删除。若 STA 配网失败，仍通过 BLE 重新扫描/尝试，不要引导用户找设备 AP。

### 11.1 小程序侧配合 T4 的调整清单

**P0（不调整就不能签收 T4-A）**

1. **扫描时序/自检评分**：扫描必须在连接前做；连接态下扫描 0 台不是故障，不能记 WARN/FAIL。连接后设备页需要重扫时，先断开再扫；设备断连会恢复广播。
2. **20B 分包测试的证据**：不要只以 `not_found` 推断“整行解析成功”。记录 420B 请求的完整命令、请求 id、响应 id；最好使用一条无副作用的已知命令/故意不存在的 operation id。若使用有效命令，必须同时校验预期业务结果，不能把业务错误当解析成功。
3. **长响应完整性**：`config.get` 当前约 1107B（以实测为准）；必须按 JSON 边界/UTF-8 重组，不能按单个 notify 判断完整；检查 `mqtt_connected`、`sta_has_ip`，并确认 `network` 中不再有 AP 字段。
4. **AP schema 兼容**：删除小程序里的 AP 配置 UI/字段解析；不要再读 `ap_ssid`、`ap_password_set`、`startup_fallback_to_ap`，不要再发送 `ap_ssid`/`ap_password`；`net_mode` 只允许 `sta`。旧字段被设备忽略（`changed=[]`），小程序不能把“未改变”当成功配置 AP。
5. **网络救援必须测**：设备无 IP/MQTT/STA 失败时，小程序配网页仍要能 scan→tryconnect→operation.get→apply；不要求设备先在线，不出现 AP 模式，不引导用户找设备 AP。测试时关闭**所有已保存 AP**（或先删除 TQ2018 等 profile），否则设备会自动回退到另一个已保存网络，`sta_connected` 仍为 true，测不到真正的 no-IP；最后确认 `sta_ip` 是目标网络、`mqtt_connected=true`。
6. **成功配网/apply 未测**：现有自检只覆盖传输，没有成功 tryconnect/apply。补测：输入现场 SSID/口令（不硬编码）→ accepted → polling → got_ip → apply → 等 IP/MQTT → 重启/重连后确认正式配置。
7. **T4-A/T4-iOS 分账**：当前先跑 Android T4-A；iOS 无设备，标记 BLOCKED，不得用 SKIP 计入 PASS；单端日志不能签收 T4。记录 OS、微信版本、协商 MTU、实际 `name`/`localName`、notify 分片长度、断链次数。
8. **DATA 全矩阵**：当前只测了双通道中的 200B。补单帧、长帧、连续帧、退订、断连 marker；DATA 仍没有应用 ACK/序号/重传/流控，报告中必须保留“可靠性未签收”，不能把 200B 逐字节一致扩展成可靠传输结论。
9. **错误/限频/token**：串行命令 ≥200ms；处理 `rate_limited`（≥350ms 重试）、`unauthorized`（重新 login）、`busy`/槽位覆盖（不重开、不误报密码错误）、`operation_state`/`trial_invalid`；长响应/operation 响应超时至少 10s。
10. **报告自检项**：当前 SKIP 的网络救援、成功 apply、错误口令/cancel/busy、token 失效、DATA 全矩阵，都应成为 T4 的必测项；SKIP 不能算 PASS。
11. **A 阶段改密**：`auth.admin.set` 成功响应含 `sessions_invalidated:true`；小程序收到后立即丢弃本地 token，下一条命令必须重新 `auth.login`；旧 token 应返回未授权，新口令可登录、旧口令拒绝。
12. **A 阶段 token 大小写**：token 按原样保存和回传，不做小写归一；大写有效，小写 v1 `unauthorized`、v0 `auth_required`。
13. **A 阶段错误码**：`auth.login` 的 `internal_error` 与 `invalid_credentials` 分开提示；`wifi_scan_failed` 不提示口令/AP 不存在；`connected_ssid` 用于判断正式网络是否在线。

**P1（建议同步调整）**

- `config.set` 方言：v1 拒绝 network 域；network/静态 IP 用 v0，275B 命令按 20B 分片；普通配网优先 `network.*` 流程，不拼 `config.set` 网络字段。
- 长响应期间 `operation.get`：请求可以被处理，但响应可能排在长响应之后；不要用 2–3s 短超时，不要重复发送同一命令。
- iOS/Android：Android 定位权限/定位服务、`wx.setBLEMTU` 可选；iOS 系统管理 MTU、名称可能走本地名；两端都用 20B 保守写。
- 重连：重新发现特征、重新订阅 CMD TX/DATA TX、重新 login；清空 JSON 缓冲和旧 operation 状态；token 断连即失效。
- DATA 断连：不要假设 `data_pipe` 会 flush；重连后用唯一 marker 验证，不要把旧数据混入新会话。
- 日志脱敏：SSID、Wi-Fi 口令、管理凭据、token、BSSID 按需脱敏；不要把真实口令写入自检报告或仓库。

自检清单建议改成：**PASS / EXPECTED（扫描 WARN 归此类）/ FAIL / SKIP（不得计入 PASS）**，并把上述 P0 项加入 T4 报告模板。
