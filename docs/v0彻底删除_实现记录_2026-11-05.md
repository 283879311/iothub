## 3. 设备验证（BLE 侧，PASS）

烧写终版 `dc29aa86…` 后（BLE 侧代码与 `e0e794a6…` 相同，仅 mqtt.c 增加 id 回填）：

| 用例 | 结果 |
| --- | --- |
| `device.info` | `IotHub-C8E4`，`protocol_versions=["1.0"]` |
| canonical 命令 `io.get` / `network.status` / `config.get` / `gpio.status` / `uart.runtime` | 全部 `ok=true` |
| `io.set {"relay_on":true/false}` | 两次均 `ok=true`，`changed=["relay_on"]`，状态正确回落 |
| v0 帧 `{"id":42,"method":"getStatus","params":{}}` | `{"id":42,"ok":false,"error":"unsupported_version"}` —— **回带数值 id** |
| v1 外壳 + 旧名 `getStatus` / `network.restart` / `network.profiles` / `web.auth.set` / `setConfig` | 全部 `unknown_command` |
| 网络状态 | `192.168.1.50` / `cfg_state=static` / TB MQTT 在线 |

**测试中发现并修掉的回归**：删除 v0 分支后，v0 拒绝回包丢了数值 `id`（`wrap` 只走 v1 包装）。已改为在拒绝分支直接构造带 id 的 v0 壳并发送——这条正是 P0 阶段明确要求保留的契约，只有上设备才暴露。

## 4. 行为变化（对客户端的影响）

- v0 客户端：`unsupported_version`（BLE 带 id，MQTT 用 v0 形状壳）——与删除前一致；
- v1 客户端用旧方法名（如 `cmd:"getStatus"`）：从"能执行"变为 `unknown_command`——**这是本次唯一的破坏性变化**，小程序/TB 端若还有旧名调用会被明确拒绝；
- 内部调用：`state.c` 触摸 LED、`network.apply` 子上下文均改为 canonical 直调，行为不变。

## 5. 未完成：MQTT 40 例回归（环境阻塞）

- 现象：PC 与设备同 SSID（CMCC-502）、同 BSSID（`5C:C0:A0:BD:F6:28`）、同网段（.19 / .50），但 **PC→设备 ping 100% 丢包**，设备→PC 的 TCP 也超时；同时设备访问 TB（公网）正常；
- 判定：**AP 客户端隔离（client isolation）**，不是固件问题（10:20 同一套环境还能通，期间路由器侧发生变化）；
- 影响：本地 amqtt 方案无法进行，MQTT 侧只验证了"设备仍在 TB 在线"，未跑 40 例；
- 需要：关闭路由器的"AP 隔离/无线隔离"，或换一台不隔离的 AP，然后重跑（命令与上一轮相同）。

**另试过的旁路（不可用）**：用 TB REST `POST /api/plugins/rpc/twoway/{deviceId}` 发 v0 RPC，想在不等局域网的情况下验证 MQTT 拒绝壳的 id 回填。结果：租户 JWT 刷新成功，但 RPC 返回 **409**，且设备串口完全没有 `rpc/request` 入站记录——TB 侧 RPC 未投递到设备。该旁路作废；MQTT 侧的 id 回填只能等 40 例回归时由 T01 用例验证（runner 会检查 `success:false` + id）。临时 JWT 与登录响应已删除，未落盘。
