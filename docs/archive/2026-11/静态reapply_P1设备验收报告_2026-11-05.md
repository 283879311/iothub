## 2. P1-E2：诊断字段（PASS）

| 场景 | 观测 |
| --- | --- |
| BLE 已连接、刚发过命令 | `device.status.ble`：`conn_find=0`、`rx_age_ms=8` |
| 已连接、26s 无写入 | diag 行：`adv=0 conn=1 cf=0 rx_age=27968` |
| 已连接、从未写入 | diag 行：`conn=1 cf=0 rx_age=-1` |
| 断开/无链路 | diag 行：`conn=0 cf=7 rx_age=-1`（7 = `BLE_HS_ENOTCONN`，符合设计） |

`cf` 与 `conn` 的组合可区分“应用层标志 vs 协议栈链路”，`rx_age` 提供“链路在但无应用层流量”的判据——DEF-BLE-001 的 H1/H2 判别条件已具备。

## 3. P1-E3：`network.reconnect` ×3（PASS）

r3 三轮串口序列一致：

```
apply_await_start gen=N
W apply_start_probe gen=N t=142..149ms driver_started=1
I apply_cfg: started (gen=N) / net_config_state=static
I sta_start_evt gen=N await=0 consumed=N completed=N probed=1
W sta_start_evt gen=N ignored (probe completed this gen)
```

- **0 次 `apply_start_timeout`、0 次 `retry_candidate`**（P0 是 4/4 超时后靠重试救回）；
- 迟到事件在 **+2.3s** 到达并被拦下，**没有再出现 `run -> init`**；
- 每轮 IP 保持 `192.168.1.50`、`cfg_state=static`；耗时 3.9–4.2s（与 P0 的 3.7s 相当——探测只改判据，不缩短驱动起链时间）。

**r2 的发现（已修复）**：未加拦截时，迟到事件会把刚建立的连接打断成 `run -> init` 并重连，单轮拉长到 6.8s。这是 P1 自引入的回归，已由 `probed` 拦截修复，日志里以 `probed=1 / ignored` 可见。

## 4. P1-E5：N06 回归（最终 PASS，含两次状态性失败）

| 轮 | 结果 | 原因 |
| --- | --- | --- |
| 第 1 次 | 35/38，N06a 无响应，设备落 `.28` | tryconnect 受理回包（`response/37`）在 WiFi 重启前未被 broker ACK；runner 没收到 → 从未发 apply → trial 孤儿存活并把设备留在 DHCP `.28` |
| 第 2 次 | 34/38，P06/N06a 均 `busy` | 上一轮孤儿 trial 仍占操作槽 → `busy` |
| **第 3 次（重启清槽后）** | **38/40 PASS，0 FAIL，2 SKIP** | 与 P0/a792 基线一致；N06a/b/c 全 PASS |

第 3 次 N06 的 apply 同样走探测：`apply_start_probe gen=2 t=142ms` → 迟到事件 `probed=1` 被拦 → `apply success`、`.50` 保持。

**定性**：第 1/2 次的失败不是 P1 代码路径（未改 `mqtt.c`/operation 槽），而是“异步受理回包与 WiFi 重启的竞态 + 孤儿 trial 占槽”。**这是独立的可靠性缺陷候选**，建议单独立项：MQTT 源 `network.tryconnect` 受理回包应在触发 WiFi 重启前确保出队/ACK，或 trial 超时/断链时必须自动释放操作槽。
