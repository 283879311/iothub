## 2. 阶段 B 用例（每条独立前置、独立归档；R6 拆分为互斥的 R6-WD / R6-APPLY）

| 用例 | 前置 | 步骤 | 通过判据 |
| --- | --- | --- | --- |
| **R4a** | `diag.m1hook status` 显示 `restart_wake_fail=0`；owner=NONE；无活动 op | ①布防 `restart_wake_fail=1` ②tryconnect(`302`+错口令) ③2s 后 BLE `network.cancel` | 日志 `hook: restart_wake forced fail (R4 injection, cleanup path)` + `cleanup wake failed -> CLEANUP_FAILED op=… by tryconnect_release`；owner=`CLEANUP_FAILED`；`status` 计数归 0 |
| **复位** | — | 复位设备（esptool run / 断电） | 重新进入 app；owner 回 NONE（清态） |
| **R4b** | 复位后：owner=NONE、无活动 op、`restart_wake_fail=0` | ①布防 `restart_wake_fail=1` ②tryconnect(`302`) 成功至 **GOT_IP** ③`network.cancel`（触发 `cleanup_request` NOTIFY） | 日志 `cleanup wake failed -> CLEANUP_FAILED op=… by cleanup_request`；`cleanup_request` 返回 false；owner=`CLEANUP_FAILED`，**不得**回 NONE |
| **R6-WD**（watchdog 专项） | FI 镜像；先 `clear` 确认 `cleanup_hold_ms=0` 且 `apply_fail` **未布防** | ① 布防 `cleanup_hold {"timeout_ms":27000}`（一次性；**不布防 apply_fail**）② 触发一次 cleanup（cancel 一个 GOT_IP op） | 依次出现：<br>· ≈12s：`cleanup watchdog: re-notify op=… elapsed=…`<br>· ≈25s：`cleanup watchdog: abort requested (owner stays CLEANUP) op=…`<br>· ≤500ms 后：`hook: cleanup hold end(abort)` → `cleanup aborted by watchdog op=… by cleanup_hold_abort`<br>· `cleanup state: -> CLEANUP_FAILED`<br>· 之后 tryconnect 返回 `cleanup_failed`（粘性确认） |
| **R6-APPLY**（可选，单独一轮，复位后） | FI 镜像；`cleanup_hold` **不布防** | ① 布防 `apply_fail {"stage":"wifi_stop","count":1}` ② 触发一次 cleanup（cancel 一个 GOT_IP op） | `apply fail` → 退避（0.5s/1s）→ `cleanup failed op=…`（明确终态）→ owner 回 NONE（经 step_locked 统一出口）——**验证 apply 失败路径，不涉及 watchdog** |

**两次 R4 之间必须单独复位**（`CLEANUP_FAILED` 粘性，否则 R4b 会被入口 `DENY_FAILED` 拒绝）。
**终态差异（v11.5）**：R6-WD 以 `CLEANUP_FAILED` 结束（粘性）→ **之后需复位**才能继续；
R6-APPLY 以 `cleanup complete`（owner 回 NONE）结束 → 无需复位即可继续。

> **互斥声明（评审指出）**：27s `cleanup_hold` 会先撞 25s abort 并经
> `cleanup_hold_abort` 提前返回——**不会**执行 apply，因此 R6-WD 中**不存在**
> `cleanup_backoff` 预期；`apply_fail` 只在 R6-APPLY（无 hold）中验证。两条
> 退出路径不得写成一条连续时间线。

### 2.1 R4b 的精确命令路径与证据链（源码核实）

| 步 | 动作 | 代码路径 | 期望证据 |
| --- | --- | --- | --- |
| 1 | BLE v1 `network.cancel {"operation_id": <op>}` | `cmd_v1` V1_KIND_CANCEL → `app_cmd_net_cancel_adapter` → `app_cmd_net_cancel_async`（读 **`operation_id`**，非 `trial_id`）；内部 `if (app_operation_cancel(op) != ESP_OK) { err="operation_state"; return false; }` | **cleanup 失败时预期 cancel 返回失败**：`{"ok":false,"error":{"code":"operation_state"}}`（`app_operation_cancel` 返回 `ESP_FAIL`，见 `operation.c:498-504`）；最终态以 `operation.get` 为准 |
| 2 | 取消触发 op 的 cleanup | `app_operation_cancel` → `cleanup_fn = app_cmd_net_async_cleanup` | 串口 `rescue=restore_persistent op=… (cleanup without commit)` |
| 3 | 请求 owner 清理 | `app_cmd_net_async_cleanup` → `app_wifi_cleanup_request()`；此时 owner 已为 **NONE**（tryconnect run 在 GOT_IP 后已 release，日志 `TRYX -> NONE`） | `op_owner: NONE -> CLEANUP by cleanup_request` |
| 4 | 注入命中 | `restart_wake()` 返回 false → `app_wifi_cleanup_wake_failed("cleanup_request")` | `cleanup wake failed -> CLEANUP_FAILED op=… by cleanup_request` |
| 5 | 请求方失败 | `app_wifi_cleanup_request` 返回 false | `rescue=restore_persistent failed (cleanup request) op=…` |
| 6 | operation 终态 | `operation.c:493` → `state=FAILED, error=cleanup_failed` | `operation.get` → `{state:"failed", error:"cleanup_failed"}` |
| 7 | 粘性确认 | 后续 tryconnect 被 `DENY_FAILED` | 响应 `cleanup_failed` |

**前置**：必须等到 `state == got_ip` **且** 日志出现 `TRYX -> NONE by tryconnect_release` 之后才发 cancel，
否则 owner 仍为 TRYX/SHARED，会走 HANDOVER 而非 NOTIFY（那是 R4a 的路径）。

## 3. 停止条件

- 门禁 rc≠0 / 冻结 BIN sha 不符 / 写入后副本 sha 不符 → 不写 Flash；
- 烧录后 `device.info.build_sha ≠ c346b934d` → STOP；
- 任一 R 项失败、出现"owner=NONE 但 cleanup 未执行"的假恢复 → STOP；
- 录制链不完整、证据缺失 → STOP（不补造）。

## 4. 边界

允许：**仅 65D8** 烧录 FI 镜像（app 分区 0x10000）、复位、串口录制、BLE/MQTT 测试命令、
`diag.m1hook` 注入与 `clear`、回归期临时复位。

expired/op-V、阶段 A 已完成的用例重复。
