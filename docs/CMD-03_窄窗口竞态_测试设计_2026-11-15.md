## 1. 被证伪的命题

> **P0（缺陷命题）**：当 `cancel()` / `expire_one()` 已置 `expiring=true`、`cleanup_fn` 已返回（`s_net_async` 与 `s_net_trial` 已被清理），但 operation 尚未 finalize（状态仍是 `CONNECTING`）时，若 `app_wifi_try_connect_ip()` 恰好返回 `APP_WIFI_TRY_OK`，worker 会：
> 1. 通过 `state==CONNECTING && generation` 守卫（cmd.c:583–591）；
> 2. 调 `app_cmd_net_store_trial()` 在 cleanup 之后**重新写入 `s_net_trial`**（含候选 SSID/口令，TTL 300s）；
> 3. 使后续 `tryconnect` 在 300s 内命中 `trial_busy` → 返回 `busy`。

**可证伪性要求**：测试必须在**未修复的基线上失败**（复现残留 trial / busy），在**修复后通过**。只写"永远通过"的测试视为无效。

### 4.2 时间与并发模型

- `portMUX` 映射为 `pthread_mutex_t`（**普通锁**，若代码在临界区内重入会立即死锁——这本身是断言）。
- `xTaskCreate` 映射为 `pthread_create`；`ulTaskNotifyTake` 用条件变量 + **虚拟时间**超时
  （timeout 到期按虚拟时钟判定，不按墙钟），使 worker/expire 的 1s 节拍在测试中可控。
- `esp_timer_get_time` 读虚拟时钟；`vTaskDelay` 等待虚拟时间前进。

**时钟驱动模型（修正：必须独立线程，否则死锁）**

`app_operation_test_hook_pause()` 是**同步**的：`app_operation_cancel()` 进入 hook 后会原地循环
等待虚拟时间推进。若由调用 `cancel()` 的主线程负责推进时钟，主线程永远阻塞在 `cancel()` 内，
形成死锁。因此：

1. 测试主线程调用 `cancel()`（或被 expire 任务触发），**不推进时钟**；
2. 独立的 clock-driver pthread 等待"hook 已进入"事件后，才以固定步长推进虚拟时间
   （步长 100ms / 2ms 墙钟）；
3. "hook 已进入"由 stub 的日志回调识别 `C1 hook: pause <tag> enter` 文本置位——hook 在进入时
   必定打印该行，属**产品代码既有行为**，不是为测试新增的接口；
4. hook 退出后 driver 停止推进，保持时钟静止，避免污染后续断言。

- 每个场景 **fork() 子进程**执行：`operation.c` 的静态表与常驻线程无法优雅销毁，fork 是唯一无泄漏的隔离方式；父进程只断言子进程退出码。

### 4.3 场景与注入点

**S1 · cancel 窗口（主场景）**

```
[主线程] app_operation_start(run_fn=fake_blocking, cleanup_fn=fake_cleanup)
[worker] CONNECTING → fake_run_fn 等待 EV_CLEANUP_DONE
[主线程] app_operation_cancel(op)
         ├─ expiring=true（O 锁内）
         ├─ fake_cleanup：置 EV_CLEANUP_DONE；返回 true
         └─ hook(cancel_post_cleanup)：暂停 hold_ms（窗口打开：state 仍 CONNECTING）
[worker] fake_run_fn 返回 ESP_OK
         预期（正确实现）：set_state(GOT_IP) 被 expiring 拒绝 → 终态 CANCELLED
         缺陷实现：守卫通过 → 调用 store_trial（Phase A 中为计数桩）→ 记录"would store"
```

- 注入点：`app_operation_test_hook_arm(hold_ms=2000, probe_to_state=APP_OP_GOT_IP)`。
  探针会在窗口内直接 `set_state(GOT_IP)` 并打印拒绝原因——这正是我们需要的确定性证据。
- 事件用 `pthread_cond` 而非 sleep：`EV_CLEANUP_DONE` 保证 worker 一定在 cleanup 之后才返回。

**S2 · expire 窗口**：同 S1，改为推进虚拟时钟越过 `deadline_ms`，由 expire 任务触发。

**S3 · 正常成功**：无 cancel，`fake_run_fn` 返回 OK → 断言 `set_state(GOT_IP)` 成功、终态 GOT_IP（防"守卫过严"回归）。

**S4 · cleanup 失败**：`fake_cleanup` 返回 false → `cancel()` 在 `if (need_cleanup && !cleanup(...))`
分支直接返回，**不会进入 `cancel_post_cleanup` hook**，因此 S4 **不参与** A1 的窗口探针断言，
只断言终态 `FAILED/CLEANUP_FAILED`。

### 4.4 Phase A 断言

| ID | 断言 | 依据 |

| A1 | S1/S2 中窗口内 `set_state(GOT_IP)` 返回 `ESP_ERR_INVALID_STATE` | hook 探针输出 + 返回值 |

## 5. Phase B：cmd 层 `store_trial` 重写验证（需代码授权）

### 5.1 现状回放（缺陷路径）

```
worker(cmd_net_async_run)              cancel 线程
────────────────────────              ─────────────
try_connect_ip 阻塞 …
                                      expiring=true
                                      cmd_net_async_cleanup(): memset(job/trial)
                                      hook 暂停 ← 窗口
返回 TRY_OK
get_status → CONNECTING/gen 一致（看不到 expiring）
store_trial()  ← 重新写 s_net_trial（当前无 active 校验）
set_state(GOT_IP) → 被拒
```

### 5.2 推荐注入方式：抽取纯判定

新增（**Phase B 才做，需批准**）：

```c
/* cmd_net_guard.h/.c：无 ESP 依赖，可 host 编译 */
typedef struct {
    bool job_active;
    bool op_match;      /* s_net_async.op == op */
} app_cmd_net_store_guard_t;

bool app_cmd_net_store_allowed(const app_cmd_net_store_guard_t *g);
/* 真值表：仅 active && op_match 为 true */
```

调用点：`app_cmd_net_store_trial()` 在**持 `J` 锁后**、写 `s_net_trial` 前取守卫值并判定；不满足则解锁返回 `false`（worker 现有分支会走 `clear_job + CANCELLED`）。

> 不改 `expiring` 语义、不改 operation 状态机；只在写入前加一道"这个 job 还归我吗"的判定。

### 5.3 Phase B 断言

| ID | 断言 | 说明 |
| --- | --- | --- |
| B1 | `allowed(active=false, match=*)` = false | 模拟 cleanup 已 memset |
| B2 | `allowed(active=true, match=false)` = false | 槽位/新 job 归属不符 |
| B3 | `allowed(true, true)` = true | 正常路径不回归 |

### 5.4 失败判据

- **基线（未修复）**：B4/B5 失败（`valid==true` / 返回 `busy`）——这就是缺陷复现。
- **修复后**：B1–B6 全通过，且 Phase A 的 A1–A6 不回归。
- 若基线也无法稳定复现（例如时序窗口靠调度难命中），则判定"机制存在但不可稳定观测"，**不得**据此直接改代码；改为记录风险 + 保留守卫设计评审。

## 6. 清理与可重复性要求

1. 每个 scenario 在 `fork()` 子进程中运行；父进程 `waitpid` 后断言退出码，**不共享静态状态**。
2. stub 的 worker/expire 线程随子进程退出被回收；禁止在父进程创建线程。
3. 虚拟时钟无真实 sleep；`vTaskDelay` shim 用条件变量等待虚拟时间，超时即失败。
4. 测试不写 `/tmp` 固定文件；如需日志，写 `mkdtemp` 目录并在退出时删除。
5. 不依赖网络、串口、BLE、NVS、任何 `/dev/*`。
6. `make -C tests/operation_host run` 必须可重复执行，连续 10 次结果一致。

## 7. 明确不覆盖

- `app_wifi_try_connect_ip` 的真实返回时序（stub 为可控 fake，只验证调用方逻辑）。
- 真实 FreeRTOS 抢占与 Xtensa 内存序（host pthread 语义更弱，**不构成**对真机数据竞争的证明）。
- `device.status` 内嵌 network 段、`operation.get` live 回落等附录 A 的其它项。
- 设备侧 `APP_C1_TEST_HOOKS` 端到端（Phase C，需独立设备授权）。
