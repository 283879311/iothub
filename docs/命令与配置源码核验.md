# 命令与配置源码核验（阶段 2 第 1 步）

> 核验基线：`feature/shared-config-cmd`，提交 `aea8dc0`（阶段 1 清单）。
> 本轮只核对源码，不修改行为。证据格式为 `文件:行号`，均对应当前工作树。

## 1. 核验结论摘要

阶段 1 清单可以作为基线，但有四个事实必须在设计异步配网前先接受：

1. `app_wifi_try_connect()` 的成功条件是 **`WIFI_EVENT_STA_CONNECTED`**，不是拿到 IP；`IP_EVENT_STA_GOT_IP` 在试连期间反而直接返回。
2. `mqtt.c` 自己监听 `IP_EVENT_STA_GOT_IP`，试连候选拿到 IP 时会独立调度 MQTT 重启，和“候选未提交”冲突。
3. `config_apply_patch()` 是 **先写 NVS、再应用域**；网络域本身只落盘，重启由调用方负责。不存在“失败回滚旧配置”的事务。
4. 主配置和 Wi-Fi profile 是两个独立 NVS 键，网络 PUT / `config.set` 都是先保存主配置、再单独保存 profile；第二笔失败时第一笔已提交。

## 3. 对阶段 1 清单的修正/补充

1. **`config.get` 的 `domains` 过滤已实现且 HTTP 实测通过**；清单中的“🟡 部分运行态”仍成立，但不要再写成“未实现 domains”。
2. **`provisioning.pin.set` 已 HTTP 实测成功**；BLE/MQTT 仍未验。
3. **`network.tryconnect` 不是“仅未暴露”**：底层函数存在，但语义是“connected 即成功”，且会改动驱动配置并恢复；不能直接视为可复用的异步试连。
4. **UART 配置不是“字段未登记”**：字段和校验都在，缺的是 `config_apply_domain_wired()` 的 UART 分支以及保存/应用顺序统一。
5. **MQTT 会在候选试连拿到 IP 时被触发**，这是阶段 1 清单没有列出的跨模块副作用，必须优先隔离。

## 5. 最小改动顺序（源码级）

1. **先修权限和响应边界，不动 Wi-Fi 状态机**：
   - 在 `cmd.c` 把 `uart.send`、`data.loopback`、BT 配置的 MQTT 来源收紧；
   - 明确 UART 配置的唯一路径（接入 `config_apply` 或保留 HTTP 专用）；
   - BLE 超长/分片失败返回明确错误，不再静默丢弃。
2. **定义候选事务契约**（仍不写状态机）：
   - 主配置与 profile 的提交顺序、失败恢复、NVS 写失败语义；
   - `CONNECTING/GOT_IP/COMMITTING/SUCCESS/FAILED/CANCELLED` 与 `operation_id` 的生命周期；
   - 取消在 `COMMITTING` 的承诺边界。
3. **在 `wifi.c` 增加候选状态机**：
   - 固定候选 SSID/口令缓冲，不新建常驻任务；
   - 用候选代次过滤事件，`IP_EVENT_STA_GOT_IP` 才置 `GOT_IP`；
   - 试连期间让 MQTT IP handler 忽略候选事件。
4. **接入 `network.status/validate/tryconnect/cancel/apply`**：
   - BLE 回调只投递；扫描/试连返回操作受理；
   - `apply` 只接受匹配的候选/`trial_id`，先确认 IP，再写主配置和 profile。
5. **回归验收**：错误密码、AP 不存在、超时、取消、NVS 写失败、旧配置恢复、试连期间 BLE 控制通道可用；记录 `free/largest` 最低值。

## 6. 结论

阶段 1 的依赖清单可以继续作为基线，但异步配网的第一行代码不应先写状态机，而应先修：

- 候选成功判定与事件归属；
- MQTT 对候选 IP 的隔离；
- 主配置/profile 跨键提交规则；
- 命令权限和 BLE 错误回包。

这四项确定后，再在 `wifi.c` 现有事件循环上实现候选状态机，才能避免“试连成功但未提交”“取消后仍然切换”“配置保存了但 profile 没保存”这三类问题。
