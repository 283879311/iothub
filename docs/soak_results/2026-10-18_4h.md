## 3. 堆水位（关键失败项）

- 三段时间共 **203 次 `html send chunk downshift`**：每次 `/config` 发送都让 WiFi TX 池扩展，
  `free` 从约 14.8KB 掉到 2–3KB，`largest` 掉到约 1KB。
- 第一段出现 **2 条 `level=critical`**：
  - `free=1616 largest=464 level=critical`，同时 `esp_littlefs: Unable to allocate FD` /
    `storage selftest: fopen failed`；
  - `free=3016 largest=1536 level=critical`，`mqtt_outbox=357`。
- 第一段 diag 的全时段最低空闲堆计数为 **`min free=44B`**；它与上面采样到的
  `free=1,616/largest=464` **不是同一瞬间**，不能把 44B 和 464B 当成同一采样点。
- 分段最低（来自 downshift/临界日志）：

| 段 | downshift 次数 | 最低 free/largest | critical |
| --- | ---: | ---: | ---: |
| 第一段 | 136 | 1,540 / 1,216（临界行 1,616 / 464） | 2 |
| 续跑 | 34 | 2,356 / 1,024 | 0 |
| 收尾专项 | 33 | 2,184 / 992 | 0 |

- 结论：页面发送本身就会把堆压到 mem_guard 临界线以下；命令/MQTT 并发时风险更高。
  第一段 MQTT 断链发生在页面发送之后（`transport_base: Poll timeout`），
  设备约 2.8s 重连；事件顺序只能作为线索，不能单独证明因果。

### 3.1 源码核查（本轮未改代码）

- `/config` **不是整页解压到 RAM**：`config.html.gz` 由常驻 `s_html_cached`（`FILE*`，
  `_IONBF`）读取，`chunk` 是静态 `char chunk[2048]`，没有整页堆缓冲；23,961B 是浏览器解压后大小。
- `chunk_bytes` 初始 2048，但预检在 `free<20KB || largest<8KB` 时先降到 1024；
  发送中按 `largest` 再降 512/256。日志里的 203 次 downshift 是这个降档路径。
- 峰值来自 `send()` 链路：`app_http_send_override` → lwIP pbuf → Wi-Fi 动态 TX 缓冲。
  当前 `CONFIG_ESP_WIFI_DYNAMIC_TX_BUFFER_NUM=4`、`TCP_SND_BUF_DEFAULT=2880`、
  `TCP_WND_DEFAULT=2880`；page 发送会触发 TX 池扩展。
- `s_html_serving` 目前只用于推迟 **MQTT 重连/连接尝试**（`mqtt.c:1312`），
  遥测/属性任务不发检查；命令 RPC 响应是直接 publish，不应被阻塞。
- `app_mqtt_publish_json` 用 `esp_mqtt_client_publish`（QoS1）发布遥测/属性，
  没有 outbox 阈值检查；`mqtt_outbox` 与 Wi-Fi TX 队列是两个层级，不能只看 outbox。
- `diag` 每 30s 的 `storage selftest` 会 `fopen` 页面文件；堆临界时它自己也会
  `Unable to allocate FD`，是页面发送期间可避免的竞争分配。

## 5. 未覆盖项

- UART1 引脚/线速/overrun（无 GPIO17↔18 跳线或 USB-TTL）。
- DUT 作为 BLE central 的 1:1 数据（无真实 Ubuntu + BlueZ 主机；角色互换只验证连接/订阅/广播）。
- MQTT 高吞吐 RPC/数据面 QoS1（无 LAN broker 或 TB 租户 API；未使用第二客户端复用 DUT token）。
- 手机 BLE 数据/CMD（手机未连接）。
- 真实浏览器 JS 轮询（无 Playwright/Chromium；仅服务端页面请求）。
- OTA/恢复出厂（中断性/破坏性，未纳入）。

## 6. 判定与后续

- **功能面**：HTTP/API、命令层、页面发送、BLE 角色互换、MQTT 重连均可用。
- **稳定性面**：FAIL。页面发送的堆峰值足以触发 critical、LittleFS FD 失败和 MQTT 断链。
- 建议下一步（按优先级）：
  1. 页面发送前提高预留门槛，或初始 chunk 直接降到 256/512B，避免首次 1024B 发送触发的 TX 池扩张；
  2. 页面发送期间等待 MQTT outbox/TX 静默，或降低遥测/属性并发；
  3. 在 soak 断言中加入串口 `level=critical` 与 downshift `largest<2048`，不能只看 status 5s 采样；
  4. 修复后用 LAN broker + 真实 Ubuntu 蓝牙主机补 MQTT 高吞吐、UART、BLE 数据 1:1 的 4h/24h。
