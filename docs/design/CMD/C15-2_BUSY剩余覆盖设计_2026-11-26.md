# C15-2 剩余覆盖设计（begin / trial / 终态 job_op）与遗留观察（2026-11-26）

> 文档状态：PENDING（设计待审）。设计成熟度：DESIGN_CANDIDATE。
> 适用范围：CMD-15 / C15-2 诊断剩余覆盖。
> 前置事实：变更 A（`5aaabea`）已入 `main`；accept-snapshot 分支已在设备受控复现中验证；原始残留 BUSY 未解释，现场已随重烧清除。

## 1. 已有结论

- 诊断功能在设备上可用：`branch=accept`、`job_active=1`、`job_op_valid=1`、`active_ops=1`、无截断。
- 该实验只验证 accept-snapshot 分支和 job/operation 关联，不解释原始 BUSY。
- begin/trial 分支、终态 `job_op` 尚无设备证据。

## 2. 实验 1：begin 分支（active operation 拒绝）

**目标诊断字段**

- `branch=begin`
- `job_active_before=0`
- `start_attempted=1`
- `operation_start_err == ESP_ERR_INVALID_STATE`（验收记录同时保存数值与符号映射）
- `mapped_busy_source=begin_operation_active`
- `active_ops>=1`

**cancel 触发路径不可行（已核对源码）**

原设计“cancel 后利用 `APP_C1_TEST_HOOKS` 暂停，再从 BLE 发第二次 tryconnect”不可执行：

- `ble_cmd.c` 的 BLE 命令任务串行执行队列命令；
- `network.cancel` 在该任务内同步调用 `app_operation_request_finish()`；
- `cancel_post_cleanup` 暂停发生在该调用内部；
- 暂停期间新的 BLE `network.tryconnect` 只能排队，不能执行；恢复后原 operation 已终态。

**可行方向 A：expire_post_cleanup（优先评估）**

- `operation.c` 的 `expire_post_cleanup` 暂停位于独立 expire 任务，不阻塞 BLE 命令任务；
- `app_operation_expire_one()` 在 cleanup 返回后暂停，此时 job 已清除、operation 仍 active；
- 暂停期间由 BLE 命令任务发送第二次 `network.tryconnect`，可进入 `begin` 并命中 `app_operation_has_active_locked()`；
- 成本：GOT_IP TTL 为 300000 ms；若停留在 ACCEPTED/CONNECTING，accepted TTL 为 45000 ms。需要设计“何时武装 hook、等待哪个 TTL、如何避免 worker 先失败并清理”；
- 需单独构建 `APP_C15_BUSY_DIAG + APP_C1_TEST_HOOKS`，并审查 hook 对实验的副作用。

**执行前置条件（方向 A 必须补齐）**

- 优先让第一次 operation 稳定进入 `GOT_IP`，再等待 300000 ms 的 GOT_IP TTL；不把 45000 ms accepted TTL 作为默认路径，因 CONNECTING 中 worker 可能先失败并清理；
- 串口记录 expire 任务已启动的证据；任务创建失败时源码会明确记录 TTL safety net disabled，出现即停止；
- hook 是单次武装：记录武装时刻、hold 时长、是否命中；未命中时用现有 `app_operation_test_hook_clear()` 清除，不假定必然命中；
- 第二次请求使用不同 `idempotency_key` 或不提供该字段；相同 key 会在 busy 检查前返回已有 operation 状态，无法进入目标分支；
- 记录 `app_mqtt_defer_restart_begin()` 的结果或等价证据：它先于 active operation 检查，若 MQTT restart 已 active 会提前返回 `ESP_ERR_INVALID_STATE`，不能误判为 active operation 拒绝。

**P1 前置：hook 目标关联（当前 hook 不具备过滤能力）**

- `app_operation_test_hook_pause()` 是全局单次武装：下一次符合条件且完成 cleanup 的 cancel/expire 即可消耗 hook；
- `expire_post_cleanup` 处没有按 operation ID 或 generation 过滤；
- `app_operation_expire_one()` 按槽位顺序扫描，不是按 deadline 排序；`cancel_post_cleanup` 也消耗同一个全局 hook；
- 实验前检查完整 operation 表，记录目标 operation 的 ID、generation、槽位，以及所有其他 active operation 的状态与 deadline；
- 必须证明目标是下一次可能触发该全局 hook 的 operation，而不只是“没有其他即将到期的 operation”；
- hook 武装至命中期间，禁止或可靠排除其他 operation 的 cancel/expire；
- 命中证据必须能把 hook pause 与目标 ID/generation 唯一关联；pause 日志只打印 generation，expire 路径后续 `finish <id> gen=` 只能作为关联证据的一部分，不能仅凭 generation 相同认定目标；
- 若无法证明上述条件，先做 test-only hook 目标过滤增强设计并审查，不得直接设备试。

**P1 前置：MQTT defer 来源区分**

`app_operation_start()` 顺序：

```text
app_mqtt_defer_restart_begin()
  → s_ops_mux 临界区
  → app_operation_has_active_locked()
```

两个位置都可能返回 `ESP_ERR_INVALID_STATE`；`operation_start_err` 只记录最终值，不能区分“MQTT restart active”与“active operation 存在”。

实验前二选一：

1. 为诊断构建增加 test-only 的 defer begin 结果记录：必须在 `app_operation_start_with_finish()` 调用 `app_mqtt_defer_restart_begin()` 后立即记录**本次调用**的结果，再进入 operation 锁区；不得使用可能被其他调用覆盖的全局结果；生产路径不变；
2. 或提供可靠前置检查，证明 MQTT restart 不处于 active 状态，并有证据证明该条件在目标 `app_operation_start()` 调用期间持续有效，而不只是实验开始前的一次读取。

未满足任一项时，不得把 `operation_start_err == ESP_ERR_INVALID_STATE` 判为 active operation 拒绝。

**可行方向 B：独立 test-only 触发任务**

- 在测试构建中由另一任务直接发起第二次请求，不依赖 BLE 命令队列；
- 需要新增 test-only 入口并审查其与命令层、锁序、来源权限的关系；
- 不作为默认方案。

**恢复/停止**

- 结束暂停后等待第一次 operation 进入 `expired`/`cancelled`，`cleanup_state=ok`；
- 核验 job 清除、`trial=idle`、STA/IP/internet_verified/MQTT 恢复；
- 若第二次被受理而非 busy，取消所有已受理 operation 并停止；
- 任一 cleanup 异常、hook 未命中、网络未恢复即停止。

**状态**：`NOT_IMPLEMENTED / 需 hook 目标关联保障（必要时增强）、MQTT defer 来源区分证据（诊断记录或可靠前置条件）与单独设备授权`。

## 3. 实验 2：trial 分支（当前顺序下 NOT_COVERED）

**实际判定顺序（源码）**

```text
idempotency_key
  → app_cmd_net_job_accept_snapshot()
  → job_active ? busy（branch=accept）
  → app_cmd_net_trial_busy()
  → app_cmd_net_job_begin_locked()
```

第一次 tryconnect 成功进入 `GOT_IP` 后，trial 建立但 `s_job.active` 仍为 1；第二次 tryconnect 会先命中 accept-snapshot 的 `job_active` 检查，返回 `branch=accept`，不会进入 trial 分支。

因此，“等待 trial 有效后第二次请求必然命中 trial”的结论**不成立**；当前顺序下无法稳定复现 `branch=trial`。

**结论**

- 不调整生产代码中的 accept/trial 检查顺序来提高覆盖率；
- trial 设备实验在当前命令顺序下记为 `NOT_COVERED`；
- 如未来仍要研究，需另行设计确定性的 test-only 并发触发方案，明确控制的两个时点，并先做 Host 验证。

**凭据边界（仅未来实验适用）**

- 正确口令仅由获授权操作者在本地安全输入，不进入对话、串口日志或新归档文件。

**状态**：`NOT_COVERED（当前顺序）；无设备实验计划`。

## 4. 实验 3：终态 job_op

正常 cleanup 顺序：

```text
cleanup 清除 job
  → cleanup 返回
  → operation finalize
  → operation 进入终态
```

`APP_C1_TEST_HOOKS` 的 `cancel_post_cleanup`/`expire_post_cleanup` 暂停在 cleanup 返回与 finalize 之间，能构造：

- `job_active=0`，operation 仍 active。

它**不能**构造目标状态：

- `job_active=1`，`job_op_state=terminal`。

因此：

- Host D04 已覆盖终态 `job_op` 的格式化输出；
- 设备侧若无“不改变生产状态机”的 test-only 构造方式，保留 `NOT_COVERED`；
- 不为覆盖率修改正常 cleanup/finalize 顺序。

**状态**：`NOT_COVERED（设备侧）；格式由 Host D04 覆盖`。

## 6. 原始残留 BUSY

- 2026-11-26 设备在无已知 operation ID 可查询的情况下返回 BUSY；
- 只读接口无法枚举 job/active op；重启后现场清除；
- 结论保持“未解释”，不得写成已定位或已修复。
