## 2. V2'：cut 注入（PASS，判据满足）

注入 `--mode cut --pass <真实口令>`，broker 在收到 response PUBLISH 时关闭且不回 PUBACK：

```
202087 operation: accepted op-6CE8775F967B290D
202097 rpc resp -> .../response/9001 {...,"state":"accepted"}
202117 resp ack gate armed msg_id=60235
203207 resp ack gate released msg_id=4242 (timeout)
208127 wifi: tryconnect: old disconnect consumed reason=8(ASSOC_LEAVE)   ← 试验第一步在此之后
208127 wifi: tryconnect: ssid='CMCC-502' ... scan=1
```

**判据成立**：worker 侧 `armed → released` 全部发生在 `tryconnect: ssid=` 之前——回包窗口被真正关掉了。

噪声说明：注入脚本当时按 SUBSCRIBE 次数重复下发 3 次（已修为单次），第 2/3 次触发 `rate_limited`，把 pending 覆盖成 4242，因此本轮日志是 `released ... (timeout)` 而非首次武装的 60235。语义无影响（本就无 ACK），但已修脚本避免误导。

## 3. V3'：孤儿自愈（部分达成，含新发现）

真实 AP + 正确口令下，试验 2.6s 到 `got_ip`（`.28`），op 进入 **GOT_IP → TTL 300s**，因此"≤25s 过期"在真实网络下**不可达**（与预判一致，非缺陷）。

已证部分（002 短期修有效）：

```
216197 IP_EVENT_STA_GOT_IP: 192.168.1.28
514037 operation: expire op-6CE8775F967B290D cleanup=ok     ← got_ip + 300s
514037 mqtt: defer_end site=expire/terminal depth_before=0
```

**解耦任务确实在 run_fn 之外驱动了过期**（本形态下 run_fn 已返回，属 GOT_IP 形态）。

**新发现（DEF-MQTT-003 候选）**：`cleanup=ok` 之后设备**仍停在 `192.168.1.28`**，而 `cfg_state=static`、`persistent_static_ip=192.168.1.50`——cleanup 报告成功却没有把运行态恢复到持久静态配置。手动 `network.reconnect` 后才回到 `.50`。这与"孤儿自愈"的目标直接冲突：槽释放了，但设备停在错误的网络形态。

## 4. E1/E2/E3（未执行）

需 `APP_WIFI_FAULT_INJECT=on` 独立构建（已构建到 `build-fi/`，未烧写）。只有它能稳定造出"trial ACCEPTED >20s 且 run_fn 阻塞"，从而验证：
- E1：`expire cleanup=ok` 与 run_fn 侧 `stale after wait, no job touch` 同现（R5 防线）；
- E2：run_fn 阻塞时其他 op 仍按期过期；
- E3：`expiring` 闸并发竞态（C1 hooks）。

## 5. 注入脚本加固（已实施）

- 新增 `--expect-client`（默认 `B0A73228C8E4`）：CONNECT 的 client_id 不含该串直接断链。起因：本轮有一台 `192.168.1.4` 的设备连到注入 broker（它在 CONNACK 后被立即关闭，未收到任何请求，未改状态）；
- 请求改为**每连接只发一次**（此前按 SUBSCRIBE 次数重复）；
- 新增 `--pass` 传真实口令。
