## 2. 根因（串口实证，两轮一致）

```
I (15140071) ble_cmd: rx v1 cmd=network.status id=rcv-3
I (15140081) NimBLE: GATT procedure initiated: notify; att_handle=10   → ×3
```

设备**收到并即时回复**了每条命令；但客户端 20B 分片写在 WiFi STA 切换期间
被排队 20–30s 才送达，客户端 20s 超时先触发。**BLE 命令通道在 WiFi 切换窗口
拥塞（NimBLE/WiFi 共存），不是设备故障、不是协议问题。**

round2 的 BLE 断链（MQTT 子系统软重启后）与 round3 的拥塞（WiFi 重连中）
是同一类的射频共存现象。

## 5. 下轮改进（v11 提案，待评审）

1. **WiFi 切换期禁用 BLE 轮询**：`operation.get` 与 `network.status` 在
   MQTT 源均为 ALLOW（`cmd_policy` 明示），且 op 为 MQTT-owned → **轮询全部
   走 MQTT（同一 EMQX）**，BLE 只用于门禁读、改指向、恢复与终态复核。
   这可根除本轮 fatal 与 round2 的恢复失效。
2. **`failed/connect_failed` 是否允许一次重试**：现行规则"failed/cancelled
   立即 STOP 不重试"是为防绕过验收，但 `connect_failed` 是射频层瞬态。
   建议：仅 `connect_failed` 允许一次重试并单独标记，其余 failed 仍 STOP。
3. **tryconnect 目标 SSID 选择**：对当前已连 SSID 做 tryconnect 需先断开，
   失败率偏高；可考虑改用持久 SSID（TQ2026）或先断开再试的策略，需评审。
