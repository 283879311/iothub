# DEF-BLE-001 取证结果：H1 确认（对端僵尸链路，2026-11-05）
> **状态**：ARCHIVED（文档状态标定 2026-11-14，定义与索引见 [docs/README.md](README.md)）


> 镜像：`50c75bc4…`（含 `cf`/`rx_age` 诊断字段）。
> 结论：**H1 成立、H2 排除**。泄漏是**主机侧控制器保留 ACL** 造成的僵尸链路，不是设备标志悬挂；设备的 `conn=1` 是事实，广播停止是正确行为。

## 1. 复现方法

`tools/ble_p0/ble_leak_repro.py`（新增）：每个子进程连接设备 + 发一条 `device.info`，然后 **SIGKILL 自己**（不发 DISCONNECT）；父进程按轮次拉起。

## 2. A/B 对照（同一镜像、同一主机）

| 模式 | 轮次 | 结果 | 扫描可见性 |
| --- | --- | --- | --- |
| **kill**（异常终止） | 1 | `[1/1] ok (2.4s, killed)` | **NOT FOUND（悬挂）** |
| **clean**（正常 disconnect） | 3 | 3/3 ok | FOUND（广播恢复） |

kill 单轮即 100% 复现；clean 多轮不触发。

## 3. 关键判据：`cf` + `rx_age`

泄漏现场 diag（`serial_leak.log` / `serial_ab.log`）：

```
wifi mode=1 ch=3/0 adv=0 conn=1 cf=0 rx_age=259
wifi mode=1 ch=3/0 adv=0 conn=1 cf=0 rx_age=8360
wifi mode=1 ch=3/0 adv=0 conn=1 cf=0 rx_age=42587
```

- `conn=1`：应用层 `s_connected` 为真；
- **`cf=0`**：`ble_gap_conn_find(s_conn_handle)` 成功——**协议栈仍持有该链路**；
- `rx_age` 单调增长：链路在、但无任何应用层写入。

判读：H2（应用层标志悬挂）**排除**（若悬挂，`cf` 应为 `BLE_HS_ENOTCONN`）。H1 成立：主机进程被杀后，**主机控制器仍在链路层应答**，NimBLE 的 supervision timeout 永不触发，设备无从分辨"僵尸"与"静默客户端"。

## 4. 根因与责任面

- 根因在**主机侧**：进程被杀 ≠ 控制器发 `LL_TERMINATE`；BlueZ/内核保留 ACL。
- 设备行为正确：有连接即停止广播；`adv watchdog` 以 `connected` 为门禁，而 `connected` 此刻是**真实**的，所以看门狗不该救、也救不了——这正是 DEF-BLE-001 立案时的推断，现由 `cf=0` 实证。
- 主机侧恢复手段：`bluetoothctl disconnect` / 重置适配器（需 root）/ 让对端主动断开。

## 5. 固件侧可选缓解（待决策）

| 方案 | 触发条件 | 风险 |
| --- | --- | --- |
| A. 空闲断链 | `rx_age > T`（建议 90s）且**无 notify 订阅** → `ble_gap_terminate` | 误杀"订阅后静默"的合法会话；用订阅状态可规避 |
| B. 客户端心跳 | 小程序 30s 心跳，设备 90s 无心跳断链 | 需小程序版本配合 |
| C. 维持现状 | 硬复位恢复 | 用户体验不可接受（现场已发生 2 次） |

建议 A（设备侧即可闭环），B 作为后续协议增强；C 不用。A 的判据数据（`rx_age`）本轮已具备。

## 6. 测试环境提示

- 任何"kill -9 客户端"的测试都会留下僵尸链路，**每轮泄漏后必须硬复位**；
- 复现器已内置"连续失败 3 次即停止"，避免在悬挂态空转；
- 脚本只做连接 + 一条只读查询，不写配置。
